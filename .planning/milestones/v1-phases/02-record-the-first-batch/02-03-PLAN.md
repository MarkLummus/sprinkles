## Phase Goal

**As a** home ice cream maker, **I want to** write on the churned recipe what I actually did — the amounts I really used, the steps I changed, what I measured, and how it tasted — **so that** the next version has evidence to cite instead of my memory.

*Provenance: as recorded in 02-01 — a mechanical restatement of the ROADMAP `**Goal:**` line for Phase 2, not a new story. Run `/gsd mvp-phase 2` to rewrite the Goal line itself.*

<objective>
The half of the record written a day later: how it turned out.

A tasting is its own dated event belonging to the batch (D-01) — added after the churn, saved with its words or its marks and nothing else required, and read back in the margin beneath the churn section. Its marks land on four fixed core axes plus whatever axes the version declared for itself, each a nine-stop keyboard group with behavioural anchor words at the ends. A batch with no tasting says so, in words, and offers to add one — which is how the binder's 14 silent batches out of 29 become a fact the record states rather than an absence nobody can read.

Then the record closes: amend with a dated amendment that never retakes the snapshot, the version line carrying the latest churn date, the margin listing a version's batches, and the 2 Aug 2026 batch seeded through the same functions a maker's own save uses — so the phase's working case exists in the store, exactly as the photographs have it.

Purpose: after this plan the whole loop the phase promised is real. A maker can record a churn, come back a day later and record how it tasted, come back a week later and correct something, and reopen all of it against the version it was made against.

Output: the complete batch record — churn plus tastings — writable, readable by URL, amendable, and seeded with the transcription Mark confirmed.
</objective>

**Domain — `app/src/domain/batch.js`.** Add four functions, all pure and all consistent with the module's existing presence-over-truthiness rule.

`isTastingSaveable(tasting)` is OBS1-01's gate and D-02's rule in code: it returns true when the tasting's `words` is a string with content after `trim`, **or** when its `marks` object has at least one own key. Nothing else is required — not a date, not a temperature, not a meltdown loss. Write the words test as `trim` followed by a length check, and state the contract in a comment: `String.prototype.trim` strips Unicode whitespace, including the non-breaking space and the ideographic space, so a field holding only invisible characters is not words; length is counted in UTF-16 code units, so a single emoji is words even though it occupies two of them. Write the marks test as an own-key count, never as a truthiness scan over the values — a mark of `0` is not a legal stop today, but the gate must not be the thing that decides that.

`sortedTastings(batch)` returns a new array ordered by `date` ascending with undated tastings last (D-03), comparing the `YYYY-MM-DD` strings directly and keeping the added order within each group. It never sorts in place.

`hasTasting(batch)` returns whether the batch has at least one tasting — the test behind "not yet evaluated" (D-05).

`addTasting(batch, tastingFields, { id })` returns a new batch with the tasting appended, carrying the supplied id. It does not validate: the caller gates on `isTastingSaveable`, matching the domain modules' existing habit of returning facts rather than throwing. It leaves `snapshot`, `recordedAt` and `amendedAt` untouched — adding a tasting is never an amendment, and the snapshot is never retaken (D-06).

A tasting is `{ id, date, tastingTempC, marks, meltdownLossG, words, nextTimeNote }`. `date` is a `YYYY-MM-DD` string or `null`; `tastingTempC` and `meltdownLossG` are finite numbers or `null`; `marks` is an object whose keys are axis keys and which holds a key only for a marked axis; `words` and `nextTimeNote` are strings or `null`.
