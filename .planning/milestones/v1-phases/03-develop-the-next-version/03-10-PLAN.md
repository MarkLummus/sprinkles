<objective>
Close G-03-6 and G-03-3's symptom 3, which the diagnoses found to be one seam: give the app a derived step number, keep the stored one as identity, and thread the derived one through every place a step number reaches a reader — including the selector option list, where the removed step must stay so the bound value has somewhere to sit.

Purpose: the stored key is doing two jobs. It is the step's identity — the comparison pairs parent to child on it, four pen handlers match on it, a row's step reference names it, a batch's step changes are keyed by it, the seed's uses lists key on it — and it is also the number printed for the step at every one of thirteen display sites. Nothing anywhere computes a position, so removing a step can only leave the survivors' numbers where they were: a child that removed step 2 reads 1, 3, 4 … 10 on the page it is made from, and a grandchild that also removed step 5 reads 1, 3, 4, 6, 7 … Renumbering the stored key was tested directly and is not available — it makes eight of nine surviving steps read as rewritten. The same split is behind the selector jumping to step 1: the option list drops the removed step while the bound value still names it, and React selects the first non-disabled option instead, showing the maker a step the data does not hold.

Output: one derived map, threaded once, so the whole page speaks one numbering.
</objective>

<flagged_assumptions>

**The step anchors keep the stored key.** `id="method-step-{n}"` is an address, not a number a reader reads, and `02-PATTERNS.md` reserves it for per-step targeting. Rewriting anchors to a position would make a saved link point at a different step after any removal. They stay on the stored key deliberately, and that is recorded here so it does not read as a site that was missed.
