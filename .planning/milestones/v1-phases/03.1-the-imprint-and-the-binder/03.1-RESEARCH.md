The briefs settle everything they name. The decisions below fill what they left to this discussion and, where marked, revise them; each revision is recorded for Impeccable to absorb into the briefs and `DESIGN.md`.

**Region names (revises the briefs' vocabulary)**
- **D-01:** The book vocabulary is dropped from every running head. Mark: "these are 'inside baseball' terms; only someone who knows the background would ever understand 'headnote' or 'imprint'; this product is not a book." The heads read, in page order: *(no head on the recipe block)*, **Versions**, **Ingredients**, **Balance**, **Method**, **Notes**. "Versions" was chosen over Imprint, Versions and batches, History, Log, Development and others "for now". — **Reversibility:** reversible — six strings and their tests; the brief's names live only in planning files.
- **D-02:** The recipe block (name, version line, intro paragraph) wears **no running head**: the recipe name in 2rem is its head. The heading outline is h1 recipe name, then h2 Versions, Ingredients, Balance, Method, Notes; no hidden "Recipe" heading.
- **D-03:** The version line under the name reads just the version line ("50 g oil · 800 g"). The churned date moves wholly into Versions; nothing recorded prints in the recipe block. This supersedes Phase 2's D-13 placement of the churn date in the version line (the fact itself, latest churn date and no count, stands).

**Versions: what it holds and in what order**
- **D-04:** Reading state, top to bottom: **the openers**, then **the version list**, then the current version's **lineage** (Parent / Batch / Reason as labelled lines, then Show changes), then **the batch list**. The block's width is everything right of the recipe block's 65ch measure; the two blocks' seam does not line up with the spread's.
- **D-05:** Openers sit as two groups on two lines: **Develop** alone on the first line (the plan's pen); **Record batch** (or **Record another**), **Amend**, **Add tasting** together on the second (the record's), separated by the small gap. Which openers appear follows Phases 2 and 3 (Record batch when the version has none; Record another, Amend and Add tasting when a batch is in view).
- **D-06:** While a pen is open its ceremony **replaces the openers** at the top of Versions; the other openers are not shown disabled, since the ceremony's presence says why. The version list, lineage links and batch list stay beneath as plain text with one hint sentence for the block: **"Links return after you save or cancel."** This narrows Phase 3's D-UAT-1 (every opener visible and disabled with its reason) to the links only; the one-pen rule itself is unchanged.
- **D-07:** The version list is a **vertical list, one version per line, flat** (no indent by lineage), in creation order, the current entry by weight and outline as plain text, "churned" in small print beside a churned version's line, every other entry an ink link. No batch count (Phase 2 D-21).
- **D-08:** The lineage reads as **labelled lines**: `Parent` (the parent's line, a link), `Batch` (the cited batch's churn date, a link; absent when none was cited), `Reason` (the maker's text, or "none recorded"), then **Show changes** as a control on its own line at the end. A root version shows no lineage. The reason paragraph therefore leaves the recipe block. The toggle's pressed state and `?changes` addressing are unchanged (Phase 3 D-02).
- **D-09:** The batch list is **always a list, one batch per line, even with one**: "churned 2 Aug 2026" as an ink link, the open batch by weight and outline as plain text, an amended batch adding "amended 5 Aug 2026" in small print on its line. With no batch the same line reads **"no batch yet"** in ink, and Notes also keeps a "no batch yet" placeholder line where the record would sit (both places).

**Control labels and their order (revises Phase 3 D-01)**
- **D-10:** **Cancel comes first in every pair.** Plan's pen on a churned version: **Cancel · Save**, where Save creates the child. Plan's pen on an unchurned version: **Cancel · Save as · Save**, the desktop pattern: Save as forks, Save writes over. Batch pen and tasting pen: **Cancel · Save**. The foot band repeats whichever set the ceremony shows. Mark: "when there are 2 save versions, the Save as and Save are fine; this is a common pattern in software." Supersedes Phase 3 D-01's outcome-at-the-end labels; D-01's opener wording is replaced by D-11.
- **D-11:** Articles are dropped and labels shortened: **Develop**, **Record batch**, **Record another**, **Amend**, **Add tasting**, **Show changes**, **remove**, **restore**, **change** / **done**, **add purpose**, **add aside**, **done differently**. The batch pen's per-step line is labelled **Done differently** (was "What did you do differently?"); the **Skipped** checkbox keeps its word.
- **D-12:** Capitalisation: **sentence case** for buttons and selects ("Save as", "Record batch", "Show changes"); **lowercase** for in-line text controls that sit inside a row or a step and read as part of its text ("remove", "restore", "change", "done", "add purpose", "add aside", "done differently"); units lowercase everywhere (existing rule). Recorded for `DESIGN.md`.

**The control treatment (the brief's "binder", `route-recipe.md` § 6 and § 8)**
- **D-13:** The treatment is written as **global element rules** in `app/src/styles/app.css` (button, select, `:focus-visible`, checkbox, date input, number input, textarea, a), every value through a token. The list page's Export and Import buttons and its links inherit it without being designed; no page can paint browser chrome again. — **Reversibility:** reversible — rules can be scoped later by wrapping them in a selector.
- **D-14:** Outline weights: **focus 1.5px** (`--focus-outline-width` reads `--rule-baseline`) on every focusable element, including the graduated rules, radios, checkboxes and links; **state 1px** (`--rule-graduation`) for pressed, current, open batch and marked rows. A focused element that is also stateful reads both. The graduated rule's own `:focus` rule is retired in favour of the global `:focus-visible` rule.
- **D-15:** **Hover** thickens a control's border from 1px to baseline weight (1.5px), nothing moves and nothing recolours, so hover and focus read alike; the pointer is a hand over anything that opens or links. Revises the brief's "nothing on hover".

- **D-19:** **Number inputs** keep `type="number"` with the spinner arrows hidden in CSS; sized to three digits and a sign as the brief says.
- **D-20:** **Placeholders:** the version-line field and the reason field carry an example in ink small print ("e.g. 55 g oil · 800 g"; "e.g. less oil after the batch of 2 Aug"); no other field carries one; the date input's native "mm/dd/yyyy" stays as part of its exception. - **D-21:** **Blocked save:** Save stays enabled; pressing it shows the sentence beside both pairs, outlines the offending row, and **moves focus to the offending field** (the grams field, or the version-line field for a blank or duplicate line) so the row scrolls into view. No live dashing while the maker is still typing.
- **D-22:** In the pen the Step column widens by a new token so each option reads "3. Build the base"; the **Data column goes blank-headed** in the pen to make room, as the brief allows; the name column absorbs the rest.

**The pen keeps the page: on-demand fields, the uses line, the foot, Escape**
- **D-23:** An emptied purpose or aside field **collapses back to its "add purpose" / "add aside" control when it loses focus while empty**; the draft stores no purpose; focus is not moved. Opening one via the control focuses the new field.
- **D-24:** The uses line's control reads **"change"** closed and **"done"** open; the checklist **stays open until "done"** is pressed, and the line of names above it updates live as boxes change. - **D-25:** The batch pen's per-step line is **on demand**: the Skipped checkbox is always present; the line sits behind a "done differently" text control, an emptied line collapses on blur, and Amend opens the lines that hold text. - **D-26:** The foot band, shown only while a pen is open: a **hairline ink rule across the whole page**, then the pair **right-aligned under the Notes column**, the blocked-save sentence beside it; no head, no opener, no field. Mark: "I like the hairline rule across the page, but I want it right-aligned under the notes column."

## Summary

This phase is a rebuild, not a build: three surface briefs and a whole-page critique are already binding, and CONTEXT.md's decisions (D-01 to D-30) resolve everything the briefs left open. There is no new stack to select — React 19 + Vite + react-router + the existing token system stay exactly as they are. The work is (1) lift the version strip, lineage line, ceremony, churned-date, and every batch-side opener out of `Headnote.jsx`/`BatchMargin.jsx` into a new `Versions` region beside the recipe block; (2) add a foot band that repeats the open pen's Save/Cancel pair; (3) write global element rules (`button`, `select`, `:focus-visible`, checkbox, date input, number input, textarea, `a`) in `app.css` so no control paints browser chrome; (4) close three named build gaps — the rule heads never strike the parent figure while the plan's pen is open, the six rules never leave the tab path in the pen, and a non-numeric grams field saves the parent's value silently; (5) fix the total row's double-unit wrap and the pen's cramped Step column.

The single most consequential finding from reading the code rather than the brief: **every component test in this repo renders through `renderToStaticMarkup` (`react-dom/server`) inside Vitest's default `node` environment — there is no jsdom, no `@testing-library/react`, and no click/keyboard driver anywhere in the tree** [VERIFIED: app/vitest.config.js:1-10, app/package.json (devDependencies list — no jsdom, no testing-library), app/src/ui/BatchMargin.test.jsx:162]. This means the phase's own focus-management requirements (D-27 return-to-opener, D-27's fork-to-child's-Develop-control, D-24's Escape closing an untouched pen, D-23's collapse-on-blur, D-24's checklist open-until-"done") **cannot be exercised by an automated assertion beyond checking a static `autofocus` attribute or a `tabIndex` value in the rendered HTML string** — an effect that calls `ref.current.focus()` after a state transition never runs under `renderToStaticMarkup`. CONTEXT.md's own Claude's Discretion section already anticipates this: "the re-critique is the human check." The plan should keep automated tests to what `renderToStaticMarkup` can prove (markup shape, attribute presence, ARIA labels, disabled state, className) and route every actual focus-transition and Escape-key behavior to the phase's UAT / Impeccable re-critique, exactly as the existing `Headnote.jsx`/`BatchMargin.jsx` focus-return refs already do today with no test coverage.

The second consequential finding: two of the three "build gaps" the critique names are one- or two-line wiring fixes with an exact call site already identified by the critique itself and confirmed unchanged in the current tree — `RecipePage.jsx:1041` still passes only `changeDiff` (null while developing) to `FormulationNote`, and `FormulationNote.jsx:16` still sets `tabIndex={-1}` only for `mode === 'recording'`, never `'developing'`. The third gap (blocked save on a non-numeric grams value) requires a genuinely new domain rule in `lineage.js`'s `blockedSaveMessage`, which today only checks for a blank grams field, never a non-numeric one.

**Primary recommendation:** Treat this as three independent workstreams that touch mostly disjoint files — (A) the Versions region extraction + foot band (mostly `RecipePage.jsx`, a new `Versions.jsx`, `Headnote.jsx`, `BatchMargin.jsx`, `VersionStrip.jsx`), (B) the global control treatment (almost entirely `app.css` + `tokens.css`, touches every component only by className/markup, not logic), and (C) the three build gaps + column arithmetic (small, targeted diffs in `RecipePage.jsx`, `FormulationNote.jsx`, `lineage.js`, `IngredientTable.jsx`). (B) and (C) can proceed with today's test infrastructure; (A)'s focus-return correctness is UAT-verified, not unit-tested.

### Pattern 1: Lifting region content without changing state ownership

**What:** `RecipePage.jsx` already owns every piece of state the Versions region needs (`mode`, `draft`, `penDraft`, `tastingDraft`, `openPen`, `penReason`, `blockedMessage`, `batches`, `citedBatch`, `parentVersion`, `versions`, `versionIdsWithBatches`). Building `Versions.jsx` is a pure render-tree move: take the JSX currently inside `Headnote.jsx`'s `mode === 'developing'` branch (lines 48-130) and its lineage/openers block (lines 169-232), plus `BatchMargin.jsx`'s openers/list/ceremony (lines 185-259, 262-357's non-field parts), and reassemble them under one new component that receives the same props `RecipePage.jsx` already threads to `Headnote`/`BatchMargin` today.

**When to use:** Whenever a brief's region reorganization does not change *what* state exists, only *where* it renders — the safest kind of large-diff UI change, because every existing domain function (`derivePenState`, `isPenDraftDirty`, `blockedSaveMessage`, `buildDiff`) is untouched.

**Example (today's call site to preserve, `RecipePage.jsx:954-974`):**
```jsx
// Source: app/src/ui/RecipePage.jsx:954-974 (read this session)
<Headnote
  version={version}
  mode={mode}
  draft={draft}
  penDraft={penDraft}
  openBatch={openBatch}
  batches={batches}
  citedBatch={citedBatch}
  parentVersion={parentVersion}
  showingChanges={showingChanges}
  blockedMessage={blockedMessage}
  openPen={openPen}
  penReason={penReason}
  onChangeChurnDate={handleChangeChurnDate}
  onStartDeveloping={handleStartDeveloping}
  onCancelDeveloping={handleCancelDeveloping}

  onSaveAsNewVersion={handleSaveAsNewVersion}

```
Every one of these props/handlers already exists and is already tested indirectly through `RecipePage.test.jsx`'s `derivePenState`/`isPenDraftDirty` unit tests — the plan should pass the *same* prop set to the new `Versions` component rather than inventing a new shape, so no handler signature changes.

### Pattern 2: The foot band repeats controls, never re-derives them

**What:** D-26's foot band shows "the same two controls, the same labels" as whichever ceremony is open. Since `openPen` (`'plan' | 'record' | 'amend' | 'tasting' | null`) already names which ceremony is showing, the foot band is a `switch`/if-chain over `openPen` that renders the *same* `onClick` handlers already passed to the top ceremony — never a second copy of the button logic.

**When to use:** Any UI requirement to "repeat a control elsewhere on the page" — render the same handler reference from two JSX sites, never duplicate the handler.

**Example (pattern, not existing code):**
```jsx
// Illustrative — RecipePage.jsx's return, after side-region, before </article>
{openPen && (
  <footer className="pen-foot">
    <hr className="pen-foot__rule" aria-hidden="true" />
    <div className="pen-foot__controls">
      {openPen === 'plan' && (
        <>
          <button type="button" onClick={handleCancelDeveloping}>Cancel</button>
          {canSaveOver && <button type="button" onClick={handleSaveOverVersion}>Save</button>}
          <button type="button" onClick={handleSaveAsNewVersion}>{canSaveOver ? 'Save as' : 'Save'}</button>
        </>
      )}
      {(openPen === 'record' || openPen === 'amend') && (
        <>
          <button type="button" onClick={handleCancelRecording}>Cancel</button>
          <button type="button" onClick={handleSaveBatch}>Save</button>
        </>
      )}
      {openPen === 'tasting' && (
        <>
          <button type="button" onClick={handleCancelTasting}>Cancel</button>
          <button type="button" onClick={handleSaveTasting}>Save</button>
        </>
      )}
    </div>
    {blockedMessage && <p className="pen-foot__blocked">{blockedMessage}</p>}
  </footer>
)}
```
Note D-10's Cancel-first ordering and D-10's "Save as / Save" desktop pattern on an unchurned version — `canSaveOver` is already computed in `Headnote.jsx:52` (`batches.length === 0`) and should be lifted to `RecipePage.jsx` once, since both the top ceremony and the foot band need it.

### Pattern 3: Global element rules for the binder (CSS only, no component change)

**What:** D-13 requires the binder to be written as bare-element rules (`button`, `select`, `:focus-visible`, checkbox, date input, number input, textarea, `a`) in `app.css`, so every existing and future control inherits it with zero markup change. This is provably possible without touching any `.jsx` file: every button/select/input in the codebase today is a native element with no library wrapper.

**When to use:** Any global visual-language rule that must apply uniformly and must survive future controls (e.g. the list page's Export/Import buttons, D-13's explicit example) without being re-applied per component.

**Example — the checkbox pattern already proven in this codebase for radios, extended to checkboxes:**

### Anti-Patterns to Avoid

- **Re-deriving `openPen`/`penReason` inside the new `Versions` component:** `derivePenState` (`RecipePage.jsx:193-207`) is the one call site (D-UAT-1's own closed gap, G-03-9). Passing `mode`/`amendingBatchId`/`tastingDraft` down separately and re-deriving inside `Versions.jsx` would reopen the exact bug class G-03-9 closed.
- **A second copy of `blockedSaveMessage`'s check for the foot band:** the foot band reads the *same* `blockedMessage` state RecipePage already sets (line 263, `useState(null)`), never a second computed value.
- **Styling `button`/`select` globally without first checking `RecipeList.jsx`'s Export/Import buttons and file-input trigger button:** D-13 explicitly requires these inherit the binder "without being designed" — verify visually (or via the existing `RecipeList.test.jsx` markup) that the hidden file input (`tabIndex={-1}`, `aria-hidden`, `RecipeList.jsx:77-85`) is not accidentally made focusable by a blanket `button:focus-visible` rule turning into `*:focus-visible` — it must stay scoped to actual interactive elements.
- **Reusing `.graduated-rule:focus` (app.css:754-757) as the new global `:focus-visible` rule's template without retiring it:** D-14 explicitly retires the rule's own `:focus` rule in favor of the global one; leaving both would double-apply the outline (or leave a stale 1px rule alongside a new 1.5px one, producing two visible rings on Chrome/Firefox which paint the outline as a single box-shadow-like ring, not additive, but the *declared* CSS becomes contradictory and the next person to touch focus styling will not know which rule is authoritative).

## Common Pitfalls

### Pitfall 1: The focus-outline token carries two different meanings today, and D-14 splits them

**What goes wrong:** `--focus-outline-width` (currently `1px`) is read by **seven** sites in `app.css` [VERIFIED: app/src/styles/app.css:202, 281, 479, 755, 820, 886, 968 — grep'd this session]. Of these, four are **state** outlines that must stay at `--rule-graduation` (1px) per D-14 (`.headnote__show-changes[aria-pressed='true']` at 202, `.version-strip__item.is-current` at 281, `.ingredient-table tbody tr.is-marked` at 479, `.batch-margin__list li.is-open` at 886), and three are **actual `:focus`** outlines that D-14 wants moved to 1.5px (`.graduated-rule:focus` at 755 — to be retired per D-14 in favor of the global rule; `.ink-field:focus` at 820; `.axis-mark__stop input[type='radio']:focus` at 968).

**Why it happens:** Phase 3 conflated "an outline at the shared weight" with "the focus outline," since both happened to be 1px and both used the one token that existed. D-14 introduces a real distinction (focus 1.5px vs. state 1px) that the current code has no way to express — redefining `--focus-outline-width` to `1.5px` in `tokens.css` would silently thicken all seven sites, not just the three that should move.

**How to avoid:** Re-point the four state sites to `var(--rule-graduation)` explicitly, keep `--focus-outline-width` reading `var(--rule-baseline)` (1.5px) as D-13's Controls table specifies, and replace the three `:focus` rules with the new global `:focus-visible` rule (retiring `.graduated-rule:focus` and `.ink-field:focus`/`.axis-mark__stop input[type='radio']:focus` as bespoke rules, per D-14: "the graduated rule's own `:focus` rule is retired in favour of the global `:focus-visible` rule").

**Warning signs:** After the token change, every pressed/current/marked/open element visibly thickens along with real focus rings — a dead giveaway the four state sites were not re-pointed.

### Pitfall 2: The total row prints its unit twice and never sets `white-space: nowrap`

**What goes wrong:** `IngredientTable.jsx`'s total row (`tfoot`, currently lines 625-641 — the critique's pointer of "629-633" has drifted slightly since 03-11 but names the same block) strikes `baselineTotalText` and prints `totalDisplayText` beside it; both come from `formatGrams()` (`domain/composition.js:87-93`), which already appends `" g"`. The result renders as `~~799.7 g~~807.7 g` — the unit appears twice, with no `white-space: nowrap`, so it wraps to two lines exactly as UAT test 17 observed ("the Total row grams value doesn't need to wrap... currently total is shown on 2 rows when show changes mode is on").

**Why it happens:** `formatGrams` is a formatting convenience built for the single-value case (D-22); nobody revisited it once a struck-and-current pair needed to share one unit.

**How to avoid:** Per D-22/the brief's "strike the bare number in the total with the unit once and `white-space: nowrap`" — either strip `" g"` from the struck value at the render site (e.g. `baselineTotalText.replace(' g', '')`) or add a bare-number formatter alongside `formatGrams` (e.g. `formatGramsValue`) and append `" g"` once after the current value; then add `white-space: nowrap` to the total row's numeric cell.

**Warning signs:** Any place that strikes one `formatGrams()`/similarly-unit-suffixed string beside another risks the same double-unit bug — the same pattern must be checked wherever a diff renders two already-formatted strings adjacently (the grams cell and step cell already avoid this because `row.grams` is a bare number with `" g"` appended once in JSX, not inside the formatter — see `IngredientTable.jsx:111-113,123`).

### Pitfall 3: Firefox has no CSS hook to hide the native date-input calendar icon

**What goes wrong:** The brief (route-recipe.md § 6, route-recipe-version.md § 6) requires "the calendar icon hidden" as a binding control-treatment rule with the segment highlight as the only named exception. `::-webkit-calendar-picker-indicator { display: none }` works in Chromium and WebKit (Safari) but **Firefox provides no pseudo-element or property to target the built-in calendar icon on `<input type="date">`; there is no reliable pure-CSS workaround** [CITED: github.com/tailwindlabs/tailwindcss discussion #19070, confirmed via web search this session].

**Why it happens:** The date-input calendar affordance is part of Firefox's internal shadow-root rendering with no exposed styling hook, unlike Chromium's `-webkit-calendar-picker-indicator`.

**How to avoid:** Apply the WebKit rule (it costs nothing in Firefox — the selector simply matches no element there) and document the Firefox gap as a known, accepted limitation rather than attempting a JS-based custom date picker, which the brief's "browser's own date input for its validation and keyboard entry" wording explicitly wants to avoid. This is a genuine gap between the confirmed brief's wording and what CSS can deliver — flag it to Mark rather than silently declaring it solved (see Open Questions).

**Warning signs:** A re-critique performed only in Chrome/Safari will report this control fully compliant; the same page in Firefox will still show the calendar icon.

### Pitfall 4: `renderToStaticMarkup`-based tests cannot prove any focus-management requirement in this phase

**What goes wrong:** D-21 (move focus to the offending field on a blocked save), D-23 (focus a newly-opened purpose/aside field, no focus move on collapse), D-24 (Escape closes the uses-checklist and returns focus to "change"), D-27 (Escape/Save/Cancel all return focus to the opener; a fork's save moves focus to the child's Develop control) are all real DOM side effects (`ref.current.focus()` inside a `useEffect`). Every existing focus-return implementation in this codebase (`Headnote.jsx`'s `developButtonRef`/`wasDevelopingRef`, `BatchMargin.jsx`'s `addTastingButtonRef`/`tastingWasOpenRef`) has **zero automated test coverage today** — `Headnote.test.jsx`/`BatchMargin.test.jsx` never reference `focus`, `Ref`, or `useEffect` at all [VERIFIED: grep of both test files this session, zero matches].

**Why it happens:** `renderToStaticMarkup` produces an HTML string with no live DOM, no event loop, and no effect execution — there is nothing for `useEffect` to run against. The one place an `autofocus` attribute is checked (`BatchMargin.test.jsx:162`, `expect(dateInput).toContain('autofocus=""')`) only proves the *initial* render's attribute, never a focus *transition*.

**How to avoid:** Do not propose introducing jsdom/`@testing-library/react` for this phase unless the user explicitly asks — CONTEXT.md's own Claude's Discretion section defers this exact question ("Test strategy: which of these are DOM-environment component tests versus the existing budget-computing token test; the re-critique is the human check"), which reads as an implicit decision to keep the existing infra and treat focus-transition correctness as UAT/re-critique-verified, not unit-tested. The plan should write `renderToStaticMarkup` assertions for every *static* fact (an element has `tabIndex={-1}`, a field has `autoFocus`, a disabled control states its reason in text, the blocked-save row carries the marked-row class) and list every focus-*transition* requirement (D-21, D-23's focus-on-open, D-24's Escape, D-27's returns) as a UAT-only verification item.

**Warning signs:** A plan that claims "tested" coverage for Escape-key behavior or the fork-to-child-focus requirement without a `checkpoint:human-verify` gate has over-claimed automated coverage this test infrastructure cannot provide.

### Pitfall 5: `blockedSaveMessage` today only blocks a blank grams field, never a non-numeric one

**What goes wrong:** `lineage.js:150-163`'s `blockedSaveMessage` checks `draftRow.grams === undefined || draftRow.grams === ''` — a value like `"4o"` or `"-5"` passes this check untouched, exactly the gap the critique's third P1 names ("a grams field holding '4o' saves the parent's value silently"). `RecipePage.jsx`'s own `draftVersion` construction (lines 414-432) already has a related guard — a non-parseable string keeps the row's own (parent) grams for the *live figures*, silently — but the save path (`buildPenFields`, lines 883-909) coerces with `Number(draftRow.grams)` and falls back to `row.grams` (the parent's value) the same way, meaning a save can silently persist the parent's number under a value the maker can still see on screen as "4o".

**Why it happens:** D-21 (blocking a non-numeric grams field) is new in this phase; Phase 3 only implemented D-04's blank/duplicate/uniqueness checks.

**How to avoid:** Extend `blockedSaveMessage` with a per-row check that a non-removed row's `draftRow.grams` matches a non-negative-number pattern (Claude's Discretion names the exact regex shape: "a non-negative number with up to two decimals, kept as typed") before the blank check even applies (a value like `"4o"` is neither blank nor a valid number, so this new check must run wherever the blank check runs, in the same fixed order so only one message shows at a time — D-04's "checked in a fixed order so the maker is told about one thing at a time" already establishes this discipline). Word the new message following the brief's own example: `"whole milk's amount is not a number"`.

**Warning signs:** Typing a letter into a grams field and pressing Save with no visible block, or the total/figures silently reverting to the old value after save with no sentence explaining why.

### Pitfall 6: The pen's `tabIndex={-1}` skip for the six rules only fires in `'recording'` mode today, not `'developing'`

**What goes wrong:** `FormulationNote.jsx:16` — `const tabIndex = mode === 'recording' ? -1 : undefined;` — only removes the rules from the tab path while the *batch* pen is open. The *plan's* pen (`mode === 'developing'`) leaves the rules in the tab path, which is the critique's second named build-gap item and directly contradicts route-recipe-version.md § 6 ("The six graduated rules leave the tab path while the pen is open, as they do while recording a batch").

**Why it happens:** Phase 2 built the batch-pen exclusion; Phase 3 never revisited this one-line condition when it added the plan's pen.

**How to avoid:** `mode === 'recording' || mode === 'developing' ? -1 : undefined` — a one-line fix, already verified as the complete scope of this gap by reading `FormulationNote.jsx` and `GraduatedRule.jsx` (the rules stay clickable and keep the focus treatment regardless of `tabIndex`, per the brief, which the existing `tabIndex` prop already satisfies since it is passed straight through to the native `<button>`).

**Warning signs:** Tabbing through the pen with the plan's pen open (not the batch pen) still lands on a graduated rule between the ingredient table and the margin.
