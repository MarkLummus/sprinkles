<objective>
Close the one gap Phase 03.2's verification found: the As-made column's joined reading breaks the moment a maker records one portion of a split row and leaves the other at plan.

`formatAsMadeReading` maps each portion to its written value or the empty string and then joins the lot with `' + '` — so a two-portion row with the second portion blank reads `120 +  g`, a dangling plus and a doubled space, both on screen and in the row's accessible name. The pen's `changedGrams` joins the draft's raw typed strings the same unfiltered way, so a screen reader announces the same artifact mid-edit. Leaving a portion blank is the app's own documented way of saying "matched the plan" (D-10) — the ordinary case, not an edge one.

Purpose: this is the screen whose whole job is "get back a record of what happened". The very next batch recorded with one portion left at plan hits this immediately.

Output: both join sites read coherently for any recording pattern, and the test that was supposed to catch this asserts the full rendered string instead of a substring, so the class of regression cannot pass green again.
</objective>

- In the **As-made column**, a blank portion means *the maker wrote nothing here*, and the plan's own amount must never appear in that column (a standing prohibition from 03.2-04). So the reading **drops** the unwritten portion.
- In the **pen**, a blank portion field means *keep this portion's own amount* — that is already the rule `currentGramsValue`, `draftVersion` and `handleSaveBatch` all apply (`parseGramsDraft(...) ?? portion.grams`). So the announced value **substitutes** that portion's stored amount, which is exactly the number that would be saved. Because the two sites put different things into the list, a shared helper would carry one filtering rule for two different meanings, and its second caller would be doing something the helper's name could not honestly describe.
