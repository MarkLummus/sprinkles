# Phase 03.2 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

Register authored at plan time (all five PLAN.md files carried a `<threat_model>`), so the
audit verified the declared mitigations rather than building a register retroactively.
Sprinkles makes no network call and no external model call (TRUST-01), and has no server
surface, so the real attack surface is three things: a hand-edited or corrupted import file
crossing `validateStoreFile`, maker-authored prose reaching a render site, and the IndexedDB
upgrade path.

---

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| Import file → `validateStoreFile` / `validateBatch` | A `.json` store file, possibly hand-edited or corrupted, becoming stored versions and batches | Untrusted object graph: schema version, row shapes, `portions` arrays, `churn.asMade` arrays, `declaredAxes` |
| Stored/imported prose → render sites | Version notes, headnotes, method text, tasting words rendered into the page | Maker-authored (or externally-authored, for an import) free text |
| Pen keystrokes → stored amounts | Raw typed grams strings becoming persisted numbers | Free text crossing into numeric domain state |
| Pen keystrokes → `aria-label` | Draft portion strings joined into an accessibility attribute mid-edit | Free text crossing into an attribute value |
| A returning profile's IndexedDB → `upgrade` | `DB_VERSION` bump drops and recreates both object stores | Previously stored versions and batches (discarded) |

## Warnings

Non-blocking observations from the 2026-09-10 audit. None changes a threat's status; each is recorded so a future auditor is not misled.

| ID | Observation |
|----|-------------|
| W-01 | **Process gap.** None of the five SUMMARY.md files carries a `## Threat Flags` section, so no new attack surface was declared from the implementation side. Audit coverage came from the plan-time register plus independent probing; the register's completeness is unattested by the executors. |
| W-02 | **False premise in T-03.2-04's mitigation text.** "`rowGrams` is the single reader of the field across the whole codebase" is untrue — `row.portions` is read in `RecipePage.jsx` (7 sites), `IngredientTable.jsx` (12 sites), `batch.js:198`, `diff.js:45`, `lineage.js:169`, `transfer.js:72-76`. The threat is closed on its substantive clause (entry-point gating), not on this sentence. A future auditor must not skip the other readers on its strength. |
| W-03 | **T-03.2-14 closes on a cross-file invariant, not a local guard.** `IngredientTable.jsx:659` still calls the baseline-falling-back `resolveStepNumber`; it is safe only because `RecipePage.jsx:550,578` guarantee `baselineStepNumbers` is null whenever that branch renders. One production call site today. A future caller passing a non-null baseline map without `showingChanges` would render a removed step's parent-era number as though live. |
| W-04 | **IN-01 (whitespace-only grams draft) assessed, no security consequence.** Blocked at `lineage.js:170-175`; even if bypassed, `RecipePage.jsx:520/1065` resolve to the portion's previous amount — never `NaN`, never `0`. A UX wording inconsistency only. Agrees with the 2026-09-10 downgrade to informational. |
