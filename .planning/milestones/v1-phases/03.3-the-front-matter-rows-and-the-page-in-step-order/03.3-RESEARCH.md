# Phase 03.3: The front-matter rows and the page in step order - Research

**Researched:** 2026-09-10
**Domain:** React/JSX front-end restructuring of an existing, working page (`app/src/ui/RecipePage.jsx` and its children) plus CSS grid rework in `app/src/styles/app.css`/`tokens.css`. No new library, no new domain capability, no store schema change.
**Confidence:** HIGH for "what exists now" (every claim below is read directly from the files this session). MEDIUM for "exactly how the target maps onto components" (the sketch and its README describe the *visual* target; component boundaries are this research's own inference, flagged `[ASSUMED]` where so).

## Summary

Phase 03.3 has no new domain math and installs no package — it is a structural re-layout of `RecipePage.jsx` and five of its children (`Versions.jsx`, `BatchMargin.jsx`, `Method.jsx`, `IngredientTable.jsx`, `Authored.jsx`) plus a label-vocabulary pass across the same files and `domain/figures.js`. The current page already has the *right ingredients* in the *wrong shape*: `Versions.jsx` today conflates "acts on the plan" (Develop, Show changes) and "acts on a batch" (Record another, Amend, Add tasting) into one region; `BatchMargin.jsx` renders a batch's read/record content inside column two ("Notes"), not in the front matter; the ingredient table renders one `<tr>` per ingredient in authored order with a visible Step column, never grouped by step. Phase 03.2 (complete) already changed the underlying row shape to `portions: [{step, grams}]` and taught `IngredientTable`/`Method` to read it — but *rendering* rows grouped by step, with the Step column removed and a split-ingredient's per-step sub-line, is entirely unbuilt; no test file references it.

The three "03.1 Gap" overrides this phase inherits are concrete, located defects/gaps, not design unknowns: Gap 1 (`Method.jsx`'s pen renders 32 bordered buttons/form fields per step — needs to become read-only prose with one `edit this step` text control), Gap 2 (three prose fields in `BatchMargin.jsx` — `drawNotes`, `ingredientNotes`, `nextTimeNote` — render with no visible label, `border: 0`, and are invisible until focused; the fix is a hairline baseline rule with no label word), and Gap 3 + WR-01 (focus-return effects in `Versions.jsx` and `IngredientTable.jsx` are keyed on value-equal-but-referentially-new dependencies, so a *second* blocked Save in a row leaves focus stranded — the fix is keying the effect on an attempt counter, not the blocked target's identity).

The thirteen settled labels are recorded verbatim in `product-requirements/05-domain-and-language.md` (added by commit `5345f5b`, 2026-09-09 13:31) — quoted in full below. None of the renamed labels have shipped to `app/src/ui/*.jsx` or `app/src/domain/figures.js`; the settled labels also change `figures.js`'s figure labels from a plain string (`'Total fat'`) to a two-part "plain word, technical term in small print" form (`Fat`/`Freezing · PAC`), which is a bigger change than a string swap — `GraduatedRule.jsx` currently renders `figure.label` as a single text node.

**Primary recommendation:** Treat this phase as five separable but sequenced changes: (1) split `Versions.jsx` into a version-row region and a batch-row region, folding `BatchMargin.jsx`'s content into the batch row and deleting `BatchMargin.jsx` as a component (its logic — tasting reading/form — can move into the new batch-row module); (2) rework `.recipe-band`'s CSS grid from one row of two side-by-side blocks into two full-width stacked rows, each with its own internal grid; (3) rebuild `IngredientTable.jsx`'s row rendering to group by step with a step-lead-in head row and a per-portion sub-line, dropping the Step column; (4) rewrite `Method.jsx`'s pen branch (`StepPenBody`) from a form of per-field inputs to read-only prose plus one `edit this step` text control per step; (5) apply the settled label vocabulary across every touched file plus `figures.js`. Do the label pass last, file by file, since it touches every other component this phase already modifies.

## Layout Mechanism (CSS)

**Grid structure today** (`app/src/styles/app.css:229-239`, read this session):

```css
.recipe-page {
  display: grid;
  grid-template-columns: 2fr 1fr;
  grid-template-areas:
    'band band'
    'ingredients side'
    'method side'
    'foot foot';
  gap: var(--gap-l);
  padding: var(--gap-xl);
}
```

The front matter (`.recipe-band`, grid-area `band`) **already spans both columns** (`'band band'`) — variant B's "front matter spans the whole page" requirement is already satisfied at the outer-grid level; what needs to change is `.recipe-band`'s OWN internal grid, which today is a single row split into `minmax(0, var(--measure-prose)) 1fr` (`app.css:246-252`, holding `Headnote` | `Versions` side by side). The target is two STACKED rows, each spanning the band's own full width, each with its own internal sub-layout (version row: name/prose left + metadata/acts right, at the `measure-prose`/`1fr` split roughly matching today's; batch row: a single flowing block with a `cells` grid for measured values, per the sketch's `.row-batch .cells { grid-template-columns: repeat(auto-fit, minmax(96px, max-content)) }`).

Column two (`side`, `.side-region`) is unaffected by the row-count change — `.recipe-page`'s outer grid areas (`'ingredients side'`, `'method side'`) stay the same; only what renders *inside* `.side-region` changes order (per the Move Map above).

**Existing tokens usable as-is** (`tokens.css`, read this session): `--gap-l` (32px), `--gap-m` (20px), `--gap-s` (12px), `--gap-xs` (6px), `--rule-baseline` (1.5px), `--rule-graduation` (1px), `--measure-prose` (65ch), `--size-figure-value` (1.25rem, matches the sketch's `.cell .v` figure-sized measured values), `--size-small-print` (0.75rem, matches the sketch's `.cell .k` labels). No new token category is obviously required for the row layout itself, though a `.text-control` treatment (underline, no border) needs new rules in `app.css` alongside the existing `button, select` binder block — this is additive CSS, not a new token axis.

**Ingredient-table column tokens** (`tokens.css`, read this session): `--col-numeric` (94px), `--col-step` (78px), `--col-data` (86px), `--col-remove` (78px), `--col-step-pen` (160px). Once the Step `<th>`/`<td>` is deleted, `--col-step` and `--col-step-pen` become dead tokens (their consuming CSS selectors — `table.step-order col.c-step { width: 0 }` in the sketch, or the equivalent `.ingredient-table__col-step` rule in `app.css` — should be removed, not left orphaned; `columns.test.js`, 300 lines, almost certainly asserts against `--col-step`/`--col-step-pen` today and will need updating).

**Sub-1280px stack is explicitly OUT of scope** (ROADMAP phase notes, confirmed twice): "The sub-1280 stack remains Phase 4's (UX1-01)." This means: the planner should NOT add a `@media`/`@container` breakpoint that stacks the two-column body (`ingredients`/`side`) below 1280px, and should NOT worry about the front-matter row's own internal 2-up layout collapsing to 1-up below ~760px (the sketch's own `@container (max-width: 760px)` rule) as a phase requirement — though nothing prevents building it opportunistically if it falls out of the row CSS "for free." The phase's own done-when criteria should be checked at ≥1280px only.

## The Table's Step Grouping

Phase 03.2 landed: `portions: [{step, grams}]` on every row (`rowGrams(row)` sums them, `domain/rows.js:34-36`), the derived total, and — per `IngredientTable.jsx`'s existing `GramsCell`/`StepCell`/`AsMadeCell` — per-portion editing fields *inside one row per ingredient*. `domain/stepNumbers.js` already provides `displayNumbers(method)` (a step's stored key `n` → its 1-based display position among non-removed steps) and `displayNumberOf(map, n)` — these are exactly what a step-head row needs to print "Step 3" correctly under removal/renumbering, and `RecipePage.jsx` already computes `currentStepNumbers`/`baselineStepNumbers` once and threads them to both `Method` and `IngredientTable` (lines 577-578, 1198-1199, 1225-1226) — no new domain module is needed for step ordering itself.

**What remains, confirmed unbuilt** (no test references either):
1. Grouping rows/portions by step number for rendering — iterate the set of distinct `step` values present across all rows' `portions` (in step-number order via `currentStepNumbers`), emit a step-head `<tr>` naming that step's lead-in text (`step.leadIn`, already on the `Method` step objects) before that group's portion rows.
2. Removing the Step `<th>`/`<td>` (`ingredient-table__col-step`, `StepCell`, `formatStepReferences`, `formatDiffSteps` — all now redundant once the step is expressed by group membership rather than a cell) — note `formatDiffSteps`/`StepCell` are also used by the **show-changes** state (`isShowingChanges` branch) and the **pen** (`isDeveloping` branch); the step-grouping rework needs a plan for all three render branches (reading / developing / show-changes), not just the reading state the sketch shows.
3. The split-ingredient sub-line: `"120 g of 370.4 g · 46.3% in all"`. This is `${portion.grams} g of ${formatGrams(rowGrams(row))} · ${formatShareOfBatch(rowGrams(row), mass)} in all"` — every piece (`rowGrams`, `formatGrams`, `formatShareOfBatch`) already exists in `domain/composition.js` (`Read` confirmed: `formatShareOfBatch(grams, mass)` at line 80, `formatGrams(grams)` at line 106). **Recommendation**: add one new pure formatter to `domain/composition.js` (e.g. `formatPortionLine(portionGrams, rowTotalGrams, mass)`) that composes these three into the sentence, tested in `composition.test.js`, so the string assembly is not duplicated inline in JSX and is unit-testable without rendering — consistent with the project's existing pattern (every other display-string builder — `formatShareOfBatch`, `formatGrams`, `formatGramsValue` — lives in `domain/composition.js`, not in a component).

**Open tension the planner must resolve or explicitly defer** (see Open Questions): the sketch README's own "Still open for shape" section lists *"Whether the written order survives on screen once step order is the sheet's order"* as unresolved, while the ROADMAP's phase goal states flatly "the ingredient table reads in step order" with no mention of a toggle. The sketch's own UI has a "Table as written" / "Table in step order" toggle as a **sketch-navigation device**, not necessarily a shipped feature — nothing in the scope bullets mentions a toggle control. Treat step order as the table's *only* rendering order for this phase unless CONTEXT/discuss-phase settles otherwise; do not build a toggle speculatively (CLAUDE.md's "no features beyond what was asked").

## The Pen's Read-Only Method

Today's `StepPenBody` (`Method.jsx:80-327`) already has the underlying on-demand mechanism this phase needs generalized: `useOnDemandField` (lines 49-72) is a reusable open/collapse-on-blur hook already used for `purpose`/`aside` (and for the batch pen's "done differently" line, `StepRecordingControls`). The read-only-with-`edit this step` requirement is the SAME pattern applied at the whole-step level instead of the per-field level: render the step's prose/targets/purpose/aside as plain text (like the **show-changes** branch already does, `Method.jsx:551-618` — this branch is nearly a template for the read-only pen render, since it already prints struck-beneath diffs without input fields), then one `edit this step` `text-control` per step that reveals the current `StepPenBody` fields. **Recommendation**: reuse the show-changes branch's read-only JSX shape as the pen's *default* per-step render, gated by a new per-step `useState` (mirroring `usesOpen`'s pattern), with `StepPenBody`'s current fields becoming the *revealed* state.

**Existing focus-return behavior and WR-01, located precisely** (code-review-confirmed, `Read` this session):
- `Versions.jsx:126-128` — `versionLineFieldRef.current?.focus()` inside `useEffect(() => {...}, [versionLineBlocked])`. `versionLineBlocked` is `blockedTarget?.kind === 'versionLine'` (a derived boolean recomputed fresh by `RecipePage.jsx` on every blocked save via `setBlockedTarget`) — a second consecutive block on the same field produces a new boolean that is *value-equal* to the old one, so React's dependency comparison sees no change and the effect does not re-fire. Confirmed exact fix direction from the code review: key the effect off an incrementing attempt counter instead.
- `IngredientTable.jsx:518-521` — identical shape: `useEffect(() => { if (!blockedRowId) return; gramsInputsRef.current.get(blockedRowId)?.focus(); }, [blockedRowId])`. Same fix needed.
- Fork's landing focus: `Versions.jsx:282-289`, `autoFocus={focusDevelopOnMount}` on the `Develop` button, wired from `RecipePage.jsx:1097` (`navigate(child.id, { state: { focusDevelop: true } })`) and `RecipePage.jsx:250` (`location.state?.focusDevelop`). Code-review-confirmed correct by reasoning; the phase's own `03.1-05-SUMMARY.md` hand-check records it as **tried live and failing** ("focus after Save lands on `<body>`, still open"). The only test coverage is `Versions.test.jsx:149-155`, which asserts the `autofocus=""` HTML attribute is present in jsdom-rendered markup — this does NOT prove a real browser moves DOM focus there (jsdom's `autoFocus` handling and a real browser's are not the same guarantee). This phase's scope line "Confirm... the fork's landing focus" should be read as: verify live in a real browser, not just re-assert the jsdom test.

## Common Pitfalls

### Pitfall 1: Treating the Step-column removal as a delete-only change
**What goes wrong:** `StepCell`, `formatStepReferences`, `formatDiffSteps`, and the `ingredient-table__col-step`/`ingredient-table__col-step-pen` CSS/tokens are read by THREE render branches (reading, developing, show-changes) in `IngredientTable.jsx`, not one. Deleting the Step `<td>` from only the reading branch while step-selection UI still lives in the pen branch (`StepCell`'s `<select>`) would leave the step choice with no visible home while developing.
**Why it happens:** The sketch only shows the reading state's step-order table; the pen's own step-allocation UI (choosing which step a row/portion belongs to) is not depicted in the sketch's step-order mode at all.
**How to avoid:** Explicitly design where step *choice* (the `<select>`) lives once the Step column is gone — likely inside each step-group as a per-portion control, or unchanged as an inline `<select>` beside the portion's grams field within its step group. Flag this as a design gap for CONTEXT/discuss-phase if the sketch doesn't resolve it (the README's own "Still open for shape" list includes "Editing a split ingredient in the pen: portions edited, total derived; not sketched" — confirming this is a genuine, acknowledged gap in the design evidence, not something research missed).
**Warning signs:** A plan that only touches the reading-state render function without touching `StepCell`/`isDeveloping`/`isShowingChanges` branches.

### Pitfall 2: Splitting `Versions.jsx` without carrying its focus-management refs correctly
**What goes wrong:** `Versions.jsx` currently owns FOUR `useRef`+`useEffect` focus-return pairs (develop, record, amend, tasting — lines 69-119) plus the blocked-save-focus effect (lines 125-128). If the component is split into a version-row module and a batch-row module, each ref pair must move to the component that owns the CORRESPONDING opener button, or focus-return breaks silently (a `ref` object cannot span two separate function components).
**Why it happens:** The refactor is not simply "extract two `<div>`s" — it's extracting stateful hooks whose closures currently share one `openPen`/`mode` read.
**How to avoid:** Map each of the four ref pairs to its new home explicitly before writing code: `developButtonRef` → version-row module; `recordButtonRef`/`amendButtonRef`/`addTastingButtonRef` → batch-row module.
**Warning signs:** A plan that treats the `Versions.jsx` split as a pure JSX-relocation task without mentioning `useRef`/`useEffect`.

### Pitfall 3: Conflating "no running head" with "no heading at all"
**What goes wrong:** The scope says "No running head on either" for the two front-matter rows. Today's `Versions.jsx` renders `<h2 className="region-name">Versions</h2>` as a `region-name`-styled running head, and `BatchMargin.jsx`'s callers render `<h2 className="region-name">Notes</h2>` around it. The sketch, however, DOES show smaller in-row headings (`<h2 class="region-name">Version</h2>` inside `.vmeta`, `<h2 class="region-name">Batch</h2>` inside `.head`) — these read as sub-labels for the metadata/acts cell, not page-level running heads for the whole row.
**Why it happens:** "Running head" is this project's specific term for the uppercase, `--bookcloth`-coloured, page-orienting label (see Phase 03.1's decision: "Running heads renamed: Ingredient table -> Ingredients, Formulation note -> Balance, Margin -> Notes"). The sketch's `.region-name` class is reused for BOTH the page-level running heads AND these smaller in-row labels, which could read as contradictory to "no running head."
**How to avoid:** Read the scope bullet as "these two rows carry no `region-name`-styled section head naming the row itself (no 'Versions'/'Batch' page-level label)" while the sketch's smaller `Version`/`Batch` sub-labels inside the metadata cell may still be warranted — but this is this research's own interpretation `[ASSUMED]`, not confirmed by any binding source read this session. Flag for discuss-phase/CONTEXT if ambiguous.
**Warning signs:** A plan that either (a) removes ALL headings from both rows including the sketch's own `Version`/`Batch` sub-labels, or (b) keeps the current page-level "Versions" `<h2 className="region-name">` unchanged, without acknowledging the tension.

### Pitfall 4: `activeRows`/`activeSteps` filtering discipline extends to the new step-group renderer
**What goes wrong:** `domain/rows.js`'s own header comment states this is "the one seam that keeps a removed row or step out of computeBalance, buildFigures, the totals, and the clean reading" — a removed row/step reaching a balance computation "would silently corrupt every figure with no error." A hand-rolled step-grouping loop that iterates `version.rows`/`version.method` directly (rather than through `activeRows`/`activeSteps` for the reading state) risks re-introducing a removed row/step into the grouped view.
**Why it happens:** The step-grouping rewrite is new code in a file (`IngredientTable.jsx`) that already has an explicit lint-style project rule against this exact mistake: "Never `.filter(` [on 'removed']... the automated gate on this file forbids a filter whose arguments mention `removed`" (comment at `IngredientTable.jsx:368-370`) — meaning the project already treats this class of bug as serious enough to gate.
**How to avoid:** Reuse `activeRows(version)`/`activeSteps(version)` (already imported in `IngredientTable.jsx`) for the reading-state grouping; keep the unfiltered `version.rows`/`version.method` only for the pen's own struck-in-place rendering, exactly as today's code already distinguishes `rows` (baseline) from `draftVersion`/`activeRowsOnly`.
**Warning signs:** A new step-grouping helper that takes `version.rows` directly and filters ad hoc, rather than delegating to the existing `activeRows`/`activeSteps` functions.
