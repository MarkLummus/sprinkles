**Reviewed:** 2026-09-15T00:00:00Z
**Depth:** standard

## Summary

Reviewed the record pen's CSS contract (`app.css`/`tokens.css` plus the three
`styles/*.test.js` suites that pin them), the battery components
(`AxisMark`, `Segmented`, `BatchRow`, `PenFoot`), `VersionRow`, `RecipePage`,
and the phase's own browser conformance probe script, at standard depth. The
full existing test suite for these files (226 tests across
`BatchRow.test.jsx`, `Segmented.test.jsx`, and the three `styles/*.test.js`
suites) passes; the CSS contract suites are thorough and internally
consistent with `app.css`/`tokens.css` as written. The token discipline (no
hex, no bare px, `--focus-outline-width` weight ordering, the `759.98px`
breakpoint prelude convention) all check out under `binder.test.js` and
`cross-cutting.test.js`.

Two real defects survived that discipline because both live at a boundary
the text-only CSS suites cannot see: a CSS class name that doesn't match any
rule (so a styled `<p>` renders as an unstyled one, and the JSX test that
covers it pins the wrong class rather than catching the mismatch), and a JS
`matchMedia` query whose breakpoint literal disagrees with the CSS
breakpoint literal used everywhere else in this exact feature — the same
class of bug the phase's own late fix `99d89c3` corrected for the axis-mark
track geometry, left unaddressed one hook away in the same file. A smaller
accessibility-pattern inconsistency in `Segmented.jsx` rounds out the
findings.

## Critical Issues

### CR-01: `useBelow760`'s matchMedia breakpoint (760px) disagrees with every CSS layout breakpoint in the same feature (759.98px)

**File:** `app/src/ui/BatchRow.jsx:114-125`
**Issue:** `useBelow760` decides, via a **real DOM swap** (`AxesGrid`'s
`below` prop — not a CSS media query), whether the axes/defects grid renders
its desktop row-major markup or its stacked mobile markup:

```js
const [below, setBelow] = useState(() => (hasMatchMedia ? window.matchMedia('(max-width: 760px)').matches : false));
useEffect(() => {
  if (!hasMatchMedia) return undefined;
  const mediaQuery = window.matchMedia('(max-width: 760px)');
  ...
```

Every corresponding CSS rule that must agree with this DOM shape — the
touch-stop track width (`.axis-mark__stops, .axis-mark__anchors { width:
var(--track-stop-narrow) }`), the stop box's own touch dimensions
(`.axis-mark__stop { width/height: var(--touch-stop-width/height) }`), and
the version row's own column collapse (`.recipe-band__row-version`) — reads
`@media (max-width: 759.98px)`, not `760px`. `app.css` documents this
`.98px` fraction explicitly and repeatedly as deliberate: "the fractional
value keeps exactly 760px on the desktop side of the boundary" (app.css
lines ~2156, ~2197-2201). `tokens.css` and every in-file comment name
"below the 760px step-down" as shorthand for the same `759.98px` rule.

At a viewport of exactly 760px: `window.matchMedia('(max-width: 760px)')`
matches (760 ≤ 760 is true) so React renders the **stacked** DOM
(`.axes-grid.axes-grid--stacked`, core-then-declared, no `.axes-rule`
hairline), but `@media (max-width: 759.98px)` does **not** match (760 >
759.98) so the stop boxes and tracks keep their **desktop** 186px/38px
geometry inside that stacked layout — a hybrid state (stacked arrangement,
desktop-sized stops) this codebase's own commit history shows it cares about
down to fractional pixels: `99d89c3` in this same phase fixed the mirror-image
bug ("the axis track geometry stays width-keyed — a 216px track overflowed
the 213px column on a wide touch screen") for this exact stop-track pair.
This hook was never updated to the `.98px` convention when it was
established elsewhere in the file (`fd6593b`, pre-dating this phase), and
this phase's own five late CSS fixes did not catch it because none of them
touch `BatchRow.jsx`'s JS.

**Fix:**
```js
const mediaQuery = window.matchMedia('(max-width: 759.98px)');
```
Apply the same string in both the initial `useState` read and the `useEffect`
listener, matching every other breakpoint literal in the file.

### CR-02: `.batch-row__dates` has no matching CSS rule — the tasted-date line renders unstyled

**File:** `app/src/ui/BatchRow.jsx:218`
**Issue:** `TastingReading`'s own "tasted {date}" line reads:

```jsx
<p className="batch-row__dates">
  {`tasted ${batch.tasting.tastedDate ? formatRecordDate(batch.tasting.tastedDate) : 'date unknown'}`}
</p>
```

`app.css` has no `.batch-row__dates` rule (confirmed by grep across
`app.css`). It does have a near-identical, styled sibling one character
shorter — `.batch-row__date` (singular), used for the churned-date span on
the batch head line (`BatchRow.jsx:416`), reading `font-family:
var(--face-text)`, `font-size: var(--size-version-line)`, `color:
var(--pen-blue)`. The tasted-date paragraph is the read view's direct
analogue of that churned-date span — same kind of fact (a recorded date),
same "pen" register — but because the class name doesn't match any rule it
falls through to the page body defaults (`--face-grotesk`, `--size-table-body`,
`--ink`) instead of the pen-blue text-face treatment the rest of the
pen/read-view date fields carry. This is a sketch-conformance regression:
the rendered date line does not match the register every other recorded
date in this same component uses.

`BatchRow.test.jsx:1062` and `:1068` assert the broken markup verbatim
(`'<p class="batch-row__dates">tasted date unknown</p>'`), so the test suite
pins the typo rather than catching it — these two assertions need updating
alongside the fix.

**Fix:**
```jsx
<p className="batch-row__date">
```
and update `BatchRow.test.jsx:1062,1068` to assert `batch-row__date`
(singular) to match.

## Warnings

### WR-01: `Segmented`'s radiogroup never uses the caption id it generates — inconsistent with `AxisMark`'s own established pattern

**File:** `app/src/ui/Segmented.jsx:25,37,51`
**Issue:** `Segmented` computes a `captionId` and assigns it as the caption
span's `id`:

```js
const captionId = `${groupName}-caption`;
...
<span className="segmented-field__caption pen-caption" id={captionId}>{groupLabel}</span>
...
<div className="segmented" role="radiogroup" aria-label={groupLabel}>
```

but the radiogroup never references `captionId` via `aria-labelledby` — it
duplicates the same text as a literal `aria-label` instead, making
`captionId` (and the `id` it writes to the DOM) dead: nothing else in the
component, or in any consumer, ever reads it. This is the opposite of the
sibling component this file's own header comment says it mirrors —
`AxisMark.jsx` wires its equivalent `nameId` through `aria-labelledby={nameId}`
on the stops group (`AxisMark.jsx:64-65,82-83`) rather than duplicating the
name as a second literal string. The functional accessible name is
unaffected (the `aria-label` already supplies it), but the dead id and the
inconsistency between two components built to share one pattern is a real
maintenance trap: a future edit to `groupLabel`'s wording only needs to
change in one place under `AxisMark`'s pattern, but two under `Segmented`'s.

**Fix:** Either drop `captionId`/the `id` attribute (if `aria-label` is the
deliberate choice), or wire it through properly to match `AxisMark`:
```jsx
<div className="segmented" role="radiogroup" aria-labelledby={captionId}>
```
and drop the redundant `aria-label={groupLabel}`.

### WR-02: `useBelow760`'s comment states the wrong breakpoint

**File:** `app/src/ui/BatchRow.jsx:106`
**Issue:** The header comment for `useBelow760` reads "a matchMedia listener
on (max-width: 760px)" — this documents the same wrong literal CR-01 flags
in the code itself, so a future reader has no comment-level signal that the
value disagrees with the rest of the file's `759.98px` convention. Once
CR-01 is fixed this comment should be fixed with it (`(max-width: 759.98px)`),
otherwise the discrepancy this review found can recur silently.
**Fix:** Update the comment alongside CR-01's code fix.
