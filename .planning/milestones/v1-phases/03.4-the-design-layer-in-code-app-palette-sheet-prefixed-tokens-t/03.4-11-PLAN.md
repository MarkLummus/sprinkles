<decisions_recorded>
1. **The disclosure stays a `<details>`; only its open state moves into React.** The element already has the keyboard operability and the summary semantics 03.4-03 chose it for, and shell.css draws the open panel through `.shell__more[open] > ul`. Replacing it with a hand-rolled menu would throw that away to solve a dismissal problem. So: `open` becomes a prop, `onToggle` keeps React and the DOM in step when the maker toggles from the summary itself, and the panel closes from code for the first time. This is History.jsx's HistoryDisclosure pattern — a disclosure whose open state is the component's — applied to the element this surface already uses.
2. **One click handler on the list, not five.** A click on the `<ul>` covers all five items and both activation paths (a pointer tap, and Enter or Space on a link or button, which fire a click). Wiring five handlers would be five chances to miss one.
3. **Focus returns to the summary for every item, not only Import and Export.** The UAT asks for it after Import and Export, but the same problem exists for the three navigation items: the element that had focus is inside the panel that just closed, so focus would fall to the document body and the tab order would be lost. One handler, one behaviour.
4. **Half B is out of scope.** Mark deferred it on 2026-09-22. Import was never specified to navigate — 03.4-03-PLAN.md:149 says the revision counter exists "so a route below can reload its own data" and adds "do not reach into any route's state". The real defect underneath it (a successful import from a non-Home route changes nothing on screen, and a failed one is equally silent because the error list sits off-screen in the header) is recorded in 03.4-UAT.md's Deferred Follow-Ups and stays there.
5. **The pin is a source-text assertion, deliberately.** Shell.test.jsx is `renderToStaticMarkup` in Vitest's node environment: it cannot click, toggle a `<details>`, navigate or run an effect, and 1119 tests passed on the defective tree. Reading Shell.jsx as text is the same technique home.test.js already uses for RecipeList.jsx, and it is what this project's harness can honestly assert. A real DOM-level interaction test needs jsdom or testing-library — a structural choice, surfaced rather than taken.
</decisions_recorded>
