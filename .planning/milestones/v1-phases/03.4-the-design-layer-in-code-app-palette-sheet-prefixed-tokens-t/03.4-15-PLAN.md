<objective>
Close G-03.4-r4-1. On Mark's iPad, Tab rings the nine shell stops and then focus leaves the page, because every control on Home is a react-router Link rendering `<a href>` with no tabindex. WebKit admits such a link to the Tab order only under the embedder's TabsToLinks preference (off on Apple platforms, with no iPadOS switch, and untouched by Full Keyboard Access) or when the link carries an explicit tabindex. With nothing reachable after Kitchen, WebCore hands focus to Safari. 03.4-14 fixed the shell's stops only; the device has now confirmed that fix. This plan applies the same remedy to every link the app renders, per Mark's ruling of 2026-09-22 ("every app link"), and records it as a project rule.

The report also contains a second fault, S2: the keyboard stayed dead until a power cycle. It reproduced in UAT test 2 with focus never entering the page. The app runs no key, focus, timer or observer code on Home and cannot cause it, so this plan makes **no code change for S2**. It carries the on-device steps that locate the fault, recorded and never asserted.

Purpose: UX1-01. The maker's own device must be able to reach every link by keyboard on every route, not only the shell.
Output: an explicit tabindex on seventeen Link sites, pinned on rendered markup per component (source text for the two sites the node harness cannot render); one convention line in `.claude/CLAUDE.md`; and a UAT truth whose tap position no longer decides the result, with S2 split out as a recorded procedure.
</objective>

<decisions_recorded>
1. **Every app link, not Home only.** Mark ruled on 2026-09-22 that every `<a>` the app renders carries an explicit tabindex of 0, closing the gap on every route in one plan. A grep at planning time found seventeen sites outside the shell, all react-router `Link`: RecipeList.jsx 9 (lines 63, 67, 110, 170, 180, 183, 192, 195, 229), RecipeHistory.jsx 3 (81, 125, 137), VersionRow.jsx 2 (225, 248), BatchRow.jsx 1 (347), RecipePage.jsx 1 (848), router.jsx 1 (63). No raw `<a>` appears in any JSX file, in `app/index.html` or in `main.jsx`. Shell.jsx's `document.createElement('a')` (line 178) is the Export download: it is appended, clicked and removed in one call, never in the focus order, and is out of scope.
2. **Per-component rendered markup, not an app-wide route render.** Per-component is the smaller mechanism, for three reasons. (a) router.jsx cannot be imported under this suite's node environment: `createBrowserRouter` runs at module scope and needs `document`, as RecipePage.test.jsx:737-743 already records. (b) Every route loads its data in an effect, and `renderToStaticMarkup` never runs effects. A route-level render of `/` shows only "Loading your recipes…", and one of `/recipe/:id` shows nothing, because RecipePage returns null while its version is undefined. That is zero of the seventeen links. (c) Making a route render see them would need jsdom, a stubbed or fake IndexedDB store and async flushing. That is a new test harness, a structural testing choice that the working agreement says to surface rather than take inside a gap fix. Each affected test file's existing render helper and fixtures already produce every link branch, so each file needs one test. Every test asserts an exact link count so it cannot pass on zero links.
3. **Source text only where the harness cannot render.** router.jsx's running head and RecipePage.jsx's not-found link (reached only after an effect sets the version to null) are pinned on source text. This follows RecipePage.test.jsx's existing running-head ownership block, which reads the same two files the same way. 03.4-14's caution was that a source regex could pass with the attribute on the wrong element. That is met by matching the whole `Link` opening tag and requiring exactly one per file: each of the two files holds one single-line `Link`.
4. **A source scan over every .jsx for future links was considered and not taken.** It would catch a missed link in a component that does not exist yet. But Mark ruled for rendered markup per component, and this project carries its other standing rules (the idb seam, no `dangerouslySetInnerHTML`) through the conventions line alone, with no scan. It is offered to Mark as a follow-up, not built.
5. **The attribute goes last in each opening tag, on that tag's one line.** react-router's `Link` spreads its rest props ahead of `href` (lib.js:317-324). The rendered tag therefore reads `<a [class="..."] tabindex="0" href="..." ...>`. Two existing RecipeHistory.test.jsx literals (lines 122 and 217) pin the cited-batch anchor's opening text with `href` directly after the tag name, and they are updated to the new rendered text. They are the only existing assertions this plan changes. A sweep at planning found no other test that pins an attribute directly before `href` on an anchor, or asserts tabindex absent where a link renders.
6. **The ring needs no CSS.** Home's and the recipe page's links use app.css's one `:focus-visible` rule (line 56). The debug session read WebKit's Tab path as focusing with FocusVisibility::Visible, so `:focus-visible` matches. So far that has only been seen on the shell, which also has a `:focus` fallback. If on the iPad focus visibly moves (Space opens the link) but no ring paints, that is a new, separate finding for the record, not a reason to add a fallback here.
7. **S2 is environmental and gets no code change.** On Home the page runs no key handler, focus call, timer, animation loop or observer. Under Full Keyboard Access no keydown ever reaches it, and the lock-up reproduced with focus never in the page. A sandboxed page has no way to disable the device's keyboard. Three candidates remain below the page: A, Safari's focus parked on a view that draws no highlight; B, the Full Keyboard Access service stalling; C, the iPadOS keyboard transport. The verification section's on-device steps tell them apart. An executor who finds themselves writing a key handler, focus guard or blur listener for this has left the plan.
8. **The UAT truth is reworded and split in this plan's verification section, as 03.4-14 did.** The tap moves beside the wordmark. (a) Home and (a2) a recipe page are asserted on the iPad. (b), S2, is recorded, never asserted. 03.4-UAT.md belongs to the verifier and is updated on reconciliation, not here.
9. **One plan, three tasks, at most five files each.** Twelve files are touched, but every change is one attribute or one test. The tasks are cut by where each component's test lives: Home plus the convention (the tracer, since Home is the route that failed on the device); the history outline and the version row; the batch register plus the two sites that cannot be rendered.
