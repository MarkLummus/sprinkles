## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `tests/db-reset.test.js` assumed `seedIfEmpty` wrote exactly one version and read it back first**
- **Found during:** Task 2 (GREEN), full-suite regression run
- **Issue:** The integration guard's `seedIfEmpty writes the seed back after the reset...` test destructured `const [seeded] = versions` assuming length 1; once `seedIfEmpty` seeds nine versions across eight recipes, that assumption broke twice over — the array has more than one entry, and `repository.listVersions()` (IndexedDB `getAll`) returns key-sorted order, not seed-write order, so the first entry was `coconut-v1`, not olive oil's version.
- **Fix:** Find the olive-oil version by id (`versions.find((v) => v.id === 'olive-oil-ice-cream-v1')`) instead of assuming array position; assert `versions.length` is `> 1` rather than `=== 1`.
- **Files modified:** `app/tests/db-reset.test.js`
- **Verification:** `npm --prefix app test -- --run` — full suite green (1343/1343).
- **Committed in:** `6d01c7e` (Task 2 GREEN commit)

**2. [Rule 1 - Bug] Coconut, Strawberry and Mocha batches array order silently misrepresented each recipe's "newest" batch on Home**
- **Found during:** Task 3, `seed-coverage.test.js`'s first run — the D-05 standings-coverage assertion failed (`AWAITING_TASTING` absent from the whole seed's Home standings)
- **Issue:** None of Coconut's, Strawberry's, or Mocha's batches carries a `churnDate`. `domain/batch.js`'s `sortedBatches` ties on that missing field and falls back to array order to decide "newest" — but every one of these three recipes had its batches authored oldest-first (matching the `versions:` array's own chronological convention), so `domain/lastEvent.js`'s `standingFor` silently read each recipe's *oldest* (tasted) batch as its newest. Every recipe with any batch therefore read `TASTED` on Home; no seeded recipe could ever read `AWAITING_TASTING`, contradicting the plan's own D-05 must-have.
- **Fix:** Per the task's own instruction ("If an assertion fails, the fault is in the data... never in the assertion"), reordered the three recipes' `batches:` arrays in `seed-recipes.js` to their true newest-first churn order — Coconut `[v2, v1]`, Strawberry `[V2.1, V2, V1]`, Mocha `[v3, v2, v0]`. No batch's own field values changed and no date was invented; Mexican Chocolate is untouched since its v1 batch carries a real `churnDate` and always wins the tie regardless of array order.
- **Files modified:** `app/src/data/seed-recipes.js`; documented as judgement call 58 in `03.5-SEED-REVIEW.md`
- **Verification:** `npm --prefix app test -- --run src/store/seed-coverage.test.js` (8/8 passing, including the standings-coverage assertion) and the full suite (1343/1343).
- **Committed in:** `64c6984` (Task 3 commit)
