<objective>
Make Out of machine and Tasting temperature open on the iPhone's numbers layer, with a minus key, by rendering the two signed degree-C fields as number inputs. Make an entry the browser cannot read a flagged error, never a blank save.

Purpose: UAT round 2, test 2 (G-03.5-R2-2). The two fields opened the ordinary text keyboard on its letters, and -6 cost a hunt for the 123 key. Mark tested a throwaway number-input build on his iPhone on 2026-09-30 and adopted it: the numbers layer opens with a minus and a period, -6 takes two taps, -6 and -12 save and read back, and the other number fields keep the numeric keypad. The change reverses the 03.3.1 rule never to use a number input, for these two fields only, because a browser hands over no text for an entry it cannot read: it reports a blank value, and the draft would save that as blank. The plan carries the browser's own unreadable-entry state into the existing field error.

Task 2 is the tracer, one signed field wired from the input through the draft and the save gate to a read-back. Task 3 expands it to the second field, the blank-return, the wheel, the box and the Correct pen.

<decisions_recorded>
1. **Variant A, as Mark tested it.** The signed fields render `type="number"` with `step="any"` and no `inputMode` attribute (an inputmode wins over the type on WebKit, so the attribute must be absent). `autoCorrect` and `autoCapitalize` are dropped from the signed fields, since they mean nothing on a number input. The unsigned fields stay `type="text"` with `inputMode="decimal"`. This is exactly the throwaway build Mark tested, plus the carry in decision 3 and the guard in decision 4, neither of which can change which keyboard opens.
2. **The authority moves first, line for line.** Contract line 187; sketch 007 line 620 and its mirror in the skill's sources (line 619); sketch 007's previewSave validity test (line 598, mirror 597), because a number input reports an unreadable entry as an empty string and the sketch would read it as blank, which is the defect in sketch form; and sketch 008 lines 354 and 359. Sketch 008 line 358 (Tempering) stays decimal. Sketch 008 line 454 is a history row drawn at the 007 weights and is not the current authority; it is left alone.
3. **The carry: the draft holds a value no parser accepts.** A number input with an unreadable entry reports value "" and `validity.badInput` true. React fires `onChange` only when the node's value string differs from the last one it saw, so a lone minus typed into an empty field fires no `onChange` at all, while the browser's raw `input` event does fire (measured in Chromium: value "", badInput true). So on the signed fields one handler serves both `onChange` and `onInput`, and it writes `MALFORMED_NUMBER_ENTRY` to the draft when `badInput` is true and the input's value otherwise. The input's `value` prop shows "" for that string, because setting a number input's value to text it cannot hold wipes the typed characters from the screen. Both events read the same live node, so the double call writes the same value twice and order does not matter. `parseMeasuredDraft` already rejects any string that is not a signed decimal, so `validateRecordDraft`, the field-error line, aria-invalid, the focus-first-invalid effect, `isDraftDirty` and `tastingHasInk` all behave with no change: a typed-then-abandoned lone minus counts as ink, so Cancel still asks. Rejected: a second badInput state in RecipePage (a new prop through BatchRow's long list and a second source of truth for the dirty check and the save gate); reading the DOM at Save time (the gate is a pure function of the draft); teaching battery.js about the browser (the domain stays framework-free and untouched).
4. **The wheel guard.** Measured at planning: in Chromium a wheel over a focused number input steps its value (5 became 4), so scrolling the page with the pointer over a focused Out of machine would silently turn -6 into -7. The signed fields take an `onWheel` handler that blurs the input, which stops the step and lets the page scroll. Safari and Firefox do not step on wheel, and the iPhone has no wheel, so this guards the desktop only.
5. **Facts checked at planning, not re-derived.** The number spinners are hidden by app.css lines 257 to 264 (D-19) and pinned by binder.test.js. Focus-first-invalid is one `focus()` call (BatchRow.jsx, the effect on `invalidFieldTarget`), and no `setSelectionRange`, `selectionStart` or `select()` appears under app/src outside tests, so a number input's null selection API is never reached. Switching the two inputs to type number in the built app changed neither their width nor their height: 56 by 44 coarse and 56 by 26.25 fine, at 393, 984 and 1366, equal to the unsigned inputs beside them.
6. **What the browser's number filter changes, accepted by Mark's choice of A and recorded.** On a '.' locale the filter drops a typed or pasted comma, so a pasted "-6,5" reads as -65, and it drops a typed or pasted U+2212, so a pasted "−6" reads as 6. Letters cannot be typed. 'e' and '+' can be typed, and "1e3" reads as a finite number that the parser then rejects with the contract sentence. The up and down arrow keys step the value, which is native number-field behaviour. The parser's comma and U+2212 paths now serve the four text fields. Contract line 187 says so, and the SUMMARY lists these for Mark.
7. **Known edge.** Removing a tasting that holds an unreadable temperature and then undoing the removal restores the carry value into a freshly mounted, empty-looking input. Save then flags that field with the contract sentence rather than saving blank, and typing and deleting a digit clears it. Rare, flagged rather than silent, and not worth a mount-time sync. It goes in the SUMMARY.
8. **Sketch 008's invalid sample.** A number input cannot be handed the sample word through its value attribute, so line 354's invalid state draws an empty field with the sentence beneath it, and its filled state draws a hyphen-minus -6. The unreadable text is the browser's own and is not drawn. The SUMMARY says so for Mark.
