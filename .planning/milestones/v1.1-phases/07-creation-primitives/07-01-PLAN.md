<objective>
A version row can be built from a library record without touching the store (MAKE-03; D-06, D-07, D-08). `rowFromLibraryRecord` takes the `{ id, entry }` record the library store holds (Phase 6 D-02) and the caller's row id and amount, and returns a row shaped exactly as the seeded rows are: a structuredClone of the entry embedded, so a later edit to the library never moves this row's figures.

Purpose: v2's creation screen turns a picked library ingredient into a row through this function, and Plan 03's createRecipe takes rows built by it. Nothing calls it yet, so no screen changes.
Output: app/src/domain/versionRow.js and its node-environment suite.

Visible choice (Claude's Discretion in 07-CONTEXT.md, recorded rather than silent): the builder refuses a contract violation by throwing a TypeError. No module in app/src/domain throws today; refusal there is by returned value (recipeNameMessage returns a message or null) and the existing constructors (createChildVersion, createBatch, renamedRecipe) validate nothing. A throw is chosen because this function's normal return is a record, so a null or an error object would travel on and fail only at import, far from the cause. v2's form gates the maker's input with message functions before calling; the throw is a backstop for a programming error. Reversible: no caller exists, so switching to a returned value is a one-file change (RESEARCH A1).
</objective>
