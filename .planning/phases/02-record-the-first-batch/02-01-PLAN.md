## Phase Goal

**As a** home ice cream maker, **I want to** write on the churned recipe what I actually did — the amounts I really used, the steps I changed, what I measured, and how it tasted — **so that** the next version has evidence to cite instead of my memory.

*Provenance: the ROADMAP `**Goal:**` line for Phase 2 is not written in user-story form, so this story is a mechanical restatement of it rather than a new one. The capability is the Goal line verbatim ("record the 2 Aug batch against the churned version — what was actually done, what was measured, and how it turned out in their own words — and reopen it later unchanged"); the actor is PROJECT.md's persona (home ice cream makers, Mark first); the outcome is the phase's own reason for existing, recorded in the surface brief §1 — 14 of 29 churned batches left no result, and the next version has nothing to cite. To make the ROADMAP Goal line itself a user story, run `/gsd mvp-phase 2` — this plan does not rewrite it.*

<objective>
The phase's tracer: one path through every layer the phase touches, wired end to end. The maker opens the churned recipe, opens the pen layer from the margin, writes a churn date and an as-made amount beside a planned one, saves, and lands on the saved batch's own URL with the ink still on the page. Behind that path: a new `batches` object store at database version 2, the seam's batch methods, a framework-free `domain/batch.js` that owns the record's shape and its snapshot, and the second route.

Then two expansions out from the proven slice: the blank/zero/absent discipline that makes 0 a real value and an untouched cell nothing at all, and the three table carries the as-made column's arrival brings with it (right-aligned content-sized numerics, a total row, and trace below 0.05%).

Purpose: proving the record's shape and its snapshot end to end on the first commit means an architectural dead end costs one commit rather than nine. Everything Phase 2 adds afterwards — the method's strikes, the churn section's measured values, the tastings, the amendment — attaches to the record this plan defines.

Output: the churned recipe with a writable as-made column, a stored batch reachable by URL, and a domain module whose snapshot provably does not move when the version underneath it changes.
</objective>

## Stated decisions (Claude's discretion, CONTEXT.md)

Every item CONTEXT.md left to Claude's discretion, decided here so the whole phase reads one answer. RESEARCH.md's two open questions are closed by items 5 and 6.

1. **Testing approach — no new package.** Phase 1's pattern continues: pure-function unit tests under Vitest's node environment for every rule in `app/src/domain/`, and human verification for interaction. `jsdom` and `happy-dom` stay uninstalled. The interactive surface this phase adds is real, but the logic under it is all expressible as pure functions, and the one genuinely interactive mechanic — the nine-stop mark group — is native browser behaviour that a DOM shim would test less faithfully than a person with a keyboard. A verify gate asserts the dependency list is unchanged, so this decision cannot drift silently.
2. **Store shape.** A separate `batches` object store keyed by `id`, with a `by-version` index on `versionId`, at database version 2 with both `createObjectStore` calls guarded. Tastings live inline on the batch record rather than in a store of their own (RESEARCH.md A2) — no v1 requirement queries them independently of their batch.
3. **The snapshot's contents.** Rows, `coefficientSetId`, `declaredAxes`, and `versionLabel`. The last two go beyond BATCH2-01's literal words: axes because a tasting's marks are keyed by axis and a later rename would orphan them, the label because the saved-state wording quotes it back.
4. **Record field names.** `{ schemaVersion, id, versionId, recordedAt, amendedAt, snapshot, churn, tastings }`, with `churn` holding `{ churnDate, asMade, stepChanges, comeUpMinutes, drawTempC, overrunPercent, drawNotes, ingredientNotes, nextTimeNote }`. Blank is the absence of a key in `asMade`, `stepChanges` and `marks`, and `null` in the scalar fields.
5. **Wording.** `trace` for a row below 0.05% of batch; `unknown` for a blank measured value; `unmarked` for an axis with no mark; `date unknown` for an undated tasting; `recorded 4 Aug 2026 against 50 g oil · 800 g` and `amended {date}` for the save and amendment lines, as the brief fixes them; `No batch recorded against this version yet.` for the empty margin. A version with more than one batch lists them in the margin by churn date, undated last, each linking to its own URL.
6. **The seed carries the 2 Aug batch**, built by calling `createBatch` and `addTasting` — the same functions a maker's own save calls — with a fixed id, so the stored record is indistinguishable from one that was typed and its URL is stable across installs.
7. **A `schemaVersion` 1 store file still imports**, as a store with no batches. Stated in full in 02-02 task 3.
8. **Repository seam methods**, sized to Phases 2–4: `listBatchesForVersion`, `getBatch`, `saveBatch`, `getAllBatches`, `putAllBatches`. Nothing speculative beyond the export/import pair the transfer contract needs.

<assumption_delta_decision>
The assumption-delta detector fired on this phase (`kind: optional` — OBS1-01's "**optionally** adding structured dimensions and a next-time note"). An optional-field signal asks whether the field the model is anchored on is still the right anchor.

- **Primary noun:** the **tasting** — a dated (or undated) evaluation event belonging to a batch — not the words written in it.
- **Decision:** `promote`. A naive reading of OBS1-01 makes `words` the required anchor of an observation and the marks an optional decoration hanging off it. D-02 refuses that: a tasting saves with *at least one of* words or marks, and neither outranks the other. So the record's primary noun is the tasting event, with `words` and `marks` as equally optional siblings gated by one save rule (`isTastingSaveable`), and the batch owns a list of them (D-01).
- **Rationale:** the sheet folded a churn and an undated tasting onto one page and Mark named that a design bug; anchoring on the words would rebuild it. Promoting the tasting to a first-class dated record is what lets a second tasting be added weeks later without an amendment (D-06) and what lets "not yet evaluated" mean something precise (D-05).
- **Consequence carried as accepted debt:** none. The `tastings: []` array lives inline on the batch record rather than in its own object store (RESEARCH.md A2). A later cross-batch tasting comparison (LEARN-01, out of scope for milestone 1) would force a promote to a second store; nothing in v1 asks for it.
- **Invariant test (suggested, landing in 02-03):** `isTastingSaveable` is asserted to return true for marks-only and for words-only, and false for neither — the test goes red the instant a future change makes either field required.
</assumption_delta_decision>

  <action>
Wire one path from a typed as-made amount through to a stored, reopenable batch. Production code, not a prototype: the record shape, the store, the seam and the route are final for this phase, and everything later plans add attaches to them.

**Record shape — `app/src/domain/batch.js` (new).** Open with the pure-module header the domain files already use, stating that the file has no framework, DOM or store import, and citing the decisions it encodes (D-01, D-11, D-18, D-20, BATCH2-01). Export `BATCH_SCHEMA_VERSION` as `1` — this is the batch record's own schema version, unrelated to the store file's.

Export `createBatch(version, churnFields, { id, now })`, a pure function that never reaches for a global clock or a global id source. It returns `{ schemaVersion, id, versionId, recordedAt, amendedAt, snapshot, churn, tastings }` where `recordedAt` is the supplied `now` (an ISO 8601 string), `amendedAt` is an empty array, `tastings` is an empty array, and `snapshot` is `{ coefficientSetId, versionLabel, rows, declaredAxes }` built with `structuredClone` of the version's `rows` and `declaredAxes`. The snapshot is what BATCH2-01 exists for and what PROJECT.md's coefficient-drift hazard names: it is taken once here and never retaken by any later function.

`churn` holds `{ churnDate, asMade, stepChanges, comeUpMinutes, drawTempC, overrunPercent, drawNotes, ingredientNotes, nextTimeNote }`. This task fills `churnDate` (a `YYYY-MM-DD` string or `null`) and `asMade`; the remaining keys are created with `null` (or, for `stepChanges`, an empty object) so the shape is complete from the first commit and 02-02 fills them rather than growing the record.

`asMade` is an object keyed by row id. **A key is present only when the maker wrote something**, and its value is always a finite number — zero included. Blank is the absence of the key, never `null` in the map and never the plan's number (BATCH1-01's anti-goal; D-11). Export two readers so no call site has to remember that rule: `hasAsMade(batch, rowId)` returning whether the key is present, using an own-property check in the manner `figures.js` already uses for authored bands, and `asMadeFor(batch, rowId)` returning the number or `null` when absent. No function in this file may use `||`, or `??` with a non-null default, on an as-made value.

Export `formatRecordDate(iso)`, which takes the leading `YYYY-MM-DD` of any ISO 8601 string and returns the sheet's date wording — `4 Aug 2026`. Build it from the string's own year, month and day components against a fixed three-letter month table. Do not construct a `Date` and do not call a locale- or timezone-dependent formatter: the same record must read the same on every machine and in every test run.
