## Phase Goal

**As a** home ice cream maker, **I want to** open the pen on a version I have already churned, change it with the old values struck beside the new ones, and save the result as a next version that names its parent and my reason, **so that** I can develop the recipe without touching the record of what I actually made.

*Provenance: the ROADMAP `**Goal:**` line for Phase 3 is not written in user-story form, so this story is a mechanical restatement of it, not a new one. The capability is the Goal line verbatim ("create version 2 from the churned version, adjust it, and see exactly what changed and what it did to the balance — with the churned version and its recorded batch untouched"); the actor is PROJECT.md's persona (home ice cream makers, Mark first); the outcome is the surface brief § 1's own reason for existing — the reason for a change is almost never on the page that makes the change. To make the ROADMAP Goal line itself a user story, run `/gsd mvp-phase 3` — this plan does not rewrite it.*

<objective>
Wire one path from the pen on the churned version through to a saved child version that reopens by its own URL, and move the store under it in the same breath — because the child record cannot exist without the shape D-06 introduces.

Purpose: this is the spine of the phase. The version record's new shape (parent id, parent line snapshot, reason, cited batch id, creation date, per-row and per-step removed flags, per-step uses lists, per-note inherited-from markers), the one-time database upgrade that lifts every stored record to it, the store file that carries it, and the third mode on the recipe page are all decided here and everything later plans add attaches to them. D-06 is rated costly: every stored version and every export carries the new shape, so going back means a second migration and a validator change.

Output: `versionLift.js`, `rows.js` and `lineage.js`; database version 3 with a cursor lift; store file schemaVersion 3 with the extended validator and the D-09 parent gate; the seed's `uses` lists; a `Headnote` component carrying the save ceremony; a `developing` mode on the recipe page; and a `fake-indexeddb`-backed test proving the churned version's figures and its batch do not move across the upgrade.
</objective>

<assumption_delta_decision>
The assumption-delta detector fired `pluralization` on this phase. The literal signal ("master-blend multiple") is a false positive — "multiple" there is a multiplier, not a second instance of anything. The genuine delta underneath it is real and is recorded here rather than passed over: **Phases 1 and 2 assumed one version per recipe.** The seed's `parentVersionId` is `null`, `RecipeList` renders one row per stored version, and `/recipe/:id` names a version id while reading as a recipe URL. This phase introduces a second version of the same recipe.

- **Primary noun:** the **version record**, keyed by its own id. That was already promoted in Phase 1 ("version-embedded ingredient row promoted as the primary identity model"); this phase does not move it.
- **Decision: `no-change`.** Lineage is added *to the version record* (`parentVersionId`, `parentVersionLabel`, `createdAt`) rather than by introducing a `recipes` object store. `recipeId` stays a grouping attribute on the version, and "each recipe once at its most recently created version" is derived in memory (1–6 versions per recipe, CONTEXT.md's discretion note: no new index).
- **Accepted debt:** a recipe has no record of its own, so there is nothing to hang a recipe-level fact on. What would force a later promote: a recipe-level attribute that is not a property of any single version (a recipe rename that must apply to every version, deleting a recipe, or a list that must show a recipe with zero versions). None of the three is in milestone 1.
- **Invariant test accepted** (the checkpoint's optional companion, built in Task 1's suite): for any number of versions of one recipe, `latestVersionPerRecipe` returns exactly one version per `recipeId` and it is the one with the greatest `createdAt` — this goes red the moment a future phase reintroduces the one-version-per-recipe assumption.

**The shape — `app/src/store/versionLift.js` (new).** Open with the one-paragraph file header convention `transfer.js` uses, naming D-06 and D-07 and stating that this is the one lift both `db.js`'s upgrade and `transfer.js`'s import call, so no second ladder can drift from it. Export `SEED_CREATED_AT` as `'2026-07-01T00:00:00.000Z'`, a fixed constant with a comment reading that it stands for "before this field existed" and is deliberately not derived from any batch, so two machines running the migration on different days agree (RESEARCH.md assumption A1). Export `SEED_USES`, the map keyed by step `n` given in the behavior block above (D-08, confirmed by Mark).

Export `liftVersionRecord(raw)`: fully synchronous, pure, idempotent, and additive. It spreads `raw`, defaults each new field with `??`, maps `rows` to add `removed` where absent, maps `method` to add `removed` and `uses` where absent, and normalises each authored note to `{ text, inheritedFrom }` — accepting a bare string (Phase 1 and 2's shape) or an object already in the new shape. When `raw.id` is `olive-oil-ice-cream-v1`, it fills each step's `uses` from `SEED_USES` **only where that step's `uses` is empty**, so a maker who later edits the seed's uses is not overwritten by a re-run. It never deletes a key it does not recognise, and it never touches `grams`, `ingredient`, `instruction`, `targets`, `equipment` or `process`. No `await` may appear in this file: Pitfall 1 in the research is that an awaited non-IDB promise inside `upgrade` auto-commits the transaction and throws `TransactionInactiveError` on the next request.

The only awaited expressions inside the callback are `store.openCursor()` and `cursor.continue()`. Add a comment on that branch naming the rule and why it matters. Keep the file's existing claim that it is the only module under `app/src` touching the store library — it still holds.
