<objective>
Close G-03-11: give every ingredient-table column an honest width, so the Remove column's buttons stop painting over the Data column's basis word and over the Formulation Note beside the table.

Purpose: this is a width-allocation fault, not a paint-order fault, and the diagnosis measured it in a real browser. `IngredientTable.jsx` emits `ingredient-table__col-data` and `ingredient-table__col-remove`, and no rule in any stylesheet matches either class — they have been the table's two unsized columns since 03-02. Under `table-layout: fixed` they split whatever the sized columns leave, and the sized columns leave 10.81px at a 1280px viewport, not the ~197px the 03-08 derivation recorded: with the default content-box every declared width has the cells' 24px of horizontal padding *added* to it, so 88px measures 112px and 66px measures 90px. That derivation comment subtracted the padding from the remainder instead, and it will reproduce this bug on the next column added. The two columns get 5.41px each, their contents cannot shrink — a single unbreakable word and a native button — and the button, painted after the Data cell in document order, covers the word entirely (60.46px of overlap, the header reading "DAEMOVE") and spills 67px past the table into the Formulation Note. The same fault is live and unreported in the reading state, where the Data column is 10.8px at 1280.

Output: four sized columns whose declared widths mean what they say, one unsized column that absorbs the remainder, and a test that computes the budget from the tokens so this cannot be shipped green again.
</objective>

<flagged_assumptions>
**The wrap begins at about 1140px, not about 1100px.** D-UAT-6 promises names unwrapped at 1280 and above and accepts a wrap "below about 1100". The measured minimums do not quite reach 1100 without giving something else up: at a 1100px viewport the table is 648px and the six non-name columns need 524px of it, leaving 112px of content box against the 142.83px "Lambda carrageenan" needs. Reaching 1100 exactly would mean narrowing the numeric columns below the 80.61px "% of batch" header and wrapping that header instead. This plan keeps the header unwrapped and lets the name begin wrapping at about 1146px — inside "about 1100" as a direction, on the wrong side of it as a number. It is recorded here rather than absorbed, and the human check names 1152 and 1024 explicitly so Mark sees both sides of the threshold.

**A struck grams value and its replacement may no longer share a line for the largest rows.** `route-recipe-version.md` § 6 asks that "the numeric columns must be sized so a struck value and a current value fit on one line at the working case's widths", while D-UAT-6 sizes those columns to the "% of batch" header at about 81px. The working case fits comfortably — UAT test 1's `40 g` struck beside `48 g` is about 60px — but the seed's largest row (370.4 g) struck beside a changed value is about 114px and would wrap to a second line. That is true at today's 88px content box as well, so this is not a regression this plan introduces; it is a promise the brief makes that the numeric column has never kept for the largest rows. D-UAT-6 is the later and binding ruling, so it is followed. The brief should be amended to say which values must share a line — an Impeccable-owned follow-up, not this plan's to write.

**The two tasks must land in this order and neither is complete without the other.** The diagnosis ran both halves as isolated runtime interventions. Border-box accounting alone (intervention B) takes the overlap from 60.5px to 0.7px but leaves both columns unsized and the word still 12.7px outside its cell. Widths alone (intervention E) removes the overlap but squeezes the name column to 158px, below what the widest name needs. Task 1 fixes the accounting so task 2's arithmetic is done in one frame; task 1 alone is a large improvement and no regression, which is why it is a safe commit on its own.
</flagged_assumptions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a control's rendered box → the values beside it | Under a fixed table layout an unconstrained control cannot widen its column, only overflow it and paint on its neighbour |
| the table's right edge → the Formulation Note beside it | An overflow that runs rightward leaves the table entirely and lands on a different region's figures |
| a declared width → the width the column occupies | With content-box cells the two differ by the cells' padding, silently, on every column at once |
| a class the component emits → a rule that matches it | A grep can prove the class is written; only reading both files can prove anything styles it |
| device boundary | Nothing crosses it — no network call, no external model call and no dependency added under `app/` |
