# Phase 03.1 Plan 04: The pen keeps the page — prose in place, purpose and aside on demand, the uses line Summary

**Every prose field in the pen (intro paragraph, step text, notes, the record's own words) now edits in place as the printed paragraph rather than a form field; a step's purpose and aside open only when asked; the twelve uses checkboxes hide behind one "change" control per step; the batch pen's per-step line does the same; and every control in a step body names its step — cutting the developing-state's interactive-element count from 202 to 92 on the seeded 10-step method.**

## Accomplishments

- A new `prose-field`/`prose-field--lead-in`/`prose-text` class family (app.css) draws every prose value as the printed paragraph — text face, pen blue, no border at rest, the outline only via the existing global `:focus-visible` rule — while `ink-field` stays untouched for grams, target chips, the version line and measured batch fields.
- Purpose and aside per step now open only when the draft already holds text or the maker presses `add purpose`/`add aside`; emptying and blurring collapses the field back to its opener with no purpose/aside stored (D-23).
- The uses list reads as one line of row names with a `change`/`done` control that opens the twelve checkboxes for that step alone; Escape inside the open checklist stops propagation so it closes the checklist only, never the pen (D-24).
- The batch pen's per-step "done differently" line reuses the same on-demand mechanism; the Skipped checkbox stays always present; Amend's own baseline opens whichever lines already hold text (D-25).
- Every field, checkbox, fieldset and on-demand control in a step body carries its step in its accessible name through the existing `fieldLabel` builder (D-28) — 12 distinct `aria-label` source lines in `Method.jsx`, up from 7.
- `Method.jsx`'s per-step pen rendering split into `StepPenBody`/`StepRecordingControls` sub-components, each owning genuine `useState`, rather than hooks called inside the bare `steps.map()` callback.
