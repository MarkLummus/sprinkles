## Planner decisions recorded for this plan

1. **The total row's fix adds a bare-number domain export, and `formatGrams` is defined in terms of it.** This resolves RESEARCH.md's second open question. Stripping `' g'` at the render site would work once and re-break the moment the unit format changes; a named export makes the bare-number case first-class, keeps `formatGrams`'s existing contract byte-identical for its four other callers, and gives `buildDiff` somewhere honest to put `total.fromValue`/`total.toValue` so no render site ever composes two already-unit-suffixed strings again. Note in the SUMMARY which one was chosen so a future column-arithmetic touch does not reintroduce the bug through the other pattern.
2. **The one pen diff is lifted to the page rather than duplicated.** `Method.jsx` already calls `buildDiff(draftVersion, baselineVersion)` locally, which is what the critique points at when it says the comparison already exists. Computing it once in `RecipePage` and passing it to both `Method` and `FormulationNote` is the fix the Don't Hand-Roll table asks for and removes a second call per keystroke rather than adding one.
3. **`--col-step-pen` is 160px, derived and asserted, not guessed.** `columns.test.js`'s own measured figure is 66.14px for the nine letters of `estimated`, i.e. ~7.35px per letter at the table body size. `3. Build the base` is 17 characters, ~125px, plus the chevron room plan 03 added and twice `--table-cell-pad-x`. At 1280px in the widest pen state the six sized columns then leave the name column ~162px, still above the measured 142.83px of the widest seed ingredient name. The suite asserts the derivation rather than trusting the number.
4. **The split-step suffix follows the brief, not the critique's wording.** The critique proposes suppressing the suffix when the primary is absent; `route-recipe-version.md` § 6 as revised 2026-09-08 requires `unallocated + 3`. The brief is both later and binding (D-29), so the primary always prints something and the suffix stays.
5. **`autonomous: false`, and the re-critique is a task, not a footnote.** This plan ends the phase, so its last task is a `checkpoint:human-verify` carrying the re-critique — a human judgement no command can make, and one the project's `human_verify_mode: end-of-phase` does not suppress, because the gate sits at the very end of the last plan of the phase rather than mid-flight. Nothing executes after it, so stopping there and deferring to an end-of-phase UAT are the same moment; the executor pays no cold-start for it. It carries `gate="blocking-human"` because auto-approving "the critique's P1s are closed" would answer the one question the phase exists to ask. The automated phase-closing commands stay in `<verification>`; the human done-check lives only in the task, so the two do not say the same thing twice.

**The domain rule.** In `lineage.js` extract the per-row walk of `blockedSaveMessage` into one internal helper that returns the first offending row together with its message, and rebuild `blockedSaveMessage` on top of it so the existing behaviour and its message strings are unchanged. Add the new rule inside that walk, after the blank check and before moving to the next row: a non-removed row whose `grams` is neither blank nor a non-negative number with up to two decimals blocks the save with the message `` `${row.ingredientName}'s amount is not a number` ``. The pattern is Claude's Discretion within the brief's rule — use an anchored pattern accepting digits with an optional fractional part of one or two digits and nothing else, so a leading minus, a stray letter, whitespace and an exponent all fail; keep what the maker typed untouched either way. Extend the function's existing doc comment to name the new check and its place in the fixed order, and keep the module framework-free.

Add a second export `blockedSaveRowId(penFields, version, versions)` reading the same helper and returning the offending row's id, or `null` when nothing blocks or when the block is the version line's. Both exports share one traversal of the rule, so the message and the row it names can never disagree.

**The page.** In `RecipePage.jsx`, where a blocked save already sets `blockedMessage`, also set a new `blockedTarget` state to `{ kind: 'versionLine' }` when the block is the line's, or `{ kind: 'row', rowId }` from `blockedSaveRowId` when it is a row's.
