# Phase 03.1 Code Review — The imprint and the binder

**Scope:** the five plans' worth of changes moving every control out of the printed spread into a new `Versions`/`PenFoot` front-matter band, the global "binder" control treatment in `app.css`/`tokens.css`, prose-in-place editing with on-demand purpose/aside/uses/done-differently fields, and the three build-gap closures (rule strikes, tab order, grams guard) plus the column-arithmetic fixes in `diff.js`/`composition.js`/`IngredientTable.jsx`.

Per the task's instructions, the following are **not** re-reported (already tracked): the `declaredAxes` lift gap in `liftVersionRecord`; the raw-string grams-draft strike comparison at `IngredientTable.jsx` (`GramsCell`/`changedGrams`); the thirteen stale UI labels; the Firefox calendar-icon gap.

## Summary

This is careful, well-documented work. Every domain function I traced (`composition.js`, `diff.js`, `lineage.js`) is pure, side-effect-free, and does what its own doc comment claims — I verified `formatGramsValue`/`formatGrams`'s never-disagree claim, `buildDiff`'s total/figures/row/step math, and `blockedSaveMessage`/`blockedSaveRowId`'s shared-traversal claim by reading `findBlockedRow` directly. The CSS contract tests (`binder.test.js`, `columns.test.js`) assert real arithmetic against the actual token values rather than hand-waved constants, and I re-derived the hover-padding equality and the `--col-step-pen` budget myself to confirm they hold. React hooks are used correctly throughout — `StepPenBody`/`StepRecordingControls` are properly decomposed into real components so `useOnDemandField` is never called from inside a bare `.map()` callback, and no hook is called conditionally anywhere I read.

The two Warnings below are both real, reproducible defects in the new focus-management code, not style preferences. Both stem from the same shape: a "move focus once, when this flips true" `useEffect` keyed off a value that can repeat.

## Warnings

### WR-01: Blocked-save focus does not return on a repeated Save press

**File:** `app/src/ui/Versions.jsx:126-128` and `app/src/ui/IngredientTable.jsx:431-434`

**Issue:** Both blocked-save focus effects fire only on a *transition* of their dependency value:

```js
// Versions.jsx
useEffect(() => {
  if (versionLineBlocked) versionLineFieldRef.current?.focus();
}, [versionLineBlocked]);

// IngredientTable.jsx
useEffect(() => {
  if (!blockedRowId) return;
  gramsInputsRef.current.get(blockedRowId)?.focus();
}, [blockedRowId]);
```

`versionLineBlocked` is a derived boolean (`blockedTarget?.kind === 'versionLine'`) and `blockedRowId` is a plain row id string. In `RecipePage.jsx`'s `buildPenFields`, every failed save recomputes `blockedTarget` via `setBlockedTarget(...)`, but if the *same* field is still the offender, the new value is referentially different but *value-equal* to the old one (`{kind:'versionLine'}` vs. `{kind:'versionLine'}`, or `'row-04'` vs. `'row-04'`). React's dependency comparison sees no change and the effect does not re-run.

**Concrete failure scenario:** Leave the version line blank, fill in everything else, and click Save. `blockedTarget` flips from `null` to `{kind:'versionLine'}`, the effect fires, and focus moves into the version-line field — correct. Clicking a `<button>` moves the browser's own DOM focus onto that button. If the maker, without touching any field, clicks Save a second time (still blank), `buildPenFields` blocks again on the same field, but `versionLineBlocked` is `true` both before and after — the effect does not re-fire, and focus is left stranded on the Save button rather than moving to the offending field, violating D-21 ("pressing it… moves focus to the offending field") for every press after the first. The identical shape reproduces in `IngredientTable.jsx` when two rows are simultaneously blank: block on row A, click Save again with nothing touched, and focus stays on the Save button instead of returning to row A's grams field.

**Fix:** Key each effect off a value that changes on every blocked attempt, not just every first block — e.g. have `RecipePage` stamp an incrementing attempt counter (or the save handler's own call count) onto `blockedTarget`, and depend on that counter rather than on the derived boolean/id alone; or have the effect read a ref that RecipePage bumps on every `buildPenFields` call that returns non-null, regardless of whether the target changed.

### WR-02: Fork save's landing focus is unverified and reported failing in the phase's own re-critique

**File:** `app/src/ui/RecipePage.jsx:1022-1037`, `app/src/ui/Versions.jsx:282-289`

**Issue:** `handleSaveAsNewVersion` navigates to the child's URL with `{ state: { focusDevelop: true } }`, and `Versions` wires that through to `autoFocus={focusDevelopOnMount}` on the child's Develop button (D-27: "after a fork saves… focus goes to the child's Develop control"). The phase's own `03.1-05-SUMMARY.md` hand-check list records this as tried live and failing: "focus after Save lands on `<body>`, still open." This is a real, currently-broken part of the D-27 keyboard contract that ships with this phase, not a hypothetical.

**Concrete failure scenario:** Open the plan's pen on an unchurned version, fill in a version line, and press Save (or Save as). The page navigates to the child's URL; per the re-critique, the child's Develop button does not receive focus — focus lands on `<body>`, meaning a keyboard-only maker who just forked a version loses their place entirely and must Tab from the top of the document to find any control.

**Fix:** This is already tracked as an open item in the phase's own SUMMARY rather than silently claimed fixed, so I am not asking for a fix here — flagging it because the phase's `status: complete` combined with a coverage table (`D5`) that reads `status: pass` for the same behavior could read as resolved to someone who does not also read the prose hand-check list. Worth surfacing plainly in the phase's outward-facing status, not just the SUMMARY's own prose.

## Info

### IN-01: `PenFoot`'s record/amend Save carries a `disabled` binding that is always false

**File:** `app/src/ui/PenFoot.jsx:56`

`penSaveDisabled` is computed in `RecipePage.jsx` as `openPen === 'tasting' && tastingDraft ? !isTastingSaveable(...) : false` — for `openPen === 'record'`/`'amend'` it is always `false`. `PenFoot`'s record/amend branch nonetheless writes `<button ... disabled={penSaveDisabled}>`, which is harmless (always renders enabled) but contradicts plan 02's own recorded key-decision ("the batch pen has never gated its Save… carr[ies] no disabled attribute"). A future change to `penSaveDisabled`'s derivation that widens its condition would silently start disabling the record/amend Save too. Consider dropping the attribute from that branch to match the documented intent, or updating the comment.

### IN-02: `ingredientNotes` is a single-line `<input>` dressed as a growing prose field

**File:** `app/src/ui/BatchMargin.jsx:198-206`

This phase (plan 04) swapped `ingredientNotes`'s class from `ink-field` to `prose-field` alongside its four textarea siblings (`drawNotes`, `nextTimeNote`, tasting `words`/`nextTimeNote`), but the element itself is a single-line `<input type="text">`, not a `<textarea>` (this predates this phase — confirmed via `git log -p`). `prose-field`'s CSS (`app.css`) includes `field-sizing: content` semantics that only apply to `textarea`; on this `<input>` the maker gets the printed-paragraph colour/no-border treatment but never the "grows with its text, no resize grip" behavior every other prose field in the same component now has, an inconsistency a maker will notice when a long ingredient note keeps scrolling sideways in a single line while every other field around it grows. Not a regression this phase caused, but this phase is what makes the sibling fields visibly behave differently, so worth a follow-up to swap the element type or intentionally document why it stays single-line.

### IN-03: `Versions.jsx`'s Reason line wording diverges from `03.1-CONTEXT.md`'s own D-08 text

**File:** `app/src/ui/Versions.jsx:354`

D-08 in `03.1-CONTEXT.md` describes the empty-reason case as reading "none recorded"; the shipped component (and its test) reads "no reason recorded". This is not a bug — the wording actually matches the binding design brief (`route-recipe-version.md` § 3: "the lineage line then reads 'no reason recorded'"), which supersedes the context doc's own looser paraphrase — but it's worth a note so a future reader comparing `03.1-CONTEXT.md` to the code does not mistake the brief-compliant string for a drift.

## Reviewed and found sound

- **Domain purity invariant:** `composition.js`, `diff.js`, and `lineage.js` import no framework, DOM, or store code (verified by direct import inspection); `blockedSaveMessage`'s own "never looks at a band, a deviation or an advisory" claim is asserted by the test suite reading the function's own source, and I independently confirmed no such reference exists.
- **Repository seam:** no module outside `app/src/store/db.js` imports `idb`.
- **No `dangerouslySetInnerHTML`** anywhere under `app/src`, and no unrendered/HTML-injecting pattern introduced by this phase.
- **`formatGramsValue`/`formatGrams` never-disagree contract:** traced `formatGrams` to be defined literally in terms of `formatGramsValue`, so the total row's struck bare number and the suffixed current value can never show different digits for the same underlying mass — confirmed against `diff.js`'s `total.fromValue`/`total.toValue`, built the same way.
- **`buildDiff`'s row/step/target/figure comparisons:** traced `buildRowDiff`, `buildStepDiff`, `buildTargetDiff`, and the figures/total assembly — all compare at display precision as documented, never mutate either input version, and the absent-vs-empty-string normalization for `purpose`/`aside` is applied identically on both sides.
- **`versionLineUnique`/`blockedSaveMessage`/`blockedSaveRowId` share one traversal** (`findBlockedRow`) so the blocking sentence and the row it names cannot disagree; `RecipePage.buildPenFields` correctly pre-filters the `versions` list by `excludeId` before calling either function, so the "exclude self on save-over" contract documented in `lineage.js` actually holds at the call site.
- **Hook usage:** `StepPenBody`/`StepRecordingControls` are real JSX-invoked components (not plain function calls inside `.map()`), so `useOnDemandField`'s `useState`/`useRef`/`useEffect` calls are never conditional or looped; no hook is called after an early return anywhere I read in `RecipePage.jsx`, `Versions.jsx`, `Method.jsx`, or `IngredientTable.jsx`.
- **Escape-key stopPropagation trick** (`Method.jsx`'s uses-checklist `onKeyDown` calling `event.stopPropagation()` against `RecipePage`'s native `document`-level listener): verified this is not a synthetic-vs-native event mismatch — React's synthetic `stopPropagation()` calls the underlying native `stopPropagation()`, and since React 17+ delegates from the root container (an ancestor of `document` in bubble order), this does correctly prevent the native document listener from also firing for the same keypress.
- **CSS token arithmetic:** independently recomputed the button/select hover "nothing moves" equality (`gap-xs + rule-baseline - rule-ink-field` at rest vs. `rule-baseline + gap-xs` on hover — both 7.5px) and the `--col-step-pen` budget derivation; both hold as documented, and `binder.test.js`/`columns.test.js` assert them from the live token values rather than hardcoded numbers.
- **`select.ink-field`/chevron specificity fix** (plan 03's own documented deviation): confirmed the combined `select, select.ink-field` selector is necessary and correctly applied — a bare `select` rule alone would lose to `.ink-field`'s class-level `background: none`.
- **Test quality:** no `.only`/`.skip`/`it.todo`, no vacuous assertions, no `console.log`/`debugger` left in reviewed files. `lineage.test.js`'s `blockedSaveMessage`/`parseGramsDraft` suite in particular cross-checks the two functions against each other ("agrees with blockedSaveMessage") rather than testing them in isolation, which is exactly the kind of test that would catch the two functions drifting apart.
- **Column/row rendering column-count parity:** verified the `isShowingChanges`/`isDeveloping`/plain-reading branches in `IngredientTable.jsx` each render the same number of `<td>`s as their corresponding `<th>` set (the As-made and Remove columns are each gated identically in header and body).
