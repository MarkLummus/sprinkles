# Phase 03.2: The portion and the reset - Context

**Gathered:** 2026-09-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 03.2 changes the stored shape of a recipe version so that a row's **portions** are what the maker authors and the row's total derives as their sum, and it retires `step` / `splitStep`. It carries no new requirements: it builds `route-recipe.md` § 3 "The portion is the authored amount" and "Split-step prose carries no amounts", both confirmed by Mark 2026-09-09.

The phase was originally written as a migration — one shared lift walking every stored record to the new shape, with `VERSION_SCHEMA_VERSION`, `DB_VERSION` and the store file's `schemaVersion` moved in lockstep, and the `declaredAxes` P0 fixed inside `liftVersionRecord`. It was re-scoped on 2026-09-09 after Mark asked why the project is doing migration work for a single recipe it can recreate. It is not: the seed lives in `app/src/data/olive-oil.js` and `app/src/data/batch-2026-08-02.js` as hand-authored source, rewriting those two files to the new shape was already the bulk of the phase, and there is no stored record anywhere that source does not already describe. **The store resets rather than migrates.**

What the reset gives up is compatibility with records held *outside* source — an older browser profile's IndexedDB, an older exported store file. Mark confirmed there is nothing in his profile worth keeping. That cost is therefore zero now and becomes non-zero at the first record he actually cares about; the migration discipline is deferred to that point, not abandoned.

The visible outcome is unchanged from the original phase: the churned olive oil version and its 2 Aug batch must reopen with **every figure unmoved**. This is a shape change with no arithmetic change.

Not in this phase: the page's arrangement — the step-order table, the front-matter rows, the margin's retirement (all Phase 03.3, which reads this shape). Not splitting a row in the pen: the portion count is fixed in milestone 1, amounts edit and the split does not; splitting in the pen is milestone 2.

</domain>

<decisions>
## Implementation Decisions

The ROADMAP's Prerequisite settles the amounts. The decisions below record the 2026-09-09 re-scope and what follows from it.

### The shape

- **D-01:** A row carries **`portions`**: an array of `{ step, grams }`, in step order. The row's total is **derived as their sum**, never stored — a stored total and a portion list are two places for one number and they drift. An **unsplit ingredient is a one-portion row**, so one rule covers split and unsplit with no second case and no branch at the read sites. — **Reversibility:** one-way for stored records once the reset lands; reversible in source until then.
- **D-02:** **`step` and `splitStep` retire.** Every reference follows — 31 across `domain/stepNumbers.js`, `ui/IngredientTable.jsx`, `ui/IngredientTable.test.jsx` and `data/olive-oil.js`. `stepNumbers.js`'s doctrine is unchanged: the stored key `n` is still the step's identity and still never moves; only a row's *reference* to it changes shape.
- **D-03:** **Split-step prose loses its amounts.** The number lives in one place — the portion. Amounts for **unsplit** ingredients stay in the prose as written; only the split ones are struck, because only they now say the number twice.
- **D-04:** **Balance reads the derived total.** The coefficient snapshot stays **per ingredient, never per portion** — a portion is an amount at a step, not a different substance.

### The reset, in place of the lift

- **D-05:** **The store resets.** `DB_VERSION` bumps and the `upgrade` callback **drops and recreates both object stores**, so a returning profile comes back empty and reseeds through the existing `seedIfEmpty` path. No cursor, no per-record rewrite. `upgrade` stays free of any `await` other than IDB-native requests on its own `versionchange` transaction — the constraint db.js already documents survives the change.
- **D-06:** **`versionLift.js`'s ladder retires.** Its seed facts are not lift facts and move to where they belong: `SEED_USES` and `SEED_CREATED_AT` go with the seed data. `VERSION_SCHEMA_VERSION` survives as a constant. Nothing under `app/src` keeps a second, private ladder — the rule that two lifts drift still holds, and the cheapest way to honour it is to have none.
- **D-07:** **The `declaredAxes` P0 is closed by authoring, not by lifting.** It was a *missing entry* in `liftVersionRecord`; with no ladder the axes are simply authored in their object shape (`{name, low: null, high: null}`) in the seed. The verifiable outcome is the one the original phase named: **the six tasting axes each take a mark independently.**
- **D-08:** **`transfer.js` narrows to the new shape alone.** Export writes the new `schemaVersion`; `validateStoreFile` accepts it and **refuses 1, 2 and 3** with a clear error rather than silently importing an old file as though it were current; `importStore` loses its lift branch. The round-trip promise narrows accordingly: a store exported **after** this change imports after it. The old promise — a store exported *before* the change imports after it — is deliberately dropped, and this decision is where that is recorded.

### The seed's new content

- **D-09:** **Authored portions** (version 1) are as the ROADMAP Prerequisite settles them: whole milk `120 + 250.4 = 370.4 g`; sucrose `12 + 64 = 76 g`. Both match their existing row totals exactly, so **no balance figure moves**.
- **D-10:** **As-made is recorded per portion**, its total deriving the same way. The 2 Aug batch's lump `'row-01': 383` becomes `120 + 263`, matching the sheet line for line. Sucrose is **not** split in the record, because it matched the plan.
- **D-11:** The trap the Prerequisite names is a planning constraint, not a note: `120 + 263` is the **as-made**, never the authored. Writing it as the authored split would take whole milk to 383 g, batch mass to 812.6 g, and move every figure on the churned version — which the phase's Done-when forbids.

</decisions>

<code_context>
## Existing Code Insights

- The seed is **source, not data**: `store/seed.js`'s `seedIfEmpty` writes `data/olive-oil.js` and `data/batch-2026-08-02.js` through the repository seam on an empty store. Resetting the store and rewriting those two files reproduces every record the app has ever held.
- There were **two** lift call sites, and both go: `db.js`'s upgrade cursor and `transfer.js`'s `importStore`.
- `declaredAxes` is referenced across `domain/axes.js`, `domain/batch.js`, `domain/lineage.js`, `store/transfer.js` and their tests — the authored shape must satisfy all of them, since only the lift is retiring, not the field.
- Every store access goes through `store/repository.js`; only `db.js` imports `idb`. The reset must not widen that seam.
- Domain modules under `app/src/domain/` stay framework-, DOM- and store-free, and their suite runs under Vitest's `node` environment. The derived-total rule belongs there.

</code_context>
