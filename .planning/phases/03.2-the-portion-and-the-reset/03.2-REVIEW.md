# Phase 03.2: Code Review Report

**Reviewed:** 2026-09-10T04:26:17Z
**Depth:** standard
**Files Reviewed:** 28
**Status:** issues_found

## Summary

This phase moves a row's amount from a single stored total to a `row.portions` array (`{ step, grams }`), makes `rowGrams(row)` the one place a total is derived, and grows a batch's `churn.asMade[rowId]` into an array aligned index-for-index with `row.portions`. The domain layer (`rows.js`, `composition.js`, `figures.js`, `batch.js`, `diff.js`, `lineage.js`) is careful and consistent: every reader that needs a row's total goes through `rowGrams`, no module stores a total beside the portions, and the diff/lineage/batch test suites exercise the split, the blank/zero/plan-never-leaks discipline, and the never-mutate contracts thoroughly. `db.js`'s reset-not-lift migration and `transfer.js`'s schema-4-only gate are both clean, well-tested pieces of work.

The defects found are concentrated at the edges of the refactor: two places where an array of per-portion values is joined into one printed string without filtering out the "not written" placeholder, one advisory that was mechanically converted from `row.grams` to `rowGrams(row)` without reconsidering whether a per-row total is still the right unit for a per-weighing rule, and one place the new import validator stops short of the alignment invariant the rest of this phase's code and comments assert. None of these touch data integrity in the store itself — the stored records stay correct — but one produces genuinely wrong-looking text on the primary "read your own recorded batch" surface for an entirely ordinary recording pattern.

## Critical Issues

### CR-01: A partially-recorded split row's as-made reading prints a dangling "+" and a doubled space

**File:** `app/src/ui/IngredientTable.jsx:415-423` (and the parallel pen-side instance at `app/src/ui/IngredientTable.jsx:679-680`, read into `rowAccessibleLabel` at `app/src/ui/IngredientTable.jsx:118`)

**Issue:** `formatAsMadeReading` builds the reading-state's as-made cell by mapping every portion to its written value or `''` when the maker wrote nothing at that portion, then joining with `' + '`:

```js
function formatAsMadeReading(row, batch) {
  if (!batch || !hasAsMade(batch, row.id)) return null;
  return row.portions
    .map((_, i) => {
      const value = asMadeForPortion(batch, row.id, i);
      return value !== null ? `${value}` : '';
    })
    .join(' + ');
}
```

Leaving a portion blank is the app's own documented way of saying "matched the plan" (D-10) — an entirely ordinary, everyday recording pattern for a split row such as whole milk (two portions, step 2 and step 3), not a rare edge case. For a two-portion row with the first portion written and the second left blank, `parts` is `['120', '']`, and `.join(' + ')` produces the literal string `"120 + "`. The caller then appends the unit: `` `${reading} g` `` → **`"120 +  g"`** — a trailing "+" with nothing after it and a doubled space before the unit. For a three-portion row with a blank middle portion the result is worse: `"100 +  + 50 g"`. This is confirmed by direct execution, not just static reading:

```
$ node -e "console.log(JSON.stringify(['120',''].join(' + ') + ' g'))"
"120 +  g"
```

The existing test for this exact scenario (`IngredientTable.test.jsx`, "a split row with one written portion renders the placeholder for the other and never that portion's plan amount") only asserts `toContain('120')` / `not.toContain('250.4')`, so it never notices the malformed joined string — it would pass unchanged even with this defect present.

The same unfiltered-join pattern reappears on the pen side: `changedGrams` (`IngredientTable.jsx:680`) is `draftRow.portions.map((portion) => portion.grams).join(' + ')` over the raw typed strings, with no blank-filtering, and is read into the row's accessible name (`rowAccessibleLabel`, line 118) as `was X g, now ${changedGrams} g` — so a screen reader announces the same "+  " artifact while a maker is mid-edit on a multi-portion row.

This reaches the app's core value directly: "get back a record of what happened" is the thing this screen exists to show, and for any split-ingredient batch where the maker recorded one portion and left the other at plan (the normal case, not a misuse), the reading is visibly broken.

**Fix:** Filter out empty entries before joining, e.g.:

```js
function formatAsMadeReading(row, batch) {
  if (!batch || !hasAsMade(batch, row.id)) return null;
  const parts = row.portions
    .map((_, i) => asMadeForPortion(batch, row.id, i))
    .filter((value) => value !== null)
    .map((value) => `${value}`);
  return parts.length > 0 ? parts.join(' + ') : '';
}
```
(or, if a written-but-partial row should visibly show which portion is missing, use an explicit placeholder like `'—'` instead of `''` before joining — either is better than the raw `.join(' + ')` over blanks.) Apply the same filtering to `changedGrams` at line 680, or route it through the same helper.

## Warnings

### WR-01: The sub-scale advisory now judges a row's total, not each weighed portion, against the scale's resolution

**File:** `app/src/domain/advisories.js:47, 50, 57-59, 81, 84-85, 120-122`

**Issue:** This phase's diff mechanically replaced `row.grams` with `rowGrams(row)` throughout `advisories.js` (confirmed via `git diff`), including in `subScaleAdvisory`:

```js
const under = rows.filter((row) => rowGrams(row) > 0 && rowGrams(row) < equipment.scaleResolutionG);
```

Before this phase, a row's `grams` genuinely was the one number weighed for that row. After this phase, `rowGrams(row)` is the *sum* of one or more independently-weighed portions (`rows.js`'s own doctrine: "a row's total is derived from its portions... never stored"). The sub-scale advisory exists to warn when a single weighing falls below what a kitchen scale can resolve — but a row split into, say, two 0.6 g portions (each individually unreadable on a 1 g-resolution scale) with a combined total of 1.2 g would never trigger this advisory under the current check, because the *total* clears the threshold even though neither actual weighing does. The inverse framing problem also applies to the advisory's own wording: `formatScaleGrams(rowGrams(row))` prints the row's combined total in the "X g" clause, which is not the amount that was actually placed on the scale at any single step once a row is split.

This is not exercised by the current seed data (no split row in `olive-oil.js` has an individual portion near `equipment.scaleResolutionG`), so no existing test catches it, but it is a real behavioural gap introduced by carrying over the pre-portions semantics without reconsidering the unit the rule should operate on.

**Fix:** Evaluate `subScaleAdvisory` per portion rather than per row total — e.g. flag any row with at least one portion whose own `grams` is below `equipment.scaleResolutionG`, and report using that portion's own amount rather than the row's combined total:

```js
const under = rows.flatMap((row) =>
  row.portions.filter((portion) => portion.grams > 0 && portion.grams < equipment.scaleResolutionG).map((portion) => ({ row, portion })),
);
```

### WR-02: The store-file validator never checks that a batch's `churn.asMade[rowId]` array aligns with the row's `portions.length`

**File:** `app/src/store/transfer.js:230-247` (`validateBatch`)

**Issue:** This phase's own comment states the invariant plainly: "a row's as-made value is an array aligned index-for-index with that row's portions" (line ~227). `validatePortion`/`validateRow` (added this phase) validate that each row's `portions` array is well-formed, and the `churn.asMade` block (also rewritten this phase) validates that each `asMade[rowId]` is an array whose elements are each a finite number or `null` — but nothing cross-checks `churn.asMade[rowId].length` against the corresponding `batch.snapshot.rows[...].portions.length` for the same row id. `validateStoreFile` is documented as "the one gate before a write" that refuses a malformed file wholesale (T-04-01) — but a file whose as-made array is shorter or longer than the row it belongs to currently imports cleanly.

Through the app's own UI this can't currently happen (a version's rows are frozen the moment it has any batch, per `canSaveOver = batches.length === 0` in `RecipePage.jsx`, so the row/portion shape a batch was recorded against never changes under it). It is reachable only through a hand-edited or corrupted import file — but that is exactly the case this validator exists to catch, and the domain layer's own graceful fallbacks (`asMadeForPortion` returning `null` past the array's end) mean a misaligned import is accepted silently rather than refused with a clear error naming the mismatch.

**Fix:** In `validateBatch`, once `batch.snapshot.rows` is known to be valid, cross-check each `churn.asMade` entry's length against the matching row's `portions.length`:

```js
const rowById = new Map(batch.snapshot.rows.map((row) => [row.id, row]));
for (const [rowId, values] of Object.entries(churn.asMade)) {
  // ...existing array/element checks...
  const row = rowById.get(rowId);
  if (row && values.length !== row.portions.length) {
    errors.push(`${path}.churn.asMade.${rowId}: expected ${row.portions.length} elements (one per portion), got ${values.length}`);
  }
}
```

### WR-03: `AsMadeCell`'s recording-mode input reads past the end of a shorter-than-expected as-made array with no guard

**File:** `app/src/ui/IngredientTable.jsx:449`

**Issue:**
```js
value={draftValues ? draftValues[i] : ''}
```
`draftValues` comes from `draft.asMade[row.id]`, which — for an Amend session — is seeded in `RecipePage.jsx`'s `handleStartAmending` directly from the stored `batch.churn.asMade[rowId]` array (see `RecipePage.jsx:673-676`), not clamped or padded to `row.portions.length`. If that stored array is shorter than the row's current portion count (the exact scenario WR-02 shows the import validator does not refuse), `draftValues[i]` is `undefined` for the missing trailing portion(s), and the `<input value={undefined}>` becomes an uncontrolled input mid-render — a real React defect (a console warning on mount, and a field that stops being driven by state) rather than the intended empty-string placeholder every other branch in this file uses.

**Fix:** Guard the read the same way the rest of the file treats a missing element as blank:
```js
value={draftValues ? (draftValues[i] ?? '') : ''}
```
