### Gaps Summary

Every literal Done-when clause named in the phase brief is backed by direct evidence and passes: the churned version and its batch reopen unmoved, the specific as-made whole-milk record reads `120 + 263`/383, the six axes each mark independently, a stale profile reseeds clean through a real IndexedDB, and a store exported after the change round-trips through `importStore`. `step`/`splitStep` are fully retired, `versionLift.js` is deleted with no remaining importer, `transfer.js` accepts schema 4 alone, the split-step prose carries no duplicated amounts, and the authored split is correctly `120 + 250.4` (never the as-made `120 + 263` trap the phase was explicitly built to avoid).

One gap blocks a clean pass: **CR-01** from the phase's own code review is a confirmed, reproducible, unfixed defect in the As-made column this phase built (D-10) — a split row with one portion recorded and the other left at plan (the app's own documented, ordinary pattern for "matched the plan") renders a malformed reading (`120 +  g`) instead of a sensible one, both on screen and in the row's accessible name. The seeded 2 Aug batch's own whole-milk record happens to have both portions written, so the literal named Done-when text is unaffected — but the very next batch recorded with the ordinary partial pattern hits this immediately, on the screen whose job is "get back a record of what happened." The existing test for this scenario doesn't catch it because it only checks `toContain`, not the full string. This is a small, well-scoped fix (filter blank portions before `.join(' + ')` in two places), not a re-architecture.

Two further review findings (WR-02: import validator doesn't cross-check as-made array length against portion count; WR-03: a consequential uncontrolled-input read if a misaligned array reaches the Amend draft) are real but reachable only through a hand-edited/corrupted import file, not through any path the app's own UI can produce today, and are not named by any of this phase's Done-when clauses or must-haves — recorded as warnings for follow-up rather than blocking. WR-01 (the sub-scale advisory judging a row's total rather than each portion) is unexercised by current data and recorded as informational.
