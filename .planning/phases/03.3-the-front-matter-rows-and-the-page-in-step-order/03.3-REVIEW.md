## Summary

This is an incremental re-review of the files changed by gap-closure plans
03.3-05/06/07 since the prior report (committed at `a981522`), which

rebuild (the front-matter rows split into a head-line/cells layout, the

batches" disclosures).

No Critical-tier defects: no hardcoded secrets, no `dangerouslySetInnerHTML`,
no CSS literal escaping the token system (binder.test.js's own greps over
every rule would already fail on this), no domain module importing
React/DOM/the store, no module outside `store/repository.js` importing
`idb`. The two structural cleanups the prior review's WR-02-adjacent
concerns implied — `versionIdsWithBatches` fully replaced by `allBatches`
with no orphaned reference, and `onStartRecording`/the Record button's
ref-effect pair cleanly relocated from `BatchRow.jsx` to `VersionRow.jsx`
with no leftover prop or handler in either file — are both done correctly;
`grep` confirms no stray `versionIdsWithBatches`/dead `onStartRecording`
signature remains. The new `descendantVersions`/`targetValueFor` domain
functions are small, pure, and well covered by their own tests, including
the "never reads a removed step" and "never mutates or reorders" invariants
this codebase holds every domain function to.

Findings below are Warning/Info tier: the prior review's `penReason`
dead-prop finding (WR-02 in the previous report) persists unfixed in
`BatchRow.jsx` and now has a second, new instance in `VersionStrip.jsx`;
`VersionStrip`'s `is-current` styling is structurally unreachable from its
one real caller now that "Later versions" only ever passes it the current

were); and one WR-01-labelled regression test in `VersionRow.test.jsx`
proves only that the component does not throw, not the re-focus behaviour
its own docstring says it exists to guard.

## Warnings

### WR-01: `VersionStrip`'s `is-current` styling is dead code at its only real call site

**File:** `app/src/ui/VersionStrip.jsx:20`, `app/src/ui/VersionStrip.jsx:27`, `app/src/ui/VersionRow.jsx:338-341`

**Issue:** `VersionStrip` marks the list item matching `currentId` with the
`is-current` class:

```js
// VersionStrip.jsx:27
const isCurrent = version.id === currentId;
```

Before this gap-closure round, `VersionRow` passed the recipe's *whole*
version list to `VersionStrip` (retired per this plan's own comment: "the
unconditional strip call this file used to make below"), so `currentId`
could legitimately match one of the rendered entries — the version being
viewed. After the rebuild, `VersionRow` computes `descendants` and passes
exactly that list, plus the *same* version's own id as `currentId`:

```js
// VersionRow.jsx:126, 338-341
const descendants = descendantVersions(versionsForRecipe(versions, version.recipeId), version.id);
...
<VersionStrip
  versions={descendants}
  recipeId={version.recipeId}
  currentId={version.id}
  ...
```

`descendantVersions(versions, versionId)` is defined to return only
versions transitively descended from `versionId` — by construction it can
never include `versionId` itself (`lineage.js:41-44`). So in the one place
`VersionStrip` is actually rendered in the app, `isCurrent` is always
`false` for every list item; the `.version-strip__item.is-current` CSS
rule and the whole "carried by weight and outline" treatment it documents
can never paint. The component's own unit tests (`VersionStrip.test.jsx`)
still exercise `is-current` because they construct a `versions` array that
deliberately includes `currentId` — proving the component works in
isolation, not that the feature is reachable through the app.

This reads as a prop/feature left over from the "Later versions" rework: it
was meaningful when the strip showed every version of the recipe, and
became vestigial once it was narrowed to "this version's own descendants."

**Fix:** Either drop `currentId`/`is-current` from `VersionStrip` (and its
CSS rule and tests) now that the component only ever renders a version's
descendants, or, if a future caller might reintroduce a list that includes
the current version, leave a comment at the `VersionRow.jsx` call site
recording that `currentId` is currently a no-op there so a future reader
does not assume it does something.

### WR-02: `penReason` is accepted but never read, in `BatchRow.jsx` (unfixed from the prior review) and now also in `VersionStrip.jsx`

**File:** `app/src/ui/BatchRow.jsx:155`, `app/src/ui/VersionStrip.jsx:20`

**Issue:** `BatchRow` still destructures `penReason` (default `null`) and
never reads it anywhere in the file body — this is the same finding the

export function BatchRow({

  ...

`grep -n "penReason" app/src/ui/VersionStrip.jsx` shows only this one

declaration recording that the row-level hint sentence already discharges
D-10 for these two components, so the parameter's presence with no use is
legible as a choice rather than an oversight.

### WR-03: `BatchRow`'s "N later batch(es)" head control can fire with no batch in view, mislabeling the count

**File:** `app/src/ui/BatchRow.jsx:204`, `app/src/ui/BatchRow.jsx:260-269`

**Issue:** The later-batches count is derived by subtracting one for the
batch currently in view:

```js
const laterBatchesCount = batches.length - (openBatch ? 1 : 0);
```

and the head line shows the control whenever that count is positive:

```jsx
{openPen !== 'record' && laterBatchesCount > 0 && (
  <button ...>{`${laterBatchesCount} later batch${laterBatchesCount === 1 ? '' : 'es'}`}</button>
)}
```

`RecipePage.jsx` sets `openBatch` to `null` when the URL's `batchId` does
not match any batch of this version (`RecipePage.jsx:589-594`), a reachable
state the row already renders its own message for ("No batch of this
version has that address."). In that state, `openBatch` is falsy, so the
subtraction does not happen: `laterBatchesCount` becomes the *full*
`batches.length`, and the head line reads e.g. "1 later batch" even though
no batch is in view and nothing is being compared against. "Later" implies
a batch after the one currently shown; with nothing shown, the label no
longer states a true fact. (The disclosure the button opens still works
correctly as a recovery path — each listed batch links to itself via
`isOpenBatch` being falsy for all entries — so this is a wording/logic
mismatch introduced by the new head-line derivation, not a broken control.)
No test in `BatchRow.test.jsx` covers the head line for this
`openBatch: null, batches: [...]` combination (`BatchRow.test.jsx:430`,
`:449` both check only the body message, not the head).

**Fix:** Gate the later-batches control on `openBatch` too (e.g.
`openPen !== 'record' && openBatch && laterBatchesCount > 0`), or compute
the count without assuming a batch is in view (`laterBatchesOpen`'s label
could read "N batches of this version" rather than "N later" when nothing
is currently shown).

### WR-04: The WR-01 attempt-counter regression test in `VersionRow.test.jsx` proves only that the component does not throw

**File:** `app/src/ui/VersionRow.test.jsx:250-281`

**Issue:** The test block titled after the prior review's WR-01 finding
(a second consecutive blocked save must re-fire the version-line focus
effect) asserts:

```js
it('accepts a non-null attempt number without throwing, on a first and then a second distinct attempt', () => {
  const firstAttempt = renderVersionRow({ ..., versionLineBlockedAttempt: 1 });
  expect(firstAttempt).toMatch(/<input[^>]*aria-label="Version"/);
  const secondAttempt = renderVersionRow({ ..., versionLineBlockedAttempt: 2 });
  expect(secondAttempt).toMatch(/<input[^>]*aria-label="Version"/);
});
```

Both assertions only confirm the version-line `<input>` renders at all —
true for any `versionLineBlockedAttempt` value, including a bug that
dropped the re-focus effect entirely. The test's own docstring is candid
about this ("a live DOM focus transition cannot be observed by
renderToStaticMarkup"), so the gap is disclosed, not hidden — but the
practical result is that the WR-01 fix (the `useEffect` keyed on
`versionLineBlockedAttempt` in `VersionRow.jsx:115-118`) has no test in
this codebase that would fail if that `useEffect`'s dependency array or
body regressed (e.g. reverted to keying on a boolean, the exact defect
WR-01 fixed). This is implementation-trivia coverage standing in for
behavioural coverage, for a fix originally raised as a real focus-management
bug.

**Fix:** No renderToStaticMarkup-based fix exists for this gap within the
current test stack. Either accept the documented limitation explicitly
(rename the `it` block to state what it actually proves — "does not throw
across two distinct attempt values" — rather than implying the
re-focus behaviour is exercised), or add the live-DOM assertion (a jsdom/
testing-library-based test, a structural stack decision this project has
not yet made) as a follow-up if the re-focus behaviour needs to be provably
guarded against regression.

## Info

### IN-01: `descendantVersions` has no cycle guard against a corrupted `parentVersionId` chain

**File:** `app/src/domain/lineage.js:41-44`

**Issue:**

```js
export function descendantVersions(versions, versionId) {
  const children = versions.filter((version) => version.parentVersionId === versionId);
  return children.flatMap((child) => [child, ...descendantVersions(versions, child.id)]);
}
```

The recursion has no visited-set guard. Under every path this codebase
actually writes a version through (`createChildVersion`, always given a
fresh `crypto.randomUUID()` id and the *existing* parent's own id), a cycle
cannot form. But the function itself takes an arbitrary `versions` array
with no validation, and nothing prevents a future write path (a bulk
import, a manual store edit, a future migration) from producing a
`parentVersionId` cycle; if one ever existed, this function would recurse
until a stack overflow rather than degrading. This is speculative — every
current writer maintains the invariant — but the same defensive-comment
discipline this file already uses elsewhere (e.g. `blockedSaveMessage`'s
own doc comment stating what it assumes about `penFields`) is absent here.

**Fix:** Either add a one-line comment recording the invariant this
function relies on ("assumes `versions` carries no `parentVersionId`
cycle — every current writer guarantees this"), or add a `visited` Set
keyed by version id as a cheap guard.
