# Phase 03.3: Code Review Report

**Reviewed:** 2026-09-10
**Depth:** standard
**Files Reviewed:** 26
**Status:** issues_found

## Summary

Reviewed the domain modules backing the FORM2-02 advisories and the six balance
figures, the binder/column stylesheet contracts, and the front-matter/page-order
UI components (Authored, BatchRow, DerivedAdvisories, GraduatedRule,
IngredientTable, Method, RecipePage, VersionRow) plus their test suites.

No Critical-tier defects found: no hardcoded secrets, no `dangerouslySetInnerHTML`,
no `eval`/injection surface, no CSS literal escaping the token system (verified
against binder.test.js/columns.test.js's own greps, which would already fail on
this), no domain module importing React/DOM/the store, no module outside
`store/repository.js` importing `idb`. The token discipline, the "no verdict"
wording discipline, and the presence-over-truthiness dirty-check discipline in
RecipePage.jsx are all followed consistently and are well covered by their tests.

Findings below are Warning/Info tier: a React key-collision risk in Method.jsx's
two read-only target-chip renderers, a dead `penReason` prop in BatchRow.jsx, a
basis-ranking constant duplicated verbatim across three files with no shared
source of truth, an unguarded `Array.prototype.find` in IngredientTable.jsx's
show-changes renderer, and a duplicated row-basis reducer with no correctness
issue but a real drift risk paired with the finding above.

## Warnings

### WR-01: `target.label` used as the React key for target chips in two read-only render paths, inconsistent with the pen's own index keys

**File:** `app/src/ui/Method.jsx:695`, `app/src/ui/Method.jsx:755`

**Issue:** In the `isShowingChanges` branch (line 695) and the plain-reading
branch (line 755) of `Method`, each target chip is keyed by `target.label`:

```js
{step.targets.map((target, index) => {
  const targetDiff = stepDiff.targets[index];
  return (
    <span className="target-chip" key={target.label}>
```

`StepPenBody` — the developing-mode renderer for the same list, in both its
open and closed forms (lines 179 and 373) — keys the identical list by `index`
instead:

```js
{draftStep.targets.map((target, index) => {
  const targetDiff = stepDiff.targets[index];
  return (
    <span className="target-chip" key={index}>
```

Nothing in the target-chip shape (`{ label, value }`, freely editable in the
pen via `target-chip__label-field`) enforces unique labels within a step's own
`targets` array. If two targets in the same step ever share a label — plausible
once a maker can freely retype a label, or with future seed data — React would
see two list items with the same key. React's reconciliation would then treat
them as the same element across renders, which can silently misattribute a
struck "was X" comparison (`targetDiff?.changed`) to the wrong chip, or carry
stale DOM state across a reorder. This is exactly the kind of rendering
class of bug `key={index}` in `StepPenBody` was presumably chosen to avoid, but
that fix was applied inconsistently — only to the pen's own renderer, not to
the two read-only renderers that show the same data.

**Fix:** Key both read-only target-chip renderers by `index`, matching
`StepPenBody`:

```js
<span className="target-chip" key={index}>
```

### WR-02: `penReason` prop in `BatchRow` is accepted but never read

**File:** `app/src/ui/BatchRow.jsx:134`

**Issue:** `BatchRow` destructures a `penReason` prop (default `null`) in its
parameter list:

```js
export function BatchRow({
  ...
  openPen = null,
  penReason = null,
  penSaveDisabled = false,
  ...
```

`grep -n "penReason" app/src/ui/BatchRow.jsx` shows this is the only
occurrence in the file — the value is never rendered, never passed to a
child, and never used in a condition. Compare `VersionRow.jsx`, which receives
the identical prop from `RecipePage` and threads it into `VersionStrip`
(`<VersionStrip ... penReason={penReason} />`, `VersionRow.jsx:184`) so the
version list can state why its links are suppressed while a pen is open.
`BatchRow`'s own batch list suppresses its links under the same condition
(`isOpenBatch || openPen ? label : <Link>...`, `BatchRow.jsx:413`) but states
no reason at all — even though the very prop meant to carry that reason
(per `RecipePage.jsx:473`'s comment: "every control that disables while a pen
is open reads openPen/penReason from here") is sitting right there, unused.
This reads as either dead code left over from a refactor, or an incomplete
wiring of D-10's "a disabled control states its reason, never only appears
dim" requirement for the batch list's own suppressed links.

**Fix:** Either wire `penReason` into the batch list's suppressed-link state
(mirroring `VersionStrip`'s use of the same prop), or remove the now-unused
parameter from `BatchRow`'s signature and its one call site in
`RecipePage.jsx:1168`.

### WR-03: The basis-ranking order (`stated < derived < estimated < inherited`) is defined three times, with no shared source of truth

**File:** `app/src/domain/composition.js:67`, `app/src/domain/figures.js:86`, `app/src/ui/IngredientTable.jsx:49`

**Issue:** The same four-value ranking is declared independently in three
places:

```js
// composition.js:67
const BASIS_RANK = { stated: 0, derived: 1, estimated: 2, inherited: 3 };

// figures.js:86
const BASIS_ORDER = ['stated', 'derived', 'estimated', 'inherited'];

// IngredientTable.jsx:49
const BASIS_ORDER = ['stated', 'derived', 'estimated', 'inherited'];
```

`composition.js`'s `weakestBasis(rows, field)` drives the figures' own basis
line (via `figures.js`'s `weakestBasis`/`worseBasis` reducer), while
`IngredientTable.jsx`'s `weakestRowBasis(row)` (lines 51-59) independently
reimplements the identical rank comparison to decide a row's "Source" column
flag (`estimated`/`unreviewed`/blank). Nothing ties the three declarations
together, so a future change to the ranking — inserting a fifth tier, or
reordering `derived` and `estimated` — made in one file would silently not
propagate to the other two. The failure mode is user-visible: a figure's own
basis line (`FormulationNote`/`GraduatedRule`) could then disagree with the
"Source" flag the ingredient table prints for the very rows that figure rests
on, which is precisely the kind of cross-region disagreement T-03-30's own
"never disagree" discipline (cited elsewhere in this phase, e.g.
`estimatedExposureAdvisory`'s doc comment in `advisories.js`) was written to
prevent for other derived facts.

**Fix:** Extract one shared `BASIS_ORDER`/rank helper (e.g. into
`domain/composition.js`, already the home of `weakestBasis`) and have
`figures.js` and `IngredientTable.jsx` import it rather than each declaring
their own copy.

## Info

### IN-01: `renderShowChangesEntry` looks up `rowDiff` with no fallback for a missing entry

**File:** `app/src/ui/IngredientTable.jsx:461`

**Issue:**

```js
function renderShowChangesEntry(row, portion, portionIndex) {
  const rowDiff = diff.rows.find((entry) => entry.id === row.id);
  ...
  <td className="ingredient-table__col-name">
    {rowDiff.removed ? <span className="struck-value">{row.ingredientName}</span> : row.ingredientName}
```

If `diff.rows` (produced by `buildDiff`, outside this review's scope) were
ever missing an entry for a row present in `rows`, `rowDiff` would be
`undefined` and the very next line (`rowDiff.removed`) would throw a
`TypeError` rather than degrading gracefully — there is no equivalent of the
`?? null`/blank-fallback discipline this file otherwise applies consistently
(e.g. `AsMadeCell`, `GramsCell`). This is speculative — it depends on a
guarantee made by `diff.js`, which is outside this review's file list — but
worth a defensive check or an explicit comment recording the invariant this
function relies on, the same way `formatPortionLine`/`DiffGramsCell`'s own
comments record theirs.

**Fix:** Either add a one-line comment stating the invariant ("every row in
`rows` has a matching entry in `diff.rows` by construction of `buildDiff`"),
or guard with `if (!rowDiff) return null;`/an equivalent fallback.

### IN-02: `weakestRowBasis` in `IngredientTable.jsx` duplicates the reduction shape of `composition.js`'s `weakestBasis`, at a different granularity

**File:** `app/src/ui/IngredientTable.jsx:51-59`

**Issue:** `weakestRowBasis(row)` iterates a single row's composition fields
to find its own worst basis, functionally parallel to `composition.js`'s
`weakestBasis(rows, field)` (which iterates rows for one field). The two are
not strictly redundant — one is per-row-across-fields, the other is
per-field-across-rows — but they duplicate the same "rank each candidate,
keep the worst" loop shape and (per WR-03 above) the same ranking table. Once
WR-03 is fixed by extracting a shared rank helper, consider whether this
row-level reducer can also share the same underlying comparison function
rather than re-deriving it.

**Fix:** No standalone change required; addressed together with WR-03's
extraction.
