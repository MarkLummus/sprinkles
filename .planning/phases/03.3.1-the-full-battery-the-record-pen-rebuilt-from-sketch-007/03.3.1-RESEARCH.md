## Summary

This phase is an in-repo rebuild against a fully settled design. The design input (sketch 007, variant A) is packaged in a self-sufficient structural contract — `.claude/skills/sketch-findings-sprinkles/references/batch-record-tasting-battery-structure.md` — whose every label, option, status string, order, number, and lifecycle rule is byte-identical to the verified sketch HTML. The research here is therefore not about *what to build* (the contract owns that) but about the **distance between the current code and the battery**, the **one-save revision** Mark added in the discussion (D-01–D-04 supersede the contract's save-pair sections), and the **store-shape reset** (D-09) that carries it. Everything was verified by reading the contract, the findings file, the surface brief, all prior CONTEXT files' referenced decisions, and every source file the rebuild touches, in full, this session.

The current code diverges from the battery in nine substantive ways: (1) the tasting axis control is nine half-stops on behavioural anchors, not five whole goldilocks stops with the core/declared split; (2) the tasting pen is a separate pen state (`tastingDraft`, `openPen === 'tasting'`) on an already-saved batch, not a section hidden inside the one record pen; (3) saves are `createBatch` + `addTasting` + `recordAmendment` as three distinct domain functions and UI paths, not one save repeated; (4) the churn battery lacks four of its six fields (churn duration, exit consistency, airiness, tempering) and carries two retired ones (`overrunPercent`, and `comeUpMinutes`/`drawTempC` under old labels); (5) the tasting battery lacks defects, the declared flaw, melt style, and the note-before-texture order; (6) numeric fields are native `type="number"` with silent `toNumberOrNull` coercion, not the contract's text-mode fields with stay-in-place inline errors; (7) the amendment list (`amendedAt[]`) is not the single `changed` date (D-04); (8) the seed version declares `Olive oil character` and `Bitterness` as free axes with authored anchors — the battery needs the fixed six-axis table, the declared pair (Body, Oil), and Bitter as the declared flaw toggle; (9) the read view shows old cells and no summary line. Each divergence has a verified citation below.

The research's most important planning facts: **the contract's save matrix, its `#churn-saves`-only-while-tasting-open rule, and the "Save batch & tasting" state-based label are superseded by D-01–D-04** — building them byte-for-byte would violate the phase's own decisions; **Tempering is a tasting field, not a churn field** (the contract's "Where sources disagree (HTML wins)" § 1 overrides D-10's field-grouping wording); and **the seed rewrite (both data files, first task, Mark reviews before execution continues — D-08) must also change the version's declared-axes model**, which D-07's mapping implies but does not spell out. No new packages, no external services, no new tools: every dependency is installed and the 735-test suite passes today.

**Primary recommendation:** Plan this as a vertical slice — reset the store shape first (D-09: DB_VERSION bump, drop/recreate, narrowed validator, rewritten seeds), then rebuild the pen and read view against the contract section by section, with the one-save model (D-01–D-04) built where the contract's save matrix sits; keep every task citing the contract by section name; verify in the browser at real widths.

## User Constraints (from CONTEXT.md)

### The one-save model (revises sketch 007's decoupled saves)

- **D-01:** The record pen has **one save action with two identical ceremonies**: Cancel | **Save batch** at the **end of the record** — after the tasting section when it is open, after the churn section when it is not, just above the shared Next time — and Cancel | **Save batch** at the **foot**, with **Add tasting** beside the foot set while the tasting section is absent. The two ceremonies are **visually identical regardless of position on the page** — same markup, same treatment, differing only in placement (Mark's explicit call). Both Cancels discard the whole pen draft (D-24); identical controls, so the carried P3 "name the two Cancels' scopes" resolves itself. The imprint ceremony stays retired for this pen per the brief's 2026-09-12 revision — with the tasting open the page holds two Cancel | Save sets, never three (Mark: "3 save/cancel button sets on the page with potentially different meaning. that's wrong.").
- **D-02:** **What a save persists is everything the record currently holds.** Mark's framing: "saving a churn and saving a tasting are the same action, one being more complete than the other." Pressing Save with the tasting section open but **empty persists the churn only** — no empty tasting record is manufactured (his earlier disable-the-button idea dissolved with the model). The labels "Save batch & tasting" (state-based) and the sketch's save matrix, including `#churn-saves` rendered only while the tasting section is open, are **retired**. The content-sniffing ban survives as: the label never changes with what is typed; the one label is true at every completeness.
- **D-03:** **A single tasting per churn** — a batch carries zero or one tasting. "Add tasting" is offered on the saved record only while no tasting exists; once one exists, **Correct reopens the same pen with everything editable**, tasting fields in place — one door, same Save. This overturns the brief's binding "a batch is one churn section plus zero or more tastings" (now zero or one) and "adding a tasting is not an amendment" (completing the record is the same save).
- **D-04:** **The record's dates read: churned, tasted, changed — and only the latest change shows** (Mark: "the important dates for a version are: created, churned, tasted, corrected (only the last one)", renaming corrected → changed). Every save after the first dates the record's `changed` value, replacing the amendment list; the batch list's small print reads "changed 5 Aug 2026" (was "amended"). The churn date stays the record's name; an absent tasted date reads "date unknown".
- **D-05:** **The churn date is required — the one deliberate exception to no-required-fields.** The batch's churn date is its name and the version line carries the latest churn date, so Save batch on a blank pen (or any pen without a churn date) refuses in words: **press-to-block per 03.1 D-21** — Save stays enabled, pressing shows a sentence beside both save sets and moves focus to the churn date (working sentence: "Enter the date you churned."; exact wording at planner discretion within the plain-words rule). Mark chose this over "date unknown" for a date-less batch.

### The one-save model (D-01–D-04) — what replaces the contract's save matrix

The contract's "Save and save-pair matrix" is **superseded by D-01–D-04** (D-06 says so explicitly). What the plan builds instead:

- **One save action, two identical ceremonies.** Both render the same component with the same label ("Save batch") and the same behaviour. Ceremony A sits at the end of the record — after the tasting section when open, after the churn section when not, just above the shared Next time. Ceremony B sits at the foot; while the tasting section is absent, "Add tasting" stands beside it.
- **What a save persists:** everything the record currently holds (D-02). Tasting section open but empty → churn only; no empty tasting record manufactured. Section absent → churn only. Section open with ink → churn + tasting.
- **The save handler is one handler.** Its branch is not "which button" but "which record operation": a fresh recording creates (`createBatch`-shaped, now assembling the optional tasting too); Correct on an existing batch completes the same record (the `recordAmendment`/`addTasting` split is retired — D-03 explicitly overturns "adding a tasting is not an amendment", which was a binding Phase 2 decision). Every save after the first stamps `changed` (D-04).
- **No save gate on completeness.** The tasting pen's `isTastingSaveable` gate and its hint ("Write words or mark at least one axis to save.") are retired with the gate — the only block is the churn date (D-05). Verified current state: [VERIFIED: app/src/ui/RecipePage.jsx:494-498]

```js
// Source: RecipePage.jsx lines 494-498, the gate D-01/D-02 retire:

    openPen === 'tasting' && tastingDraft
      ? !isTastingSaveable({ words: tastingDraft.words, marks: tastingDraft.marks })
      : false;
```

- **The tasting pen state retires.** `tastingDraft`, `openPen === 'tasting'`, `handleStartTasting/handleSaveTasting/handleCancelTasting`, `handleUseAsExpectedShortcut` (the removed shortcut — its only render is in the retired tasting ceremony [VERIFIED: app/src/ui/BatchRow.jsx:230-232]), `isTastingDraftDirty`, `derivePenState`'s tasting branch ([VERIFIED: app/src/ui/RecipePage.jsx:224-226]), and `PenFoot`'s tasting branch all collapse into the record pen. `derivePenState`'s pens become `plan` / `record` / `amend` (amend now meaning "Correct reopens everything, tasting in place" per D-03).

The battery replaces this model: six fixed axes with sketch-fixed anchors, the declared pair being Body + Oil for the working case (brief § 3: "the recipe-declared pair — Density/body, Oil character"), and **Bitter is not an axis at all** — it is the declared-flaw toggle trailing the defects row ("Bitter · declared", full aria-label "Declared for this recipe: Bitter") [CITED: contract "Controls spec"]. So the rewritten `olive-oil.js` must declare the battery's pair and the flaw, and `batch.snapshot.declaredAxes` (structuredClone of it) carries whatever shape the planner chooses — the snapshot validator (`validateDeclaredAxis`) changes with it. Anchors authored on the version (02-CONTEXT D-15) are superseded by the sketch's fixed anchor words for these six axes; the goldilocks-vs-descriptive-anchors question stays closed unless Mark reopens it.

### Validation and the measured fields

The contract's numeric rules, verbatim [CITED: contract "Controls spec", lines 158-168]:

- Non-date inputs carry `inputMode="decimal"`. Blank is always allowed.
- Decimal point and comma both accepted; a Unicode minus (−) is normalized to ASCII; negatives are rejected except on °C fields (a field is a temperature when its label's text includes "°C" — "Out of machine" and "Tasting temperature").
- Malformed values stay in place, marked `aria-invalid`, with a `.field-error` line appended inside the field's label and wired by `aria-describedby`; focus moves to the first invalid field; the status reads "Check the marked measurements. Your entries have been kept."
- The two error strings, verbatim: "Enter a temperature, such as −6, or leave blank." for °C fields; "Enter zero or a positive number, or leave blank." for all other numeric fields.
- Validation scope follows the save pressed: the churn row's save validates the churn section alone; the footer save validates the whole pen.

The last bullet describes the two-save sketch; under D-01's identical saves both presses are the same action and the natural reading is both validate everything the record holds (see Assumptions A5). Implement the °C detection by **field metadata** (a `signed: true` flag on the field config), not by sniffing rendered label text — the contract's rule names which fields are temperatures; the mechanism is the planner's.

This supersedes the current coercion pattern: `toNumberOrNull` silently converts a non-finite raw string to `null` [VERIFIED: app/src/ui/RecipePage.jsx:235-239], which would make a typo vanish as "unknown". The battery's malformed value is never silently dropped — it stays, it blocks the save with the contract's sentence, and it keeps the maker's characters in the field. A new pure domain function (a `parseMeasuredDraft(raw, { signed })` shaped like `parseGramsDraft`) is the right home; do not reuse `parseGramsDraft` — it rejects `.5`, `45.`, and accepts nothing the battery's looser measured rule must accept (brief § 7 records exactly why the two predicates must not be merged).

### Feedback, undo, and live regions

Two live regions: the tasting-status beside the action in the tasting head, and form-status at the foot — both `role="status"`, `aria-live="polite"` [CITED: contract "Feedback and undo lifecycle"]. Status strings, verbatim, with targets [CITED: contract lines 199-210]:

- "Nothing recorded to clear." → tasting-status (empty tasting, always-visible mode — a comparison mode that is NOT built; see Pitfall 6)
- "Tasting removed." → form-status (empty tasting, hidden mode; collapses, focus → Add tasting, no undo)
- "Tasting removed. You can undo this." → form-status (data, hidden mode; focus → Add tasting, undo exists)
- "Tasting cleared. You can undo this." → tasting-status (data, visible mode — not built)
- "Tasting restored." → tasting-status, after undo
- "{Axis name} cleared." → form-status, from the per-axis Clear control
- "Check the marked measurements. Your entries have been kept." → form-status, on invalid measurements
- Plus D-05's blocked-date sentence beside both save sets (working words: "Enter the date you churned.")

Removal paths in the built (hidden) mode: empty removal → "Tasting removed." (no undo, section collapses, focus Add tasting); data removal → "Tasting removed. You can undo this." (undo exists). Toasts self-clear after five seconds, guarded so the timer never wipes a newer message (it clears only if the text is still the message it wrote); the per-axis Clear and validation announcements write persistently. Undo placement: tasting head slot while the section is visible, footer slot (trailing Add tasting) when absent — a real DOM move. Retirement scope: any edit inside the tasting body retires a pending undo; never a churn-section edit or a Next-time edit. Adding a tasting writes **no announcement** — the section opening and focus landing on the Tasted date are the evidence; clear the status line instead [CITED: contract, all above].

**React realization of the carried edges:** holding the undo payload as React state (the removed tasting's values) rather than captured element references makes the undo survive the axes re-render a breakpoint crossing triggers — the carried "data-based undo that survives resize" P3 is liftable in this phase (it is listed under the contract's "Deferred to the phase plan (recorded, not built)"). The 5-second guarded self-clear is a `useEffect` timer with a ref-guard comparing the current message text.

The contract requires **two DOM orders, one per arrangement** [CITED: contract "Keyboard and tab order"]: row-major flat for the 3-column desktop (Hardness, Scoopability, Body, Smoothness, Sweetness, Oil — tab order follows the eye; the hairline draws the core/declared boundary between columns 2 and 3); core-then-declared grouped containers when stacked (Hardness, Scoopability, Smoothness, Sweetness, then Body, Oil). ## Common Pitfalls

### Pitfall 1: Building the sketch's superseded save model
**What goes wrong:** The contract's "Save and save-pair matrix", the `#churn-saves`-only-while-tasting-open rule, and the "Save batch & tasting" state-based footer label are byte-accurate to the sketch HTML — but D-01–D-04 retire them (D-06 names the supersession). An executor following the contract literally builds three save sets with different meanings — exactly what Mark called wrong.
**Why it happens:** The contract is the per-task citation source and is otherwise byte-authoritative; the save sections are the one place a *later* decision overrides it.
**How to avoid:** The plan must carry the D-01–D-04 text into the save tasks themselves and state explicitly that the contract's save matrix and `#churn-saves` rows are NOT built; the contract's "How to cite this contract" line ("supersedes the sketch HTML as the reading surface") needs the companion note that D-01–D-04 supersede the contract on save-pair structure only.
**Warning signs:** Any task text quoting "Save batch & tasting", `#churn-saves`, or the save matrix's Undo-placement rows as build targets.

### Pitfall 2: Tempering's section — the contract wins over D-10's grouping
**What goes wrong:** D-10 lists tempering among "the churn-phase fields"; the contract's field list puts it in the tasting section. A planner following D-10's wording renders Tempering in the churn section — contradicting the design Mark verified in the browser.
**Why it happens:** The contract's "Where sources disagree (HTML wins)" § 1 says exactly this: "the settled HTML renders Tempering (unit min) in the TASTING field-row, between Tasted and Tasting temperature. The HTML governs: Tempering is a tasting field." D-10's list is about *stored facts existing*, not UI placement, but its grouping language misleads.
**How to avoid:** Store tempering with the tasting-side fields (planner's field-name discretion) and render it in the tasting field-row per the contract. The seed value is blank either way (D-07), so no seed impact.
**Warning signs:** A churn-section task carrying a "Tempering, min" field.

### Pitfall 3: The declared-axes model mismatch in the seed rewrite
**What goes wrong:** The seed version declares `Olive oil character` and `Bitterness` as free axes with authored anchors; the battery needs the fixed six-axis table with the declared pair (Body, Oil) and Bitter as the declared-flaw toggle. D-07 maps the batch's marks but does not name the version's new declaration; a plan that rewrites only `batch-2026-08-02.js` leaves the version (and every batch's snapshot) declaring axes the battery does not render.
**Why it happens:** D-07's mapping is about values, not the declaration model; the model change is implied by the battery's fixed AXES table + the brief's "recipe-declared pair — Density/body, Oil character".
**How to avoid:** The first task (D-08's seed rewrite, `data/olive-oil.js` included by name) rewrites the version's declared data to the battery's model — the declared pair per the brief, the flaw Bitter — and bumps whatever schema numbers the shape change needs; Mark reviews it (D-08). `axesForBatch`/snapshot validator change in the same task family.
**Warning signs:** `axesForBatch` still reading free `declaredAxes` entries whose names ("Olive oil character", "Bitterness") match nothing in the battery's AXES table.

### Pitfall 4: Silently coercing malformed numerics
**What goes wrong:** Reusing `toNumberOrNull` (Number(raw) → null on non-finite) for the battery fields makes a typo read "unknown" forever — the contract requires stay-in-place, `aria-invalid`, a `.field-error` line, `aria-describedby`, focus on the first invalid field, and the "Check the marked measurements..." status.
**Why it happens:** The function is right there in RecipePage and the draft fields look like the old ones.
**How to avoid:** A new pure domain parser for measured drafts (decimal/comma, minus normalisation, negative rejection except °C via field metadata); the save path runs it, keeps the raw string in the field on failure, and blocks. The plan pen's `parseGramsDraft` stays untouched for its own column (the unreadable-as-made question stays open — do not broaden or narrow it here).
**Warning signs:** A battery field whose malformed input produces a stored `null` without any words on screen.

### Pitfall 5: Hand-rolling a focus manager for the stop groups
**What goes wrong:** Building buttons with `role="radio"` plus a custom roving-focus manager reimplements what native radios give free (arrows, one tab stop), adds bugs, and contradicts the codebase's recorded decision in `AxisMark.jsx`'s header comment.
**How to avoid:** Native radio inputs as the base; add the per-stop `aria-label "{n}: {word}"` and click-again-clears; verify Home/End in Chrome and add a minimal keydown only if the browser lacks it. Same approach for the three segmented controls (the codebase already restyles native controls — the `select.ink-field` chevron precedent).
**Warning signs:** Any keydown handler containing an arrow-key focus index.

### Pitfall 6: Building the sketch's always-visible tasting mode
**What goes wrong:** The contract's removal matrix has four rows; two of them ("Nothing recorded to clear.", "Tasting cleared. You can undo this.") belong to the always-visible mode, which the settled defaults explicitly exclude ("Always-visible stays a comparison mode, not the default" — a sketch comparison device, never to be built).
**How to avoid:** Build only the hidden-mode paths: "Tasting removed." (empty) and "Tasting removed. You can undo this." (data), with the restore path "Tasting restored." The Clear/Remove control reads "Remove tasting" (hidden mode) only.
**Warning signs:** A "Clear tasting" control or an always-visible tasting section in the pen.

### Pitfall 7: Zero-or-one tasting ripples
**What goes wrong:** With D-03's single tasting, `sortedTastings`, `hasTasting`, and the plural machinery keep compiling but mislead: BatchRow's later-batches meta builds "tasted once/twice/N times" wording [VERIFIED: app/src/ui/BatchRow.jsx:504-508]; `addTasting` appends; the read view maps tastings. A one-element list preserved by inertia reads as "more coming".
**How to avoid:** Decide the storage shape (single object `null | tasting` or a list of at most one — planner discretion per D-10) and reshape every reader deliberately; the "tasted twice" wording is retired (a batch is tasted zero or one times); the read view's tasted date is the one tasting's.
**Warning signs:** Any UI string that can read "twice".

### Pitfall 8: matchMedia under emulation + two DOM orders
**What goes wrong:** Emulated viewport changes may not fire the `matchMedia` change listener, so the axes never re-render between arrangements under emulation — the carried caveat. And the two DOM orders are a real re-render, not a CSS reorder (one DOM order cannot serve both tab orders).
**How to avoid:** Verify breakpoint behaviour at real window widths in the browser (the carried caveat names this); render the two arrangements conditionally from one `matchMedia`-derived state; keep marks keyed by axis key in page state so they survive.
**Warning signs:** Tab order reading Hardness→Scoopability→Smoothness→Sweetness→Body→Oil in the desktop 3-column arrangement (that is the stacked order, not the row-major one).

### Pitfall 9: The CSS contract suites
**What goes wrong:** The battery's CSS is heavy in hard numbers (186px/216px tracks, 34×32/40×44 stops, 640px pen, 760/768/600 breakpoints, `calc(200% / 3)` rule position). Three style suites (`binder.test.js`, `columns.test.js`, `cross-cutting.test.js`) read `app.css`/`tokens.css` as text through `css-source.js`, whose parser "handles exactly one level of nesting — a top-level @media block" and **throws** on nested at-rules or any other at-rule keyword (`assertNoAtRules`) [VERIFIED: app/src/styles/css-source.js:16-21, 57-73].
**How to avoid:** Every visual value through `tokens.css` (the tokens-only convention); the ladder lands as multiple top-level `@media` blocks (never nested); px literals where the existing touch tokens set the precedent (resolved by `resolveTokenPx`). Run `npm --prefix app test` after each CSS task.
**Warning signs:** A new `@container`, `@supports`, or an `@media` inside an `@media`.

### Pitfall 10: Preserving retired decisions for consistency's sake
**What goes wrong:** Three recorded prior decisions are deliberately overturned by this phase, and an executor (or planner) honoring them for consistency produces the wrong build: (a) Phase 2's "recordAmendment and addTasting are kept as two distinct domain functions with two distinct UI call sites (never a single patch-shaped updater)" — superseded by D-02/D-03's one-save model; (b) the tasting save gate `isTastingSaveable` and its hint — superseded by D-02 (no completeness gate); (c) the "As expected, nothing to note" shortcut control — removed 2026-09-12, its only render site is in the retired tasting ceremony.
**How to avoid:** The plan names each retired thing and its replacement; the STATE.md carry-list is read as history, not as binding here.
**Warning signs:** A plan task that "keeps the two functions to preserve the Phase 2 decision".

### Pitfall 11: Snapshot immutability with the new fields
**What goes wrong:** The battery extends the batch, and the snapshot must still be taken once and never retaken — but the snapshot now must carry whatever the read view needs about the declared pair and flaw even after the version is superseded (BATCH2-01; "the record reads unchanged when the version is superseded").
**How to avoid:** However the declared model is stored, it rides the existing `structuredClone`-at-authoring-time pattern into the snapshot; the read view reads only the snapshot, never the live version's axes.
**Warning signs:** `axesForBatch(batch)` reaching for a live version record (the existing comment calls this "exactly the drift this phase exists to prevent" [VERIFIED: app/src/domain/axes.js:27-31]).

### 2. Measured draft parsing (pure, node-env testable)

```js
// New domain function, shaped like parseGramsDraft but with the battery's rules.
// NOT parseGramsDraft: that strict predicate rejects ".5" and "45." and serves the
// plan pen's grams rule with a blocking sentence (brief § 7 records why not to merge).
export function parseMeasuredDraft(raw, { signed = false } = {}) {
  if (raw == null || raw === '') return { ok: true, value: null };        // blank always allowed
  const normalized = raw.replace(/−/g, '-').replace(/,/g, '.').trim();    // Unicode minus, comma
  if (!/^-?\d*\.?\d*$/.test(normalized) || normalized === '' || normalized === '-') {
    return { ok: false, value: null };                                    // stays in place, .field-error
  }
  const value = Number(normalized);
  if (!Number.isFinite(value)) return { ok: false, value: null };
  if (!signed && value < 0) return { ok: false, value: null };            // negatives only on °C fields
  return { ok: true, value };
}
```

The two error strings come from the field config, verbatim (see Architecture Patterns). °C fields are known by metadata (`signed: true` on "Out of machine" and "Tasting temperature"), not by sniffing label text.

```js
    setBlockedDateMessage('Enter the date you churned.');  // wording: planner discretion (plain words)
    focusChurnDate();                                      // beside BOTH ceremonies (D-05)
    return;
  }
  const now = new Date().toISOString();
  const tasting = tastingOpen && tastingHasInk(draft) ? buildTastingFields(draft, parsed) : null;
  const record = amendingBatchId
    ? completeRecord(batchBeingAmended, buildChurnFields(draft, parsed), tasting, { now }) // stamps changed
    : createBatch(version, buildChurnFields(draft, parsed), buildTastingFields(draft, parsed),
        { id: crypto.randomUUID(), now });                 // first save: changed starts null/absent
  repository.saveBatch(record).then(/* return to reading, focus back to opener (D-27) */);
}
```

Naming of `createBatch`/`completeRecord` (or whatever replaces `recordAmendment`+`addTasting`) is planner discretion; the contract with the domain is: one deterministic entry per operation, impure inputs supplied, snapshot never retaken, `changed` dated on every save after the first (D-04).

## Open Questions

1. **Does saving a Correct-pen whose tasting section was removed delete the stored tasting?**
   - What we know: D-02 says a save persists everything the record currently holds; the contract's removal matrix is pen-session behaviour; nothing names the persisted outcome for a batch that already has a tasting.
   - What's unclear: keep-on-removal vs delete-on-removal for the stored tasting.
   - Recommendation: build the D-02-consistent reading (section absent on save → no tasting stored), note it in the plan, and surface it at the D-08 checkpoint or end-of-phase UAT; it is one test either way.
2. **The read-view summary line's exact words per stop.**
   - What we know: the line belongs to the batch read view ("Soft (2) · grainy · bitter" is the recorded example); the sketch has no saved/read state, so nothing specifies which word stands for stops 2 and 4.
   - What's unclear: "leaning soft" (the contract's stop word) vs "soft" (the anchor) for the line's tokens.
   - Recommendation: planner proposes wording within the plain-words rule (D11); flag for Mark's eyes at UAT. The marks themselves read with the contract's five stop words.
3. **Validation order when both the churn date is blank and a measurement is malformed.**
   - What we know: both are press-to-block with a sentence + a focus target; the contract fixes neither priority.
   - Recommendation: validate measurements first (field-level, contract sentences), then the churn date (D-05) — or the reverse; pick one, test it, keep both ceremonies identical.
4. **Escape with the tasting section open but empty.**
   - What we know: Escape closes only an untouched pen; adding the section writes no ink. Whether Escape should close the pen or just collapse the section is unspecified.
   - Recommendation: treat the open-but-empty section as no ink (Escape closes the pen; Cancel likewise) — simplest, matches "adding writes no announcement/nothing"; note it for UAT.
