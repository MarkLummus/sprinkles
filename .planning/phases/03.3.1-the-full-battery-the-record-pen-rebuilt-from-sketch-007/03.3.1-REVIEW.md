# Phase 03.3.1: Code Review Report

**Reviewed:** 2026-09-13T18:07:52Z
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

The domain layer (`axes.js`, `batch.js`, `battery.js`, `lineage.js`) is careful and well covered: presence-over-truthiness discipline is applied consistently, `structuredClone` is used correctly at every snapshot boundary, and the test suites exercise the documented edge cases (written zeros, `__proto__` poisoning, blank-vs-absent) directly against the invariants the code comments claim. `transfer.js`'s prototype-pollution guard is sound and its own tests prove it.

The one substantial defect found is in the two shared radio-based controls (`AxisMark.jsx`, `Segmented.jsx`): both wire the actual state-changing callback exclusively through the radio's `onClick`, leaving `onChange` a no-op. Native grouped radios change their `checked` state (and fire a `change` event, not a `click` event) on arrow-key navigation, so a maker who selects a stop or a segmented option purely by arrow-key navigation — the primary keyboard interaction pattern for a radiogroup — never has that selection reach the record's draft state. This directly contradicts the component's own header comment, which claims arrow-key movement between stops is "almost all" free from the native mechanism.

Beyond that, the review found a handful of smaller robustness/consistency gaps: `transfer.js`'s import gate does not validate several fields (`versionLabel`, `headnote`, a method step's `leadIn`/`instruction`/`targets`) it otherwise treats as required elsewhere in the same file, `RecipePage.jsx` computes `now` once for a save and then throws it away for the non-amend path, and every generic field-change handler in the record pen wipes the *entire* `fieldErrors` map rather than just the field being edited, which can silently hide an already-shown validation error for an untouched sibling field.

## Critical Issues

### CR-01: Arrow-key navigation in AxisMark and Segmented never updates application state

**File:** `app/src/ui/AxisMark.jsx:79-91`, `app/src/ui/Segmented.jsx:21-28`
**Issue:**
Both controls render a native grouped `<input type="radio">` per option, with a real state-changing handler wired only to `onClick`, and a no-op `onChange`:

```jsx
// AxisMark.jsx
<input
  type="radio"
  name={groupName}
  value={stop}
  checked={value === stop}
  ...
  onChange={() => {}}
  onClick={() => handleStopClick(stop)}
/>
```

```jsx
// Segmented.jsx
<input
  type="radio"
  name={groupName}
  value={option}
  checked={value === option}
  onChange={() => {}}
  onClick={() => onChange(value === option ? null : option)}
/>
```

This is deliberate for one reason — a native radio's `click` does not re-fire for a re-click on an already-checked option, which is what the "click-again-clears" behavior relies on. But it has a side effect the header comments do not account for: **arrow-key navigation inside a native radiogroup changes the focused/checked radio and fires a `change` event, not a `click` event.** `AxisMark.jsx`'s own `handleStopsKeyDown` explicitly intercepts only `Home`/`End` (`if (event.key !== 'Home' && event.key !== 'End') return;`) — every other key, including the arrow keys that natively drive radiogroup selection, is left to native behavior plus this no-op `onChange`.

The practical effect: a maker who tabs into the five-stop track and presses the arrow keys to choose a stop (the standard, expected way to operate a `role="group"` of radios, and the one AxisMark's own comment claims works "almost for free") never calls `onChange`/`onClear` — `handleChangeRecordMark` in `RecipePage.jsx` is never invoked. The application's `draft.marks` state does not change. Whatever the maker visually lands on via arrow keys is not what gets saved; only a subsequent mouse click (or a fresh Tab-then-Space activation, which fires a real `click`) commits a value. The same defect applies to `Segmented.jsx`'s three controls (Exit consistency, Airiness, Melt style).

This is provable from the code alone — the callback that writes to state is simply never reachable from a `change` event — independent of exactly how React's controlled-input reconciliation behaves on top of it. It silently produces a batch record that does not match what the maker believed they selected via keyboard.

**Fix:** Wire the real update through `onChange` as well (arrow-key navigation always changes `checked` to a genuinely different value, so it can never collide with the click-again-clears case, which only needs to intercept a *re-click of the same, already-checked* option):

```jsx
<input
  type="radio"
  ...
  checked={value === stop}
  onChange={() => handleStopClick(stop)} // arrow-key/keyboard selection now reaches state
  onClick={() => handleStopClick(stop)}  // click-again-clears still handled the same way
/>
```
(Equivalent change in `Segmented.jsx`'s `onChange`.) Verify in a real browser that arrow-key-only selection now persists to the saved record — the existing test suites explicitly disclaim interaction coverage (`renderToStaticMarkup`, no click driver), so this class of bug is invisible to them.

## Warnings

### WR-01: `transfer.js`'s import gate does not validate several fields it treats as required elsewhere

**File:** `app/src/store/transfer.js:106-117` (`validateStep`), `app/src/store/transfer.js:314-362` (`validateVersion`)
**Issue:** `validateStoreFile` is documented as "the only gate before a write" that "collects every error found" so "a malformed file is refused... never half-applied." `validateRow` checks every field of a row (`id`, `ingredientName`, `portions`, `ingredient.composition`, `removed`), but the sibling `validateStep` checks only `removed` and `uses` — it never checks that `n` is a number, or that `leadIn`/`instruction` are non-empty strings, or that `targets` is well-formed (contrast with `olive-oil.test.js`'s own assertion that "every entry has a non-empty leadIn and a non-empty instruction"). Likewise `validateVersion` never checks `versionLabel` or `headnote` at all, even though both are read directly by the UI (the version-line uniqueness check, the headnote's own `<h1>`).
A crafted or corrupted import file can therefore carry a method step with `leadIn: 123`, `instruction: null`, or `targets: "not an array"`, or a version with no `headnote`/`versionLabel`, and still pass `validateStoreFile` and get written into the store — moving the failure from "import refused with a clear message" to "next visit to that recipe throws or renders garbage."
**Fix:** Extend `validateStep` to check `n` (finite number), `leadIn`/`instruction` (non-empty strings), and `targets` (array of `{label, value}`); extend `validateVersion` to require `versionLabel`/`headnote` as non-empty strings, matching the thoroughness already applied to `validateRow`.

### WR-02: `RecipePage.jsx` computes `now` once, then discards it for the fresh-batch save path

**File:** `app/src/ui/RecipePage.jsx:1247-1265`
**Issue:**
```js
const now = new Date().toISOString();
const churnFields = buildChurnFieldsFromDraft(draft, parsed);
const tasting = draft.tastingOpen && tastingHasInk(draft) ? buildTastingFieldsFromDraft(draft, parsed) : null;

if (amendingBatchId) {
  const batchBeingAmended = batches.find((batch) => batch.id === amendingBatchId);
  const record = completeRecord(batchBeingAmended, churnFields, tasting, { now });   // uses `now`
  ...
}

const record = createBatch(version, churnFields, tasting, { id: crypto.randomUUID(), now: new Date().toISOString() }); // fresh call, ignores `now`
```
`now` is computed up front and used by the amend path, but the fresh-record path calls `new Date().toISOString()` again inline instead of reusing it. This contradicts the surrounding comment's own stated invariant ("the two impure calls — a fresh id, the current instant — run, here, in the one save handler"): there are now two "instant" calls instead of one, and the `now` variable is silently dead code on the create path. Functionally harmless in the overwhelming majority of cases (the two calls are milliseconds apart), but it is a real inconsistency against the file's own documented single-instant contract and an easy place for a future edit to introduce a genuine timestamp mismatch.
**Fix:** Reuse `now` in both branches: `createBatch(version, churnFields, tasting, { id: crypto.randomUUID(), now })`.

### WR-03: The record pen's generic field/segment/as-made/step-change handlers wipe every field error, not just the one being edited

**File:** `app/src/ui/RecipePage.jsx:994-1003` (`handleChangeRecordField`), `:1012-1021` (`handleChangeSegment`), `:1089-1103` (`handleChangeStepChange`), `:1112-1129` (`handleChangeAsMade`)
**Issue:** Every one of these setters calls `setFieldErrors({})` unconditionally, clearing the *entire* `fieldErrors` map on any single field's edit:
```js
function handleChangeRecordField(field, value) {
  setFieldErrors({});
  ...
  setDraft((prev) => ({ ...prev, [field]: value }));
}
```
If a Save attempt reported two malformed measurements (e.g. `outOfMachineTempC` and `meltTestG` both invalid) and the maker fixes only one of them, editing that one field wipes the `aria-invalid`/`field-error` state for the *other*, still-invalid field too — it silently reads as valid again in the UI even though its value has not changed and remains malformed. The mistake is caught again only if the maker attempts Save a second time; until then the interface is misleading about which fields still need attention.
**Fix:** Clear only the error entry for the field actually being edited (`setFieldErrors((prev) => { const next = { ...prev }; delete next[field]; return next; })`), or re-run `parseAllMeasuredFields` against the field just edited and update its own entry.

### WR-04: `BatchRow.jsx`'s recording-mode axes grid reads the live version's `declaredAxes` instead of the batch's own snapshot

**File:** `app/src/ui/BatchRow.jsx:569-575`
**Issue:**
```jsx
<AxesGrid
  axes={axesForBatch({ snapshot: { declaredAxes: version.declaredAxes } })}
  ...
```
`domain/axes.js`'s own `axesForBatch` contract is explicit that a batch's declared-axis pair must be read from `batch.snapshot.declaredAxes` and "from nowhere else — the snapshot is what protects a stored mark from a later change to the recipe's declared pair, and reaching for a live version record here would be exactly the drift this module exists to prevent." This call site does exactly the thing that comment warns against, for both the fresh-record and the amend pen (both render with `mode === 'recording'`). It happens to be safe today only because `saveOverVersion` — the one path that could change `declaredAxes` on an existing version id — is gated off the instant any batch exists (`canSaveOver = batches.length === 0`), so a version with a batch to amend can never have its `declaredAxes` changed afterwards. That invariant is not enforced or asserted anywhere near this call site, so a future change to either `saveOverVersion` or `canSaveOver` could silently reintroduce the exact drift `axesForBatch`'s contract exists to prevent, with no test currently guarding against it.
**Fix:** During amend, read the axes grid from the batch actually being amended (`axesForBatch(batchBeingAmended)`) rather than from `version`, or add an explicit regression test pinning the "a version's declaredAxes cannot change once it has a batch" invariant this shortcut relies on.

## Info

### IN-01: `lineage.js`'s `blockedSaveMessage`/`blockedSaveRowId` each independently run the same row traversal

**File:** `app/src/domain/lineage.js:215-237`
**Issue:** `blockedSaveMessage` and `blockedSaveRowId` are two separate exported functions that both call the internal `findBlockedRow` from scratch. `RecipePage.jsx`'s `buildPenFields` calls both back-to-back on every blocked save, so the same row-by-row/portion-by-portion walk runs twice per blocked attempt. Both are pure functions of the same inputs so they cannot disagree today, but the duplication means a future change to one traversal's early-exit condition (e.g. adding a new kind of block) has two call sites to keep in sync instead of one.
**Fix:** Have one function return `{ message, rowId }` and have the other two exported names delegate to it, or have `buildPenFields` call `findBlockedRow`-shaped logic once and derive both facts from a single result (not required — this is a maintainability note, not a correctness defect).

## Disposition (orchestrator, post-review)

**CR-01 — verified FALSE POSITIVE via live browser testing.** The claim that arrow-key
radiogroup navigation never reaches `onChange`/state (because the real handler lives on
`onClick`, and arrow keys fire `change` not `click`) does not hold in Chrome: per the HTML
Standard's radio-button "activation behavior," a keyboard-driven selection change within a
native radiogroup also queues a `click` event on the newly-selected radio, which the existing
`onClick` handlers already capture. Confirmed by repeatedly pressing arrow keys against the
live app (`AxisMark`'s Hardness track and `Segmented`'s Exit consistency control) at
`http://localhost:5173` and observing the visible state label / checked radio update correctly
on every press, with no click ever issued by the test — only `computer.key`. No code change
made.

**WR-01, WR-02, WR-03, WR-04 — fixed.** See commit `7a89895`
(`fix(03.3.1): apply code review findings WR-01 through WR-04`). WR-01 also gained ten new
`transfer.test.js` cases proving the extended validators both reject the malformed shapes
they previously missed and still accept well-formed ones. WR-03's fix was extended beyond the
review's four named handlers to the other tasting-body setters (`handleChangeRecordMark`,
`handleClearAxisMark`, `handleChangeDefect`, `handleToggleBitter`) sharing the identical
root-cause pattern — none of their fields are ever `BATTERY_FIELDS` keys, so unconditionally
clearing the whole `fieldErrors` map on every one of them was equally destructive of an
unrelated sibling's still-shown error.

**IN-01 — deferred**, per the review's own disposition ("not required — this is a
maintainability note, not a correctness defect").

Full suite: 895/895 passing (10 new); `npm run build` compiles clean.
