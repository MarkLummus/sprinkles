## How the pass was run

1. **Serve.** A throwaway `python3 -m http.server 8787 --directory .planning/sketches` serves the sketch tab; `npm --prefix app run dev` serves the app (note the printed port — Vite's default is 5173, but the pass reads whatever the running instance actually prints). The reference is sketch 007 at `109733d` and sketch 003 at `59f7948` (D-20) — both hashes and the app's merged-main HEAD are recorded in this file's YAML head. The sketches are served from disk with no cache headers, so hard-reload each sketch tab (`Cmd+Shift+R`) once before the first measurement of a session; a stale tab silently measures yesterday's HTML.
2. **One browser tool per width.** `gsd-browser` (Playwright-backed) sets the viewport exactly, including 393 — the 03.3.1-06 precedent found the interactive Chrome window floors around ~500px, so `gsd-browser` is the primary tool for every one of the ten D-16 widths and `claude-in-chrome` is used only for optional interactive re-checks (hover, real Tab-key focus) at 500px and above. Both tabs at a given width are read with the *same* tool in the *same* session, so font rendering and DPR match between them.
3. **Per width, per state**, both tabs are opened at that width. The sketch's state is set by script (the snippets in `03.3.1.1-conformance-probe.js`'s `SKETCH_STATE_SNIPPETS`, sourced from RESEARCH "Setting the sketch's state"). The app is driven by real clicks and typing in English (Record batch → Add tasting for state 1; the same marks and field values for state 2; save and read back for state 3, compared against sketch 003).
4. **Frame equalisation below 784px (Pitfall 9).** Below the width where the sketch's pen stops being capped at 640px, the sketch's `.frame` padding makes its pen narrower than the app's `.batch-margin--pen` at the same viewport unless corrected. The pass calls `equaliseSketchFrame(appPenWidthPx)` from the probe helper — it reads the app pen's measured width, reads the sketch frame's own computed padding, and sets `.frame`'s width so the two pens measure the same — and records that the equalisation ran, in the row for that width.
5. **Never measure sketch 003 with its "full" preset.** `setWidth(0)` writes `width: 100%` and `relayout()` reads it back with `parseInt`, so `parseInt('100%') === 100` and the frame is classed `.narrow` at every real width regardless of the preset chosen (003 lines 510-511). Every state-3 reading sets a real viewport (or one of the numeric presets — 834, 1024, 1280, 1440) and records `.frame`'s measured width and whether it carries the `.narrow` class beside the reading, so a mis-set preset is visible in the record rather than silently invalidating the row.
6. **Measure caption/axis-head lines before AND after a pick (Pitfall 12).** Below 760px every axis head and every segmented caption line reserves 44px whether or not Clear is showing (24px above 760px). Read naively, the app's head growing on first mark could look like a spacing bug; the correct reading is 24-before/24-after (desktop) or 44-before/44-after (narrow) in both tabs. A head that measures 24 before and 44 after IS the bug.
7. **Two open questions the procedure resolves by measurement, not assumption.** At 393, record the pen's full height in both tabs (Open Question 6) — a taller app pen than the sketch is not itself a gap, since the 44px caption-line reserve alone adds roughly 9 × 20px; if Mark objects after seeing the measured number it is a sketch round, not an app fix. At 780px, the sketch's `.row-version` collapse is keyed to a *container* width (760px inside a padded `.front`) while D-15 (and the app) key the same collapse to a *viewport* width (759.98px) — the two disagree by roughly the page's padding, so a 780px divergence on this one element is recorded as container-vs-viewport arithmetic (Open Question 5), not a gap, and Mark decides which number is the intent after seeing it.

**The common cause.** Sketch 007 puts every 44px touch rule inside `@media (max-width: 760px)` (lines 174-182), and the app mirrors it at `759.98px`. Touch sizing is therefore keyed to viewport width rather than pointer type, so a tablet — wide *and* coarse-pointer — takes desktop targets on every control. The candidate revision is to widen the condition to `(max-width: 759.98px), (pointer: coarse)` in the sketch first, then the app follows (D-01). This changes control sizing on every touch device at every width, so it is a design decision for a sketch session, not a patch.

**Measured on Mark's own device (2026-09-15).** The readout from the iPad running Brave (WebKit — iOS/iPadOS requires the system engine, so Brave there renders as Safari does): **viewport 1366 CSS px, DPR 2, `pointer: coarse` true, the `759.98px` block does NOT fire.** That is an iPad Pro 12.9" in landscape. Two consequences sharpen SR-1:

- The device is **wider than the widest width in the D-16 ladder** (1280), so the pass never measured the viewport Mark actually uses.
- **No width threshold can catch it.** A tablet reporting 1366 is wider than most laptops, so any `max-width` chosen for phones will always miss it. `(pointer: coarse)` is the only condition that identifies this device, which makes the candidate revision above the *only* workable one rather than one option among several.

**SR-6 — the empty date field collapses on WebKit (app defect, not sketch-round).** Measured on the same device: an empty `input[type='date']` renders **128 x 6px** — exactly its 2px padding plus 1px border, top and bottom, with zero content height — against a 28.5px text field beside it. The 12px gap is correct; the box is a sliver. A date input *with a value* renders 28.0px, essentially matching, which is why no screenshot of a completed record ever showed it and why 653 Chromium measurements missed it. Cause: WebKit gives a date control no intrinsic height once `appearance: none` strips it; Chromium keeps one. Device-tested fixes: `min-height` restores the box (25px), `line-height` does nothing (the stripped control has no line box). This is an implementation defect, not a design disagreement — the sketch draws both boxes at a normal height — so it is an `app/` fix, not a sketch round.

**Why the pass did not catch it.** The D-16 ladder is 1280, 1180, 1080, 980, 880, 780, 680, 580, 480, 393 — no iPad width (768 / 820 / 834) sits on it, and the pass ran at DPR 1 with no touch emulation. A future ladder should carry at least one tablet width with `hasTouch` set, one DPR 2 reading, a width above 1280 (Mark's own device reports 1366), and an **empty** as well as a filled date field (the "1.5px renders as 1px" fact that retired 1.5px borders is a DPR 1 observation).
