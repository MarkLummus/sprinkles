<decisions_recorded>
1. **The attribute, not a focus manager.** An explicit tabindex of 0 on each stop is the one page-side change WebKit's own source routes past both gates (HTMLAnchorElement.cpp:132-134 and HTMLFormControlElement.cpp:222-223 short-circuit to Element::isKeyboardFocusable when tabindex is set explicitly; WebKit commit 89bf60bf9f relies on exactly this for the chrome-to-page hand-off). No JavaScript: no focus() on mount, no keydown handler, no roving index. A skip link was considered and not taken — it adds a stop and still needs the link gate bypassed to be reachable itself.
2. **Every stop, not only the seven the diagnosis decided.** The two buttons are focusable under KeyboardAccessFull, but only while that value has reached Safari's web process — an environment condition (FKA switched on while Safari was already running) the app cannot control. Giving them the attribute makes them independent of it. The phone arm — the tab row's links, More's summary and the five items inside More — gets it for the same reason, and so the test can honestly say "every".
3. **RailPlace carries it once.** Ten of the nineteen rendered stops come from the one `RailPlace` component; the attribute goes on its NavLink, not on each call site. The other nine stops are authored inline and each gets it there.
4. **The `.shell__place:focus` fallback stays.** With focus now able to arrive, whether WebKit sets :focus-visible for a Tab on iPadOS is still unmeasured — entry from the chrome goes through setInitialFocus with an empty FocusEventData, so it may not. The rule is the ring for when focus does arrive; its comment stops claiming it was ever more than that. Removing it would be a second unmeasured bet.
5. **The record is corrected by a dated note, not a rewrite.** 03.4-09-SUMMARY.md gains one correction section; its frontmatter, key-decisions and coverage blocks stay as written so the history reads as it happened. 03.4-09-PLAN.md is not touched. 03.4-UAT.md belongs to the verifier and is updated on reconciliation, not here.
6. **The truth is split at the Safari boundary.** (a) With focus already in the page, Tab rings every stop in order — the app's own behaviour, assertable on the iPad, and what closes this gap. (b) Tab from Safari's chrome entering the page depends on Safari's closed-source `_webViewCanBecomeFocused:` answer and on when its web process last read the FKA value; it is recorded from the device probe in the verification section below, never asserted.
7. **Scope kept surgical.** shell.test.js's describe title names the round-two debug session; it pins the rule, not the premise, and is left alone. Import feedback (G-03.4-3 half B) stays deferred; the overscroll-white-everywhere todo stays a todo; every other gap in 03.4-UAT.md is resolved and is not reopened.

Rings appear on Import and Export only: the link attribute did not ship — impossible after this plan, and a code failure if seen. Focus cycles the chrome and never enters the page: Safari does not hand focus to the web view here; tap-then-Tab is the procedure on this device, and (a) still holds. Write the observation into 03.4-UAT.md as a note on the gap; do not fail the gap on it.
