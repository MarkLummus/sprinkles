## Summary

This phase is not new-feature work in the usual sense — it is a large, mechanical CSS custom-property rename across an already-shipped, heavily test-pinned stylesheet system, plus a font vendoring task, plus a Home rebuild that replaces an already-shipped (but explicitly provisional) "Sprinkles Jar" world with the DESIGN.md-approved App marks grammar. There are no new runtime dependencies: React 19.2.8, Vite 8.2.2, react-router 8.3.1, `idb` 8.0.3 and Vitest 5.0.0 are already the whole stack (`app/package.json:12-23`, read this session) and nothing in D-01 through D-20 requires adding a package. The one new artifact is a vendored `Caveat-Regular.woff2` font file plus its SIL OFL license text, shipped as a static asset — not an npm dependency.

The single highest-risk mechanical fact this research surfaces: `app/src/styles/css-source.js`'s `assertNoAtRules` (read this session, `css-source.js:63-78`) throws on **any** at-rule other than a top-level `@media` block. `binder.test.js`, `cross-cutting.test.js` and `home.test.js` all call `readAllRules` on `app.css`/`history.css`/`home.css`, which calls `assertNoAtRules` internally. A `@font-face` declaration placed in any of those three files will fail the test suite at import time, before a single assertion runs. The Caveat `@font-face` must live in a file none of those suites parses — a new `app/src/styles/fonts.css` (imported in `main.jsx`, never touched by `readAllRules`), not `tokens.css` (safe by contract but architecturally odd) and never `app.css`.

The second highest-risk fact: `cross-cutting.test.js` pins app.css's media-block set to an **exact enumerated list of 7** (`cross-cutting.test.js:296-328` and `:333-344`), and separately pins the `print` block to **exactly one rule**, `.page-status { display: none; }` (`cross-cutting.test.js:758-768`). D-17's forced-colors and print fallback for the hand must land as new selectors **inside the existing** `(forced-colors: active)` and `print` blocks (reusing the two conditions already in the allowlist), and the print-block cardinality assertion must be deliberately updated in the same commit — not treated as an incidental side effect.

The third fact: `GraduatedRule.jsx` (read this session) hard-codes `"var(--ink)"` as a literal JavaScript string in eight SVG `stroke` attributes (`GraduatedRule.jsx:52,118,128,129,132,141,145`, plus one in a code comment). These are invisible to a CSS-file grep and must be renamed in the same D-01 sweep, to `var(--sheet-ink)`. The same file's SVG geometry constants (`WIDTH`, `RULE_BASELINE`, `RULE_BAND_EDGE`, `RULE_TICK`, `HATCH_STROKE`) are plain JS numbers, not `var()` references — they do **not** need touching; SVG presentation attributes take user-space units, not CSS custom properties, so they were hand-mirrored from the tokens at write time and stay that way.

**Primary recommendation:** Sequence the rename in three clearly separated waves — (1) tokens.css + app.css + history.css + the three contract suites + GraduatedRule.jsx's colour literals, verified green before touching anything else; (2) the font vendoring and the hand's forced-colors/print fallback, added to app.css's *existing* blocks with the print-block test assertion updated deliberately; (3) the Home rebuild (home.css, home.test.js, RecipeList.jsx, RecipeList.test.jsx, a new domain/lastEvent.js, a new shell component, router.jsx) as an independent rewrite, not a rename — followed by D-04's removal of the jar/recipe-hue system as the phase's explicit last step.

### Pattern 1: react-router 8 layout route with `Outlet`

**What:** A parent route with no `path` (or a shared prefix) that renders a persistent shell and an `<Outlet/>` for whichever child route matched. react-router 8.3.1 (confirmed installed, `app/package.json:16`) is the data-router generation (`createBrowserRouter`, route objects, `Component`/`element`), the same API family `router.jsx` already uses (`createBrowserRouter([{ path: '/', Component: RecipeList }, ...])`, read this session, `router.jsx:81-85`). Nesting a layout route is additive to this existing shape — no API migration required.

**When to use:** Exactly the codebase's stated need — "the shell (rail, tools row, tab bar) wraps every route, so it lands at the router or a layout route, not inside `RecipeList`" (CONTEXT.md, Integration Points).

**Example (shape, not yet in the codebase — [ASSUMED] from react-router's stable data-router API, not fetched from live docs this session):**
```jsx
// router.jsx — nesting the existing leaf routes under a layout route
export const router = createBrowserRouter([
  {
    Component: Shell,          // renders <nav>...rail/tools row...</nav> then <Outlet/>
    children: [
```

### Pattern 2: `@font-face` with a vendored local file, kept out of the contract-suite parser

**What:** A single `@font-face` rule pointing at the vendored woff2, declared in a file none of the three contract suites (or `home.test.js`) reads with `readAllRules`.

**Why this file placement matters (verified this session):** `css-source.js:63-78`'s `assertNoAtRules` throws on any at-rule keyword other than a top-level `@media` — the regex explicitly lists `font-face` among the forbidden keywords (`css-source.js:65`). `binder.test.js:26,33` and `cross-cutting.test.js:26-34,44` both call `readAllRules(appCssSource)` (which internally calls `assertNoAtRules`); `home.test.js:17,29` does the same for `homeCssSource`. Adding `@font-face` to `app.css`, `history.css`, or `home.css` fails the suite at import time.

**Example:**

```css
/* app/src/styles/fonts.css — NEW, never parsed by readAllRules */
```

### Pattern 3: the hand's `forced-colors`/print fallback, added to app.css's *existing* blocks

**What:** D-17's fallback — "Under `forced-colors: active` and in print the role falls back to the text face in italic" — must be new *selectors* inside the two @media blocks app.css already carries, never new blocks.

**Verified constraints (this session):**
- `cross-cutting.test.js:296-328` pins `app.css`'s media-block set to an exact `allowedMedia` array of 7 strings, including `'(forced-colors: active)'` and `'print'` — adding an 8th distinct media condition fails this test.
- `cross-cutting.test.js:758-768` pins the `print` block to **exactly one rule**: `.page-status { display: none; }`. Adding a hand-fallback selector here requires deliberately updating `printRules).toHaveLength(1)` to `toHaveLength(2)` (or however many rules land) **and** the `printRules[0].selector` assertion, in the same commit — this is the D-17 equivalent of D-01's "every suite stays green," and should be called out explicitly in the plan's task, not left as an unplanned test failure to fix later.
- The `(forced-colors: active)` block (`app.css:2538-2554`, read this session) has no exact-count pin — only an existence check (`binder.test.js`'s "the forced-colors block keeps a fill..." test uses `.find`, not a length assertion) — so adding a selector there is lower-risk.

### Pattern 4: a framework-free "last event / standing" domain helper

**What:** A pure module mirroring `domain/lineage.js` and `domain/batch.js`'s existing conventions — no framework/DOM/store import, ISO-string date comparison (never `new Date()`, matching `batch.js`'s `formatRecordDate` comment: "Never constructs a Date and never calls a locale- or timezone-dependent formatter — the same record must read the same on every machine and in every test run," `batch.js:25-27`, read this session).

**Data available (verified this session):**
- `version.createdAt` — set at creation (`lineage.js:126`, `createChildVersion`) and never retaken on a correction (`lineage.js:154-165`, `saveOverVersion`); present in the seed data too (`data/olive-oil.js:56`, `createdAt: SEED_CREATED_AT`).
- `batch.recordedAt` — set once at `createBatch` (`batch.js:147`) and never retaken.
- `batch.changed` — `null` at creation, stamped with `now` on every `completeRecord` call (`batch.js:171-178`, "a completing save is always a save after the first") — this is the field to read for "a batch was **recorded**" *after* its first save (a tasting added via `completeRecord` bumps `changed`, not `recordedAt`).
- `batch.tasting.tastedDate` — the maker-entered tasting date (a domain fact, not a system timestamp); there is no separate system-clock field for "when the tasting was added" beyond `batch.changed`.
- `batch.churn.churnDate` — the maker-entered churn date (also a domain fact, already used by `sortedBatches`/`latestChurnDate`, `batch.js:303-327`).

**Recommended "last event" derivation (Claude's Discretion territory — CONTEXT.md leaves the exact mechanics open, only the three event *kinds* are named in D-05):** for a given recipe, take the max of: every one of its versions' `createdAt`; every one of its batches' `recordedAt` and `changed` (the system-clock save events, not the maker-entered `churnDate`/`tastedDate`, which are domain facts about when something *happened in the kitchen*, not when it was *entered in the app* — D-05 says "a recipe's last event (version saved, batch recorded, tasting added)," which reads as **save events**, i.e. `createdAt`/`recordedAt`/`changed`, not the churn/tasting dates themselves). Flagged as `[ASSUMED]` in the Assumptions Log — this reading is not stated explicitly enough in D-05 to call `[VERIFIED]`, and the two readings (save-time vs. kitchen-time) produce different orderings whenever a maker back-dates a churn.

**Standing derivation (D-07):** reuse `batch.tasting` presence (`hasAsMade`-style own-property/null check, matching the module's existing explicit-null discipline) and `batch.churn` presence to place a recipe's newest batch into "not yet churned" / "awaiting tasting" / "tasted" — `sortedBatches` (`batch.js:303-312`) already gives the newest-first ordering to read this from.

### Anti-Patterns to Avoid
- **Adding `@font-face` to `app.css`, `history.css`, or `home.css`:** fails `assertNoAtRules` at import time in `binder.test.js`, `cross-cutting.test.js`, or `home.test.js` respectively. Use a new `fonts.css` (or `tokens.css`, safe but architecturally odd) instead.
- **Adding a new `@media` block for the hand's forced-colors/print fallback:** fails `cross-cutting.test.js`'s exact 7-item `allowedMedia` array and the `stripped.match(/@media\b/g)).toHaveLength(7)` assertion (`cross-cutting.test.js:296-328,333-344`). Extend the two existing blocks instead.
- **Leaving the print block's cardinality test unmodified after adding a hand-fallback rule:** `cross-cutting.test.js:758-768` pins the print block to exactly one rule today; this must be a deliberate, documented change, not a surprise red test.
- **Renaming only CSS files and missing `GraduatedRule.jsx`'s eight literal `"var(--ink)"` strings:** a `--ink` → `--sheet-ink` rename that stops at `.css` files leaves the graduated-rule SVG drawing every stroke in an undefined custom property (silently invisible — `var()` with an unresolved reference computes to nothing, drawing no stroke at all, not an error).
- **Treating `home.css`/`home.test.js`/`RecipeList.jsx`/`RecipeList.test.jsx` as D-01 rename targets:** they are not — they currently implement and test "The Sprinkles Jar" world (jar hues, `recipe-colour.js`, `--c` custom property, `home__tally-mark--version/--batch`) that D-04/D-06/D-07/D-11 structurally replace with the App marks grammar. Renaming tokens in these files would be renaming code this phase deletes or rewrites outright.
- **Reading D-16's "Home at 390 — bottom tab row" board title as a literal new `390px` breakpoint:** D-16's own text says "The breakpoint follows the existing ladder in `app.css`" — the board's "390" names the phone viewport Mark reviewed on the canvas, not a new media-query literal. The existing ladder's narrowest named step is `(max-width: 600px)` (`app.css:2442`, confirmed via grep this session); reuse it (or `759.98px` if the rail-to-tabs transition is meant to happen earlier) rather than introducing an unlisted `390px` condition that would also fail the exact-7-media-blocks pin. Flagged as an Open Question below since CONTEXT.md does not disambiguate which existing step D-16 means.
- **Fetching Caveat from Google Fonts' CDN (`fonts.googleapis.com`) at runtme:** explicitly forbidden by D-17 ("nothing is fetched from a network"); vendor the file into `public/fonts/`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Deriving "last event across versions/batches/tastings" | Ad hoc `Date`-object comparisons scattered inline in `RecipeList.jsx` | One framework-free `domain/lastEvent.js` helper using ISO-string comparison, mirroring `lineage.js`'s `sortedVersions`/`batch.js`'s `sortedBatches` null-tie-break convention | The codebase already solved timezone/locale-independence once (`batch.js:25-27`'s comment is explicit about why `new Date()` is banned); re-deriving it inline risks reintroducing a bug already fixed elsewhere |
| A persistent shell across routes | Wrapping every leaf component individually, or a `useLocation()`-driven conditional render inside `App()` | react-router's built-in layout-route + `<Outlet/>` (Pattern 1) | It is the framework's own mechanism for exactly this need, and the codebase already uses the data-router API (`createBrowserRouter`) this pattern extends |
| Fallback typography under `forced-colors`/print | A JS `matchMedia` listener toggling a class | The two `@media (forced-colors: active)` / `@media print` blocks already in `app.css` (Pattern 3) | The whole binder system (buttons, checkboxes, the pen-blue fill) already uses CSS-only forced-colors fallbacks — matching that convention keeps one mechanism for "how does a rule adapt to forced colours," not two |
| Vendoring/serving a static font file | A base64-inlined font-face in a JS string, or fetching via `@import url(fonts.googleapis.com/...)` | Vite's `public/` static-asset convention (a plain file, referenced by an absolute `/fonts/...woff2` URL) | Vite copies `public/` verbatim to the build output with no processing needed for a single binary asset; base64-inlining a woff2 bloats the JS bundle for no benefit, and a Google Fonts `@import` is a network fetch D-17 explicitly forbids |

**Key insight:** every "don't hand-roll" item above already has a codebase-native mechanism (`domain/*.js`'s pure-function convention, react-router's layout routes, `app.css`'s existing forced-colors/print blocks, Vite's `public/`) — none of this phase's new work needs a library that isn't already installed.

## Common Pitfalls

### Pitfall 1: `@font-face` breaks the contract suites if placed in the wrong file
**What goes wrong:** `npm --prefix app test` fails immediately (a thrown error at module-import time, not a normal assertion failure) if `@font-face` lands in `app.css`, `history.css`, or `home.css`.
**Why it happens:** `css-source.js`'s `assertNoAtRules` (`css-source.js:63-78`, read this session) explicitly forbids `font-face` among other at-rule keywords, and three test files call `readAllRules` (which calls `assertNoAtRules`) on those three stylesheets.
**How to avoid:** put the `@font-face` rule in a new file (`fonts.css`) that no suite reads with `readAllRules`.
**Warning signs:** a Vitest failure message reading `"css-source.js's readAllRules parses exactly one level of nesting..."` rather than a normal `expect(...).toBe(...)` failure.

### Pitfall 2: the print block's exact-cardinality test
**What goes wrong:** adding the hand's print fallback rule to the existing `@media print` block silently fails `cross-cutting.test.js`'s `expect(printRules).toHaveLength(1)` assertion (`cross-cutting.test.js:758-768`).
**Why it happens:** that test was written when the print block existed for exactly one purpose (suppressing `.page-status`) and pins the block's contents exhaustively, by design (its own comment: "Nothing else is styled there").
**How to avoid:** update the test's expected length and selector list in the same commit that adds the hand's fallback rule; treat this as a planned, named change, not a rename-sweep side effect.
**Warning signs:** a passing rename-sweep commit (Wave 1) followed by an unexplained print-block test failure in Wave 2 — should never happen if Wave 2's task explicitly lists this test file among its edits.

### Pitfall 3: token names hard-coded as JS string literals outside `.css` files
**What goes wrong:** a CSS-only rename (even one that updates every `.css` file and every test-suite string) leaves `GraduatedRule.jsx`'s eight `"var(--ink)"` SVG stroke attributes pointing at an undefined custom property post-rename, since `--ink` no longer exists once D-01 lands.
**Why it happens:** SVG presentation attributes are plain string values, invisible to a `grep -l '\-\-ink' *.css` scoped search; `GraduatedRule.jsx`'s own header comment even flags the distinction ("expressed as plain numbers because SVG presentation attributes read user-space units, not CSS lengths" — for geometry — but the **colour** is deliberately `var(--ink)` as a string, not a number, per the same comment: "Colour is never a literal — every stroke reads var(--ink)").
**How to avoid:** run `grep -rn "var(--" app/src/ui app/src/domain` (not scoped to `*.css`) as an explicit Task-0 verification step before considering the rename complete; this session found exactly one file (`GraduatedRule.jsx`) with this pattern, but the planner should re-run the grep against the current tree rather than trusting this list, since other components may have been touched since this research.
**Warning signs:** a graduated rule's scale/tick/hatch lines silently stop rendering (blank instead of drawn) after the rename — no console error, since an unresolved `var()` degrades to the property's initial value (`currentColor`/unset for `stroke`), which can look like "nothing visibly wrong" until compared side-by-side.

### Pitfall 4: home.css/RecipeList.jsx are a rewrite, not a rename target
**What goes wrong:** applying D-01's mechanical rename discipline (grep-and-replace token names 1:1) to `home.css`/`RecipeList.jsx`/`RecipeList.test.jsx`/`home.test.js` produces a "renamed Sprinkles Jar," not the App marks grammar D-05–D-20 actually specify.
**Why it happens:** these four files currently implement an entire retired design (`--jar-*`, `--recipe-hue-*`, `recipe-colour.js`, the `--c` inline custom property, `home__tally-mark--version/--batch`, `home__words` for the "last verdict") that CONTEXT.md's Phase Boundary and D-04–D-20 replace, not merely rename. `RecipeList.test.jsx`'s own describe block is even named `'RecipeRows — The Sprinkles Jar identity and tallies (route.md, 260918-gha)'` (`RecipeList.test.jsx:97`, read this session) — a literal signal that these assertions test the retired world.
**How to avoid:** scope these four files to the Home-rebuild wave (structural rewrite against DESIGN.md's App marks section and route.md's "Active work first" direction), separate from the token-rename wave; do not attempt to preserve the Jar tests' shape while swapping token names.
**Warning signs:** a plan task titled "rename home.css tokens" that does not also touch the row markup, the tally-colour source (destination accent vs. recipe hue), and the standing/next-action logic.

### Pitfall 5: the `--gap-xl` / `--gap-page` comment drift (the folded todo)
**What goes wrong:** `tokens.css`'s ingredient-column derivation comment (`tokens.css:172-210`, quoted for context: "`.recipe-page`'s 2fr/1fr grid, minus `--gap-xl` (48px) padding on both sides...`", `tokens.css:190-191`) and `columns.test.js:43-44`'s matching comment still name `--gap-xl` in prose, even though the actual page padding is read through `--gap-page` (which resolves to `--gap-xl` by default and steps to `--gap-m` below 600px, per `tokens.css:52-68`).
**Why it happens:** documented in `.planning/todos/pending/2026-09-17-gap-xl-references-no-longer-greppable-to-the-page-gutter.md` — the relationship is arithmetically correct today but no longer *discoverable by search*, since a future reader grepping for `--gap-page` (the token the rule actually reads) will not find these two derivation comments.
**How to avoid:** since `tokens.css`'s block is being rewritten wholesale for D-01/D-02/D-03 anyway, take the todo's option 2 while doing so — name `--gap-page` alongside `--gap-xl` at both comment sites — unless the planner checks the numbers and finds option 1 (both sites reading `--gap-page` directly) holds below 600px too. Delete the todo file once done.
**Warning signs:** none functionally (the suite stays green either way) — this is a documentation-discoverability fix folded into the rewrite, not a behavioral risk.

### Pitfall 6: `--gap-xl`/`--gap-l` in `columns.test.js` are bare numeric constants, not token reads
**What goes wrong:** assuming `columns.test.js`'s `GAP_XL = 48` / `GAP_L = 32` local constants (`columns.test.js:52-53`, read this session) will automatically track a token rename or a value change.
**Why it happens:** these are plain JS numbers hard-coded in the test file's own page-arithmetic helper (`tableWidthAt`), not `resolveTokenPx(tokens, '--gap-xl')` calls — they duplicate the token's *value*, not its *name*. Since D-02 keeps `--gap-xl`/`--gap-l` unprefixed and unchanged, this phase does not need to touch them, but a future value change to either token would silently desynchronize from these constants.
**How to avoid:** no action needed this phase (D-02 doesn't rename these), but worth a one-line note in the plan that this pre-existing drift is out of scope, so it isn't mistaken for something D-01's sweep should have caught.
**Warning signs:** none this phase; flagged for awareness only.

3. **Does the font's `font-display` choice need a design decision, or is `swap` (this research's default recommendation) acceptable?**
   - What we know: D-17 specifies the fallback behavior under `forced-colors`/print but says nothing about the loading-flash behavior on a normal screen render.
   - What's unclear: whether a brief FOUT (flash of unstyled text, text-face-then-hand) on Home's lead block is acceptable, versus `font-display: optional` (never swaps if the font isn't cached fast enough) or `block` (invisible text briefly).
   - Recommendation: `swap` is the safest default (text is never invisible) and low-risk to leave as Claude's Discretion, since it's a loading-perf nuance CONTEXT.md doesn't mention.
