## Warnings

### WR-01: The More panel's native `<summary>` disclosure marker is never suppressed

**File:** `app/src/styles/shell.css:246-334` (the bottom tab row / More panel block)
**Issue:** `.shell__more` is rendered as a native `<details>`/`<summary>` pair (`Shell.jsx`, out of this review's scope but load-bearing context), and `<summary>`'s user-agent default is `display: list-item` with a generated disclosure triangle (a `::marker` in Firefox/Chromium, a separate `::-webkit-details-marker` pseudo-element in Safari/WebKit). `shell.css` sets `display: flex` on the summary via the `.shell__tabs .shell__place` rule (line 289), which removes the `::marker` triangle in Chromium and Firefox, but Safari's `::-webkit-details-marker` is a distinct pseudo-element that is *not* removed by changing `display` away from `list-item` — it must be hidden explicitly (the standard `summary::-webkit-details-marker { display: none; }` idiom). I grepped every stylesheet under `app/src/styles/` for `marker`/`summary`/`list-style` and found no such rule anywhere in the project, old or new.

This directly contradicts the project's own, heavily-precedented convention — repeated at length in `app.css` for the select chevron (D-17), the checkbox (D-13), the number spinners (D-19) and the date picker icon (SR-6): "every control drawn by the page, not the browser." The More summary carries a custom `MoreIcon` SVG plus the word "More" (`Shell.jsx`); on Safari/iOS/iPadOS a native ▶/▼ triangle will additionally render beside it, an unaccounted-for glyph with no token and no design provenance (the board this block cites, "board 171," is explicitly noted elsewhere in the same file as never having drawn the open panel at all). No test in `shell.test.js` checks for this, since the contract-reader (`css-source.js`) is text-only and cannot see rendered UA pseudo-elements — this is exactly the class of defect the file's own human-verify-at-end-of-phase caveat exists for, but nothing currently flags it for that pass.
**Fix:**
```css
.shell__more > summary {
  list-style: none; /* Firefox/Chromium: removes the ::marker box */
}

.shell__more > summary::-webkit-details-marker {
  display: none; /* Safari/WebKit: a separate pseudo-element, unaffected by display or list-style */
}
```

### WR-02: Recipe rows and the lead block still render an unguarded, possibly-blank recipe name (carried forward from the prior review's WR-01)

**File:** `app/src/ui/RecipeList.jsx:108-109` (`HomeLead`), `app/src/ui/RecipeList.jsx:229-230` (`RecipeRows`)
**Issue:** Both `HomeLead` and `RecipeRows` still render `entry.name` directly as the sole content of the recipe-name link (`<Link to={...}>{entry.name}</Link>`), with no fallback for an empty or whitespace-only string. Nothing in the ten files under review enforces non-empty `recipeName` at the domain or store layer, and this phase's gap-6 work (the standing word, the tally, the lead block) added more content around this link without adding a guard. An empty name still produces a silent, unlabelled link — now inside a five-column grid row (rail / place / standing / tally / actions) where a blank name cell is even easier to overlook visually than in the previous single-line card, and would still read as nothing to a screen reader.
**Fix:** `entry.name || 'Untitled recipe'` (or equivalent) in both `HomeLead` and `RecipeRows`, unless recipe-name validation is confirmed to already live in the store/domain layer outside this file set.

## Info

### IN-01: `STANDING_WORDS`/`RowActions` render silently empty for any standing outside the three current values

**File:** `app/src/ui/RecipeList.jsx:156-160` (`STANDING_WORDS`), `app/src/ui/RecipeList.jsx:166-206` (`RowActions`)
**Issue:** `STANDING_WORDS[entry.standing]` is `undefined` for any standing value not in `{NOT_YET_CHURNED, AWAITING_TASTING, TASTED}`, which React renders as nothing rather than an error — the `<span className="home__standing">` would be present but empty. `RowActions` has the matching gap: its `if` chain returns `null` for the same set of unhandled standings, so a row in that state would show neither a standing word nor any action at all, with no console warning or visible failure. Both call sites document this as an intentional, current-phase scope limit (`lastEvent.js`'s `standingFor` cannot return the two Recipe-Book/Idea-Log standings D-07 also names), and it cannot be reached today. It is worth a defensive fallback (e.g. a `default:`/final `??` case, or at minimum a dev-time console warning) before either `standingFor` or a future destination widens the set of reachable standings, since the current shape fails silently rather than loudly.
**Fix:** None required now; consider a fallback branch (e.g. `STANDING_WORDS[entry.standing] ?? entry.standing`) when a fourth standing is ever introduced, so a mismatch between `lastEvent.js` and this lookup table surfaces instead of rendering blank.

### IN-02: New greedy-regex test assertions in `RecipeList.test.jsx` are structurally loose

**File:** `app/src/ui/RecipeList.test.jsx:263, 271` (the "gap 5" `HomeLead` block-shape tests)
**Issue:** Two new assertions use an unanchored `[\s\S]*...<\/div>` pattern to check that content sits "inside one element," e.g. `expect(markup).toMatch(/<div class="home__lead-identity">[\s\S]*Notebook[\s\S]*Olive oil[\s\S]*<\/div>/)`. Because `[\s\S]*` is greedy and the regex is not anchored to the *matching* closing tag, this pattern is satisfied by the *last* `</div>` anywhere later in the string, not necessarily the one that actually closes `home__lead-identity`/`home__lead-next`. In the current markup this happens to be correct (there are no other `<div>`s in `HomeLead`'s output for it to over-match against), but the assertion would keep passing even if a future change moved the caption or name outside the intended wrapper, as long as some `</div>` still followed it somewhere in the page. This mirrors an existing pattern elsewhere in the test file, so it is not a new convention, but it is a genuine fragility in the two new tests specifically.
**Fix:** Scope the match more tightly, e.g. capture up to the *first* subsequent `</div>` (`[\s\S]*?<\/div>`) or assert on a parsed DOM fragment instead of a raw-string regex, if this file ever gains real DOM-testing tooling.

### IN-03: The paper-world's cream `body` background is no longer painted at the viewport edge for any route other than the three Sheet frames

**File:** `app/src/styles/app.css:5-11` (unchanged `body` rule), `app/src/styles/shell.css:20-26` (`.shell`'s new `background: var(--app-background)`)
**Issue:** `body` still declares `background: var(--sheet-ground)` unconditionally (untouched by this diff), and the new "own paper" fix has `.shell` (not `body` or `html`) paint `--app-background`, with `.recipe-page`/`.page-head`/`.not-found` painting `--sheet-ground` back over it for the three Sheet-frame routes. Since `.shell` is a normal flow element (`min-height: 100vh`, not `height: 100%` on `html`/`body`), any pixel outside its box — most concretely, the iOS/Safari elastic-overscroll "rubber-band" region when a maker scrolls past the top or bottom of a route — will briefly show `body`'s own `--sheet-ground` cream rather than the App's white, on every non-Sheet route (Home, the shell's five destinations). This is exactly the class of WebKit-only rendering gap this project has repeatedly caught only on Mark's own device (see the SR-6/date-field comment in this same file), so it is flagged for the same end-of-phase real-device pass rather than asserted as certain from source alone.
**Fix:** If confirmed on-device, paint `--app-background` on `html`/`body` as the new default (matching the old, now-removed `body:has(.home)` rule's original intent of reaching "the whole viewport"), letting the three Sheet-frame surfaces continue to paint their own `--sheet-ground` over it exactly as they do today.
