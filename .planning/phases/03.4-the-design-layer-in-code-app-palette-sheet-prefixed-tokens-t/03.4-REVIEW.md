# Phase 03.4: Code Review Report

**Reviewed:** 2026-09-21T21:20:00Z
**Depth:** standard
**Files Reviewed:** 22

## Summary

Most of this phase is a large, mechanical rename (`--ink`/`--ground`/`--pen-blue`/etc. → `--sheet-*`; `--home-*` → `--app-*`) plus the Home page rebuild ("Active work first") and the new `Shell.jsx` layout route with its rail/tools-row/bottom-tab navigation. The rename was verified end-to-end: no stale unprefixed token names remain anywhere under `app/src`, `tokens.test.js`'s unresolved/unread gates pass, and the full targeted test run (196 tests across the 9 touched suites) is green.

The one real defect found is a genuine implementation gap, not a rename slip: `Placeholder.jsx` (the component six of the app's ten routes render) ships two classes, `.place__title` and `.place__note`, that carry no CSS rule anywhere in the stylesheet tree. This was planned work — 03.4-03-PLAN.md lists both classes under "New CSS classes" and the phase's own SUMMARY claims shell.css is "scoped to `.shell`/`.place`" — but the rule never landed. `domain/lastEvent.js`'s recency/standing logic and `RecipeList.jsx`'s App-marks row grammar were traced carefully (null handling, tie-breaks, malformed-batch guards, empty-store paths) and hold up; no bug found there.

## Critical Issues

### CR-01: Placeholder pages ship with no CSS at all — `.place__title`/`.place__note` are declared nowhere

**File:** `app/src/ui/Placeholder.jsx:6-13`, `app/src/styles/shell.css:1-13`
**Issue:** `Placeholder.jsx` is the component rendered at `/notebook`, `/recipe-book`, `/idea-log`, `/ingredients`, `/kitchen` and `/search` — six of the app's ten routes. It renders:
```jsx
<div className="list-page">
  <h1 className="place__title">{name}</h1>
  <p className="place__note">{name} is not built yet.</p>
</div>
```
Neither `.place__title` nor `.place__note` — nor a `.place` root class at all — has a matching rule in `shell.css`, `app.css`, `home.css`, or `history.css` (confirmed by grep across every stylesheet). `shell.css`'s own file-header comment claims "Two root classes only: `.shell` ... and `.place` (the unbuilt-place page Placeholder.jsx renders inside `.shell__main`)", but `Placeholder.jsx` doesn't even apply a `.place` class to its root element (it reuses `.list-page` instead), and no `.place`-scoped rule of any kind exists to style the two child classes it does apply.

This is not a passive oversight: `03.4-03-PLAN.md` explicitly lists `.place__title` and `.place__note` under "New CSS classes" as required deliverables for this task, and `03.4-03-SUMMARY.md` claims "`shell.css` (new) ... scoped to `.shell`/`.place`" — the rule was planned and reported as shipped but never written. The title falls back to the browser's default `h1` size/weight/margin and the note falls back to default paragraph margins; both happen to inherit `--app-text` colour and `--face-grotesk` from `.shell`/`body`, so the pages are legible, but they carry zero project typography (no `--app-size-title`, no tracking, no controlled spacing) — a direct violation of the project's own rule that "every visual value ... reads through a CSS custom property ... no component or stylesheet carries a literal" (CLAUDE.md), since here the rendered values are pure unstyled UA literals rather than an omitted-but-intentional default.

No existing test catches this: `shell.test.js` only asserts the placeholder's text content and the rail's `aria-current`, never that `.place__title`/`.place__note` resolve to a rule.

**Fix:** Add the missing rule(s) to `shell.css` (or give `Placeholder.jsx`'s root element the `.place` class the file's own header comment already promises), reading the App type tokens the rest of the shell uses, e.g.:
```css
.place {
  /* whatever wrapper treatment was intended — currently .list-page substitutes */
}

.place__title {
  margin: 0 0 var(--gap-hair);
  font-family: var(--face-grotesk);
  font-size: var(--app-size-title);
  font-weight: 800;
  letter-spacing: -0.02em;
}

.place__note {
  margin: 0;
  font-family: var(--face-grotesk);
  font-size: var(--app-size-meta);
  color: var(--app-text-secondary);
}
```
and add a `shell.test.js` assertion pinning the rule's existence so this can't regress silently again.

## Warnings

### WR-01: `.home__lead` renders no visible "Notebook" place name is a duplicate concern for future destinations, but today `placeNameFor()`/`entry.name` blank-name edge case is unhandled

**File:** `app/src/ui/RecipeList.jsx:95-116`, `app/src/ui/RecipeList.jsx:191-218`
**Issue:** `HomeLead` and `RecipeRows` both render `entry.name` (`latestVersion.recipeName`) directly with no fallback for an empty or whitespace-only string. A version record whose `recipeName` was saved blank (the domain layer does not appear to enforce non-empty recipe names anywhere in the reviewed files) renders an empty `<h2>`/link with no accessible text — a silent, invisible row rather than a labelled one. This is a pre-existing gap widened by this phase's shift to a two-column-of-meaning layout (place name + recipe name + actions all crowd one row), where a blank name is more likely to be mistaken for a rendering bug than in the old single-line card. Low likelihood given upstream validation elsewhere in the app, but nothing in the reviewed files guards it.
**Fix:** If recipe-name validation already lives elsewhere in the store layer (out of this phase's scope), no action is needed beyond confirming it; if not, consider a `entry.name || 'Untitled recipe'`-style fallback in `HomeLead`/`RecipeRows` so an empty name can never produce an unlabelled link.

### WR-02: Two `<nav aria-label="Places">` landmarks coexist in the DOM at every viewport width

**File:** `app/src/ui/Shell.jsx:236, 262`
**Issue:** `Shell.jsx` renders both `.shell__rail` and `.shell__tabs` as `<nav aria-label="Places">` unconditionally; only CSS `display: none` (via the `759.98px` media query in `shell.css`) hides whichever one is inactive for the current viewport. The code comment acknowledges this ("a hidden element leaves the accessibility tree, so only one navigation is ever exposed"), which is correct behaviour in every current browser, but it is not a load-bearing accessibility guarantee — a `display: none` element is defined to be removed from the accessibility tree, but this depends on the CSS staying exactly synchronized with the JS-rendered pair (e.g. print stylesheets, forced-colors mode, or a future JS-driven `matchMedia` mismatch could expose both, or expose neither). Duplicate identically-labelled landmarks in one page, even when only one is exposed by current UA behaviour, is a fragile pattern to build on.
**Fix:** No change required for current correctness, but consider `aria-hidden` fallback or a documented single source of truth (e.g. render only the active nav based on a `matchMedia` hook) if this pattern is extended further, rather than relying solely on `display: none`.
