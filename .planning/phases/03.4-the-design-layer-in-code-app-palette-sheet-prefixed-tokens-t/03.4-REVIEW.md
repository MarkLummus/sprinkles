## Warnings

### WR-01: A comment claims the route-change close always returns focus to the More summary; the code only does that on the click path (new, Shell.jsx)

**File:** `app/src/ui/Shell.jsx:274-281` (comment), `152-159` (implementation)
**Issue:** The comment above `.shell__tabs` states: "The `<ul>`'s own click handler closes it on item activation and an effect keyed on the route closes it on navigation, in both cases returning focus to the summary." The implementation does not match this for the route-change path:

```js
useEffect(() => {
  setMoreOpen(false);
}, [pathname]);

function closeMore() {
  setMoreOpen(false);
  moreSummaryRef.current?.focus();
}
```

`closeMore` (bound to the `<ul>`'s `onClick`) does call `moreSummaryRef.current?.focus()`, but the `pathname`-keyed effect only calls `setMoreOpen(false)` — it never touches focus. This is reachable independently of `closeMore`: on the phone-width tab bar, `.shell__tabs` renders Home/Notebook/Recipe book/Idea log as siblings of the `<details>`, not inside its `<ul>`. Opening More, then tapping one of those sibling tabs (or using the browser's back/forward button) triggers the route-change effect without ever going through `closeMore`, so the panel closes but focus is not moved to the summary — contradicting "in both cases." In a codebase where comments are treated as the structural record of a decision (per this project's own convention), a comment that overclaims what the code does is a real defect: a future maintainer trusting the comment could reasonably assume focus-return is guaranteed on every navigation and build on that assumption.
**Fix:** Either correct the comment to describe only the click path returning focus (the route-change path deliberately does not, since focus is usually already on whatever the user just activated), or, if focus-return really is intended on every close, add it to the effect too:
```js
useEffect(() => {
  setMoreOpen(false);
}, [pathname]);
```
→ leave as-is and narrow the comment, since forcing focus back to the summary after a sibling-tab tap would steal focus from the control the user just used.

### WR-02: The More panel's native `<summary>` disclosure marker is still never suppressed on WebKit (carried forward, prior WR-01)

**File:** `app/src/styles/shell.css:279-284` (`.shell__more`/`.shell__more > ul`), `app/src/ui/Shell.jsx:291` (`<summary>`)
**Issue:** Re-verified in the current source: `.shell__more > ul { list-style: none; ... }` (shell.css:280-284) only strips the list styling of the panel's own item list. No rule anywhere in `shell.css` targets the `<summary>` element's own disclosure marker (`summary::-webkit-details-marker` for Safari/WebKit, or `summary { list-style: none }` for the `::marker` box Firefox/Chromium generate). `.shell__tabs .shell__place` sets `display: flex` on the summary, which removes the `::marker` box in Chromium/Firefox, but Safari's `::-webkit-details-marker` is a separate pseudo-element unaffected by `display`. This phase's device-UAT target is explicitly iPadOS Safari (G-03.4-4's own comment measures WebKit behaviour a few lines above this file's More panel work), so this is the one engine most likely to actually be checked and where the native ▶/▼ triangle will render beside the custom `MoreIcon` SVG and the word "More" — an unaccounted-for glyph, contradicting this project's own "every control drawn by the page, not the browser" convention (already applied to the select chevron, checkbox, spinners and date icon in `app.css`).
**Fix:**
```css
.shell__more > summary {
  list-style: none;
}

.shell__more > summary::-webkit-details-marker {
  display: none;
}
```

## Info

### IN-01: The Home lead's rod is hidden identically in both new media steps (new, home.css)

**File:** `app/src/styles/home.css:357-359` (1099.98px step) and `434-436` (759.98px step)
**Issue:** `.home__lead .home__rail { display: none; }` is declared once inside `@media (max-width: 1099.98px)` and declared again, word-for-word, inside `@media (max-width: 759.98px)`. Because the narrower query is a strict subset of the wider one, every viewport where the second declaration applies already has the first one applied too — the second is a dead duplicate, not a functional override (same selector, same property, same value). Harmless today, but it is exactly the kind of duplication that drifts silently: a future edit to the 1099.98px rule (e.g. changing it to `visibility: hidden`) would leave the 759.98px block still forcing `display: none`, and nothing would flag the two falling out of sync.
**Fix:** Drop the repeated declaration from the 759.98px block; the 1099.98px block already covers it at every narrower width.

### IN-02: Loose, unanchored regex assertions in `RecipeList.test.jsx`'s `HomeLead` tests (carried forward, prior IN-02, line numbers updated)

**File:** `app/src/ui/RecipeList.test.jsx:266, 274`
**Issue:** Re-verified at the current line numbers: `expect(markup).toMatch(/<div class="home__lead-identity">[\s\S]*Notebook[\s\S]*Olive oil[\s\S]*<\/div>/)` and the equivalent for `home__lead-next` still use a greedy, unanchored `[\s\S]*...<\/div>` pattern. The match is satisfied by the *last* `</div>` anywhere later in the markup, not necessarily the one that closes the named wrapper — currently correct only because `HomeLead`'s output has no other trailing `<div>` for it to over-match against. A later change that moved content outside the intended wrapper would still pass this assertion as long as some `</div>` appeared afterward.
**Fix:** Use a non-greedy match up to the first subsequent `</div>` (`[\s\S]*?<\/div>`), or assert against a parsed DOM fragment if this file gains real DOM-testing tooling.

### IN-03: No `aria-live`/`role="status"` on the new loading line (new, RecipeList.jsx / home.css)

**File:** `app/src/ui/RecipeList.jsx:43` (`<p className="home__loading">Loading your recipes…</p>`)
**Issue:** The loading-to-loaded transition (replacing the previous `return null`) is a real content change assistive tech would benefit from being told about, but the paragraph carries no `aria-live` region or `role="status"`, so a screen reader user gets no announcement when the list of recipes appears. Minor — the transition is typically brief and the page title is static — but worth a note since the rest of this phase is otherwise careful about explicit ARIA semantics (`aria-hidden`, `aria-current`, `aria-label`) elsewhere in the same files.
**Fix:** Optional: `<p className="home__loading" role="status">Loading your recipes…</p>`.
