## Info

### IN-01: tabIndex={0} added uniformly to elements that don't need the fix it documents

**File:** `app/src/ui/Shell.jsx:231,235,318,324` (the four `<button type="button">` stops: Import and Export, in both the tools row and the `More` panel)
**Issue:** The comment justifying this change (`Shell.jsx:144-151`, mirrored in `shell.css:191-203`) documents a WebKit-specific gap: `<a href>` elements are only keyboard-focusable under the embedder's `TabsToLinks` preference, which is off on Apple platforms with no iPadOS toggle. That's a real gap for the `NavLink`-rendered stops (`<a href>`) and plausibly for `<summary>` (WebKit has had its own focusability quirks there too), which is why an explicit `tabIndex` fixes them. `<button>` elements, however, are keyboard-focusable by default in every browser engine, including WebKit — no platform preference gates a button's focusability the way `TabsToLinks` gates a link's. Adding `tabIndex={0}` to the four `<button>` stops (Import/Export, tools row and `More` panel) doesn't fix anything WebKit was withholding; it's a no-op there.
**Fix:** No functional risk — `tabIndex={0}` on an already-focusable element is harmless and the uniform "every stop carries one" rule is easy to reason about, so this doesn't need to change. If precision matters here, the comment could note that the button stops are included for consistency/uniformity rather than because they shared the `<a href>`/`TabsToLinks` gap, so a future reader doesn't assume WebKit was silently skipping buttons too.
