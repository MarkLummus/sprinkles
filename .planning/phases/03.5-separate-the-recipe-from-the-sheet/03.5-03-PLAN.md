<decisions_recorded>
1. **Which binder recipes.** D-05 leaves the choice open. This plan takes the two research found cleanest. Pineapple v1 (IMG_2481, audit § 29) is a single version with a full formula and a recorded outcome. Coconut v1 -> v2 (IMG_2471-2472, §§ 19-20): v1's outcome is recorded, and v2 was churned with a draw temperature, a churn time and no outcome. Cherry Garcia v1 is avoided (the audit calls it unreconstructable). If a Coconut photo proves unreadable where the formula matters, swap in Mango on Light Base (IMG_2458, § 6). Flag the swap in the review and rename the module file to match.
2. **States coverage by source, not by construction.** Churned and tasted: Mexican Chocolate v1, Pineapple v1, Coconut v1 (and olive oil). Churned, not yet tasted: Coconut v2, and Mexican Chocolate v3 if a batch is recorded for it, since its Observations are stale v1 text. Not yet churned: Mexican Chocolate v4, an Ice Ed export with no binder page. Every one of the 29 binder pages was churned, so no binder recipe supplies "not yet churned".
3. **The version model already has homes for some Ice Ed fields.** An earlier phase gave each version `iceEd: { style, servingTemperatureC, hardness, overrunPercent }` and `targets` (bands). Where the source gives a value and the home exists, the version takes it. The sidecar still records every source field, so it is a complete capture (D-08's list named these four, and the review says where each one went). Ice Ed's PAC/POD target bands are on a per-kilogram sucrose-equivalent scale; the app's bands are per 100 g. The version's `targets` stay unset and the bands go to the sidecar, as D-08 lists them. Converting them is Mark's call, flagged.
4. **Coefficient scale.** Ice Ed stores PAC and POD per gram relative to sucrose = 1. library.js uses sucrose = 100 (library.js sucrose, allulose, salt). A D-03 entry's pac/pod are Ice Ed's value times 100. Ice Ed's `Sugar` for dairy is lactose, which the app derives from msnf, so dairy entries take fat and msnf only. Non-dairy `Solids` beyond fat and sugar go to `other`, or to `stabilizer` for a stabilizer's own share. Each conversion is written in the review document per ingredient.
5. **Basis for Ice Ed data.** D-03 says "basis recorded as Ice Ed". The library's `basis` field ranks trust (stated, derived, estimated, inherited; composition.js BASIS_RANK), and an unknown value would silently rank as trusted. Each converted field therefore takes `source: 'Ice Ed export (<file name>)'` and `basis: 'estimated'`, so figures resting on it are flagged (FORM1-02). This reading of D-03 is flagged for Mark.
6. **Binder-recipe ingredients the library lacks** (pineapple, coconut cream, coconut milk, shredded coconut and so on) take per-gram coefficients from the photographed printout's own per-row columns (a row's grams of Water, Sugar, Fat, MSNF, Solids, PAC, POD and Stabilizer divided by its Amount). Source: 'Ice Ed printout (IMG_NNNN)', basis: 'derived'. This extends D-03's rule to a source D-03 did not name, and is flagged.
7. **Ids.** Recipe ids are kebab-case names (`mexican-chocolate`, `pineapple`, `coconut`); version ids are `<recipeId>-v<N>` using the source's own version number; batch ids are fixed string constants in each module (as batch-2026-08-02.js does). Nothing reuses Ice Ed's own RecipeId UUID.
8. **Version names read against the derived ordinal.** versionLabel takes the source's real version name (D-01). The app numbers versions by creation order, so Mexican Chocolate v3 will read "Version 2 · v3" on the rail. That is the app's own count, not a made-up v2, and it is flagged so Mark can see it before approving.
</decisions_recorded>
