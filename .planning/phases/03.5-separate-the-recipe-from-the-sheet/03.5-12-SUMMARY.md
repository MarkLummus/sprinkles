## Decisions Made

- **Task 2 answered option-measure** (Mark, recorded before execution in this plan's own `decisions_recorded` item 5). Task 3 made no change, per that option's own action text.
- **Hit-test point for mark-vs-track:** the mark's own x centre combined with the *track's* own y centre, not the mark's own geometric centre. Empirically, at the mark's own centre the pre-fix build still returned the mark (not the track) — the design's own token values put the track's 1px band (27–28px local) almost, but not quite, at the mark's own 12px-tall centre (22–34px local, centre 28), and the point landed exactly on the ambiguous pixel boundary. Retargeting at the track's own y (confirmed the reliable overlap point via a real render) is what actually reproduces and then closes the bug.
- **Hit-test point for fade-vs-node:** the rail's own left edge + 10px, not the fade element's own `getBoundingClientRect().left`. A scrolled fade is a `position: absolute` child of the rail itself, which is *also* the scrolling element (`overflow-x: auto`) — confirmed by a real render that its box scrolls along with the rail's content (its reported `left` trailed the rail's own left edge by exactly the scrolled amount), so most of its own box is clipped by the rail's visible frame. The rail's own edge is where the fade is actually visible.
- **A cloned DOM node, not a real second version, produces the rail overflow the fade check needs.** The seeded fixture (`APP_ROUTE`) carries exactly one saved version, which cannot overflow the rail on its own. Rather than drive a full fork-and-save ceremony through the UI (fragile, and orthogonal to what this check is actually about — pure CSS stacking, not app data), the probe clones the real, rendered first node into the live `.notebook-history__nodes` list purely for the read, the same "for the read only" treatment the plan's own behaviour text already gives the fade's `pointer-events` override.
