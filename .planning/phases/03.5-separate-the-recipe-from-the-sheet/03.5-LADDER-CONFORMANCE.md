## Two probe fixes made during this run

Both are the same class of bug 03.5-08's own run found and fixed
(`2fc1083`): a selector written against an earlier board shape silently
mis-locates the element once a later decision restructures that shape.
Both are fixed in this run's own commit, in `03.5-conformance-probe.js`:

1. **`readVersionColumn`'s board branch** located the version column via
   `caption.parentElement` — correct for 03.5-08's original boards, where
   the "Version" caption span sat as a bare sibling of the identity/dl
   pair. Decision 18 (03.5-15) wraps that caption inside the fold-version
   button's own baseline-gap span, so `caption.parentElement` now reaches
   the wrong element and `identity`/`dl`/`nextVersion` all read `null` on
   every board. Fixed by locating the column through the fold-version
   button's own parent when present, falling back to the old shape for a
   board that predates the fold.
2. **`readRail`'s board branch** fell back to every `<a>` in the recipe
   `<header>` when the rail's own `#fold-history` body was absent — correct
   when no fold mechanism exists at all, but decision 19's own boards omit
   `#fold-history` from the markup specifically WHEN THE FOLD IS CLOSED
   (the generator's own convention: "a closed fold's content is left out
   of the drawing"), which is the normal state below 1366. The fallback
   then picked up the version column's own "Draft: Version 2 · less oil"
   link instead of a rail node — a false positive measured at every
   below-1366 width in this run's own first pass. Fixed by treating a
   `button[aria-controls="fold-history"]` with no matching body as "closed,
   genuinely no rail to read" rather than a cue to widen the search.

`readSheet`'s plan-grams selector (`03.5-08-PLAN.md` Task 2's own reading,
carried in this file's header comment) was ALSO already stale — it assumed
the plan amount lived inside `td.ingredient-table__col-name`, which
decision 15 (03.5-11) moved into its own preceding `td.ingredient-table__col-grams`
— fixed the same way, reading the new cell directly on both pages.

## Reading the tables below

- **match** — the board and app values agree (within 1px for numbers).
- **accepted** — a documented, pre-existing convention or an intentional
  layout choice, not new drift, usually citing `03.5-CONFORMANCE.md`'s own
  precedent for the same difference.
- **scenario** — the board and app differ because they depict different
  states of the SAME feature (the app's fixture has one saved version and
  one batch; several boards draw a second, unsaved draft version and/or a
  richer History/Batches state) — not a rendering difference to fix.
- **drift fixed** — a genuine CSS difference, corrected in this run within
  notebook.css/app.css/tokens.css only, with the commit named.
- **open** — listed in "Open for Mark" below rather than patched, because
  fixing it would need a component or behaviour change this plan's own
  prohibitions rule out.
