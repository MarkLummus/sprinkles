# Phase 03.5: Separate the recipe from the sheet - Research

**Researched:** 2026-09-24
**Domain:** In-repo data-model split (recipe record vs. version/Sheet) + route migration + responsive layout rebuild (React 19 + react-router 8 + idb) + binder-to-seed transcription
**Confidence:** MEDIUM-HIGH — the shape of every change is settled in canonical docs and confirmed by reading the current code; the two open risks are (1) the History rail is a near-total rebuild of `RecipeHistory.jsx`'s current nested-tree UI into a flat dated rail, and (2) the binder transcription is real editorial work gated by a blocking human checkpoint (D-07), not a mechanical port.

## Summary

This phase has three independent bodies of work that the planner should treat as separate waves: **(A)** a store/domain change (new `recipes` object store, `recipeId`→`recipeName` becomes `recipeId`→lookup, `headnote`→`sheetTitle`/`sheetDescription`, `carriedForward` removed, DB reset to a new `DB_VERSION`, `transfer.js` schemaVersion bump); **(B)** a route change (`/recipe/:id[...]` → `/notebook/:recipeId/:versionId[...]` with redirects, plus a UI rebuild to layout C per sketch 011 — new App-context front-matter band, a rebuilt History rail, batch/tasting log moved into App-context markup); **(C)** a seed-content transcription (Mexican Chocolate v1/v3/v4 plus 2–3 more binder recipes), which is gated by a **blocking human-review checkpoint (D-07)** before it is wired into `seed.js` — this is not something an executor can complete unattended.

Every discrete value quoted below (DB_VERSION, schemaVersion, route paths, class names, field names) was read directly from the file cited beside it this session. The recipe already has a `recipeId` field distinct from a version's own `id` — `app/src/data/olive-oil.js` seeds `recipeId: 'olive-oil-ice-cream'` today — so the recipe-grouping mechanism (`versionsForRecipe`, `latestVersionPerRecipe`, `activeWork`) does not need to change; only the *source* of a recipe's name/description changes, from `version.recipeName` to a new `recipes` store record looked up by `recipeId`.

**Primary recommendation:** Sequence the phase as three waves — (1) store/domain (recipe record, field rename, schema bump, transfer validator, seed structure) proven against a real IndexedDB and `transfer.test.js`; (2) routes + the layout-C rebuild (App front-matter band, rebuilt History rail, App-context batch/tasting log, redirects) verified side-by-side against sketch 011's boards in a real browser; (3) the binder transcription, executed up to the D-07 blocking checkpoint and then held for Mark's approval before `seed.js` is touched. Do not let (3) block (1) or (2) — olive oil alone is sufficient proof content for the store/route/layout waves.

## Common Pitfalls

### Pitfall 1: Trusting D-17's link-site list as exhaustive
**What goes wrong:** A grep-verification step is skipped because CONTEXT.md already names the sites.
**Why it happens:** The list looks authoritative and complete.
**How to avoid:** Re-run `grep -rn "'/recipe/\|\"/recipe\|\\\`/recipe" app/src --include="*.jsx" --include="*.js"` at execution time and diff against D-17's list — this session's research found 3 additional sites in `RecipeList.jsx` alone.
**Warning signs:** A build or manual click-through surfaces a still-old `/recipe/...` link after the phase is "done."

### Pitfall 2: Treating the History rail as a CSS restyle of `RecipeHistory.jsx`
**What goes wrong:** A task estimates "restyle the history panel" and discovers mid-task that the DOM shape, data grouping (versions-only vs. versions-with-nested-batches), and visual marks (rail fill/hollow/ring) are all different from what exists.
**Why it happens:** The component name (`RecipeHistory.jsx`) and its general purpose (show history) look unchanged.
**How to avoid:** Read `1600-long-history.html` (the board specifically drawn for History's own scrolling/dense state) before scoping this task; treat it as new component work that may *reuse* `versionForest`/ordering logic from the domain layer but *rebuilds* the render tree.

### Pitfall 3: Copying Ice Ed coefficients verbatim for an ingredient the library already has
**What goes wrong:** Dextrose or sucrose's PAC/POD gets overwritten with Ice Ed's differently-scaled value, silently changing every other recipe's balance figures that share the library entry.
**Why it happens:** D-03's "take coefficients from the Ice Ed JSON as-is" reads like a blanket rule if the "for ingredients the library lacks" qualifier is skimmed.
**How to avoid:** Build the near-match ingredient list first (Cream heavy, DSMP, Salt, Sucrose, Dextrose, Allulose) and resolve each explicitly in the D-07 review doc before touching `library.js`; never let a new version's embedded row silently diverge from the shared library entry without a recorded decision (each row embeds a `structuredClone` at authoring time per the existing pattern, so a wrong shared-library edit propagates to every *new* version created after it, not retroactively — but is still wrong going forward).

### Pitfall 4: Scoping the "Instructions" rename as a full find-and-replace
**What goes wrong:** An executor greps for "Method" and starts renaming class names / code identifiers, contradicting the explicit "screen-only… code identifiers keep method" rule.
**Why it happens:** The heading text is already "Instructions" but supporting UI strings (`fieldLabel`, aria-labels) may still say "Method", creating an inconsistent surface that looks like it needs a full rename to fix.
**How to avoid:** Grep for the literal string `'Method'`/`"Method"` in JSX render output (not `.method-*` class names, not `version.method`, not `Method.jsx`'s filename) and fix only user-visible text; leave every code identifier untouched.
