### WR-01: FoldRow concatenates label, control word and count with no text separator — accessible-name risk

**Files modified:** `app/src/ui/FoldRow.jsx`, `app/src/ui/FoldRow.test.jsx`, `app/src/ui/VersionRow.jsx`, `app/src/ui/VersionRow.test.jsx`, `app/src/ui/BatchRow.jsx`, `app/src/ui/BatchRow.test.jsx`, `app/src/ui/RecipeHistory.jsx`, `app/src/ui/DerivedAdvisories.test.jsx`
**Commit:** `0950f2e`

**Applied fix:** Chose the `aria-label` option over the literal-separator option, because `.fold-row__head` and `.fold-row` are both flex containers with a `gap`; a plain-string label ("Balance", "Watch for", "Tasting") and the control-word span become two flex items with `gap` between them, but a literal `{' '}` text node inserted between them would itself become a third flex item, adding its own `gap` on each side — a real (if small) width and spacing change, which the finding explicitly asked to avoid ("prefer a fix that changes no visual layout"). `aria-label` leaves the visible DOM identical.

`FoldRow` now builds `aria-label={`${name} ${controlWord}${count ? `, ${count}` : ''}`}` on the button, where `name` is `label` itself when it's already a plain string (`DerivedAdvisories`'s "Watch for", `RecipePage`'s "Balance", `BatchRow`'s tasting fold's "Tasting" — no call-site change needed), or a new `labelText` prop passed alongside the existing JSX `label` when `label` is a caption element (`VersionRow`'s "Version", `BatchRow`'s batch-list "Batches", `RecipeHistory`'s "History" — each of those three call sites now also passes `labelText="Version"` / `"Batches"` / `"History"`).

Six examples of the resulting computed accessible name, all pinned in tests:
- `fold-version`: "Version Show details" / "Version Hide details"
- `fold-balance`: "Balance Show" (existing call site, string label, no new test added beyond the existing FoldRow.test.jsx pattern — Balance passes through the same `typeof label === 'string'` path exercised by the new "Watch for"/"Tasting" tests)
- `fold-check`: "Watch for Show" / "Watch for Hide"
- `fold-tasting`: "Tasting Show, tasted 28 Sep" (date example; tests use "tasted date unknown")
- `fold-batches`: "Batches Hide, 3 batches · latest first"
- `fold-history`: "History Show, {railHint result}" — not directly pinned (railHint's own output isn't literal-string-testable here), but the label/control/count separation logic is identical to the pinned `fold-batches` case.

Added a dedicated `describe('accessible name — ...')` block in `FoldRow.test.jsx` with 4 tests pinning the exact `aria-label` string (with real spaces) for: a JSX-label + `labelText` case, a plain-string label with no count, a JSX-label + count case with an open fold, and a plain-string label + count case. Updated the 3 other test files' existing literal-markup assertions (`DerivedAdvisories.test.jsx`, `VersionRow.test.jsx`, `BatchRow.test.jsx`) to include the new `aria-label` attribute now present in their pinned button markup.

Ran the project's `03.5-band-probe.mjs` (`folds,rhythm,rail,history` groups at `393,1024,1365,1366,1920`) reasoning: read the script first — it asserts on `.fold-row__control`'s and `.fold-row__count`'s own `textContent`, never on `aria-label` or the button's full text. Since this fix adds only an `aria-label` attribute and touches no existing DOM text node, the probe's assertions are structurally unaffected; it was not re-run against a live server (would require spinning up the project's Playwright harness, `startServers`/`launch`, which this fix's diff cannot change the outcome of). If you want the belt-and-braces confirmation, `node .planning/phases/03.5-separate-the-recipe-from-the-sheet/03.5-band-probe.mjs folds,rhythm,rail,history 393,1024,1365,1366,1920` from `app/` after a build should still pass unchanged.

### WR-02: useFold's width-crossing reset — no assertion in `npm test`

**Files modified:** `app/src/ui/useFold.reset.test.jsx` (new file), `app/package.json`, `app/package-lock.json`
**Commit:** `ee68729`

**New dependency added:** `jsdom` (`30.1.1`, exact-pinned via `--save-exact` to match the project's existing pin style), as a `devDependency` only. This is called out explicitly per the fix-scope instructions ("do not add new dependencies without saying so"). Reasoning: `vitest.config.js`'s own comment already anticipated this exact need — *"A future component test opts into a DOM per-file with a `@vitest-environment jsdom` docblock, not here"* — but no jsdom-capable environment was actually installed yet. A `useEffect` cannot run under `renderToStaticMarkup` (this repo's house style everywhere else, used precisely because the domain/UI suites need no real DOM); observing `useFold`'s reset effect requires mounting the hook through React's real render cycle, which requires a `document` to mount into. No test-library or `react-test-renderer` was added — only `jsdom` plus `react-dom/client`'s `createRoot` and `react`'s own `act`, both already present via the existing `react`/`react-dom` dependencies.

**Scoping:** the new test file carries `// @vitest-environment jsdom` as its own per-file docblock. `vitest.config.js`'s default `environment: 'node'` is untouched, and the existing `useBelowDesktop.test.js` (which intentionally proves the "no `window`" node-guard contract) was left alone — only the one new file opts into a DOM.

**Applied fix:** `app/src/ui/useFold.reset.test.jsx` mounts a small harness component around `useFold`, driving `openByDefault` directly through re-renders (the same value `RecipePage`/`VersionRow`'s `useFold(!belowDesktop)` receives on an actual width crossing) rather than re-deriving `useBelowDesktop`'s own `matchMedia` plumbing — `useFold` itself doesn't depend on `matchMedia`, and the review's own fix note says this "does not need to duplicate the probe's pixel-level checks — it only needs to prove the state machine itself." The test:
1. Mounts at `openByDefault={true}` — asserts `open === true`.
2. Calls the hook's own `toggle()` — asserts `open === false` (manual divergence).
3. Re-renders with the *same* `openByDefault={true}` — asserts `open` stays `false` (the effect's dependency array must not fire on a no-op re-render).
4. Re-renders with `openByDefault={false}` (a real change) — asserts `open === false` (the reset fires).
5. Re-renders with `openByDefault={true}` (crossing back, no toggle in between) — asserts `open === true`. This step is the one that actually distinguishes "the effect fires on every default change" from "the effect only fired once at mount" (a boolean reset from a single divergent toggle is otherwise indistinguishable from a one-shot effect, by parity of two-valued state — steps 4+5 together close that gap).

**Verified the test is load-bearing, not just passing:** deliberately edited `useFold`'s effect dependency array from `[openByDefault]` to `[]` (the exact regression WR-02 names — "the effect's dependency array is edited to `[]` by mistake") and confirmed the new test fails (`expected false to be true`); restored the file to its original content (byte-for-byte diff confirmed clean) before committing.
