### CR-01: Seed batch "newest first" reordering has no effect; standing for Coconut, Strawberry and Mocha still reads the wrong batch

**Files modified:** `app/src/domain/batch.js`, `app/src/domain/batch.test.js`, `app/src/data/seed-recipes.js`, `app/src/store/seed-roundtrip.test.js` (new)
**Commit:** c6efce4
**Status:** fixed: requires human verification (ordering logic)
**Applied fix:** `sortedBatches` keeps its churn-date ordering (dated newest first, undated last). Batches that tie on churn date now order by `recordedAt` descending, with a missing `recordedAt` last. The result no longer depends on the order the store returns records in. The "newest first" batch arrays in `seed-recipes.js` went back to chronological order, and the comments that claimed the array order decided the sort were removed.

Tie-break order confirmed against the seed data before committing. In every seeded recipe, `recordedAt` equals the owning version's `createdAt`:
- Coconut: v1 2024-12-27T21:21:12Z, v2 2024-12-28T15:10:46Z. v2 is newest (untasted, so Home shows awaiting tasting).
- Strawberry: v1 2024-09-02, v2 2024-09-14T12:03:59Z, v2.1 2024-09-14T12:04:00Z. V2.1 is newest (tasted). The one-second gap is the documented ordering placeholder.
- Mocha: v0 2024-12-23T14:16:41Z, v2 ...:43Z, v3 2024-12-28T13:07:34Z. v3 is newest (untasted).
- These match the true churn order given in the old seed comments (V2.1 > V2 > V1, v3 > v2 > v0, v2 > v1).

Tests added: a unit test for the tie-break in both input orders, and `app/src/store/seed-roundtrip.test.js`. The round-trip test seeds a fake-indexeddb store through `seedIfEmpty`, reads through `repository.getAllBatches()` and asserts each recipe's newest batch and standing.

**Observation, not changed:** Mexican Chocolate is unaffected by this fix, and its ordering reads oddly. Its v1 batch has `churnDate: '2025-12-13'` and its v3 batch has `churnDate: null`. Under the existing rule (dated before undated) v1 is "newest", so standing reads v1's tasted state even though the v3 batch is newer and untasted. This is pre-existing domain behaviour outside the finding, so I left it for Mark to decide.

### WR-01: `seedIfEmpty` is non-atomic, and its emptiness guard flips on the first version written

**Files modified:** `app/src/store/seed.js`, `app/src/store/seed.test.js`
**Commit:** cfbaf2a
**Applied fix:** `seedIfEmpty` now calls `putAllRecipes`, then `putAllBatches`, then `putAll` (versions), each one transaction through the repository seam. Versions go last, so the emptiness check (which reads versions) only flips once everything else is written; an interrupted seed leaves the store looking empty and reseeds on the next boot (the writes are puts). The stale comment (IN-01's concern, same lines) was rewritten as part of this change. The test's in-memory repository now implements the three bulk calls, and a new test pins the write order `recipes, batches, versions`.
