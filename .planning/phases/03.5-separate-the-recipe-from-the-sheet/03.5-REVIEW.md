## Summary

Reviewed the gap-closure changes (plans 14..25) since 43b9d0c. The CSS work is sound: every new custom property exists in tokens.css, no literals were introduced, no `dangerouslySetInnerHTML`, and every new `Link` carries `tabIndex={0}`. The History strip geometry checks out arithmetically, including the single-node case, where the track collapses to zero width. The `Method.jsx` new-step guard is correct at the call site it touches.

The main defect is in the seed data. The "newest first" batch reordering (judgement call 58) does not survive the IndexedDB round trip, so the fix it claims does nothing at runtime. Separately, seeding is now a long non-atomic sequence guarded by a check that flips on the first write.

## Critical Issues

### CR-01: Seed batch "newest first" reordering has no effect; standing for Coconut, Strawberry and Mocha still reads the wrong batch

**File:** `app/src/data/seed-recipes.js:50-58,64-68,73-76` (consumed via `app/src/domain/lastEvent.js:61`, `app/src/domain/batch.js:317`, `app/src/store/repository.js:38`)
**Issue:** The comments claim `sortedBatches` ties on `churnDate: null` and "falls back to this array's own order". That holds only for the in-memory arrays the tests build. In the app, batches reach `activeWork` and `standingFor` through `repository.getAllBatches()`, which is `db.getAll('batches')`. IndexedDB returns records in primary-key order (the `id` string), not insertion order. So the order in `seedRecipeGroups` is discarded on write.

The stable sort therefore sees the batches in id order:
- Coconut: `coconut-v1-batch-01`, `coconut-v2-batch-01`. The first entry is v1's batch, which is the tasted "EPIC FAIL". The truly newest batch is v2's, which is untasted. Home shows the recipe as tasted when it is awaiting tasting.
- Strawberry: `strawberry-v1-…`, `strawberry-v2-1-…`, `strawberry-v2-…` (`'1' < 'b'`). The first entry is V1's batch, but the newest is V2.1's.
- Mocha: `mocha-v0-…`, `mocha-v2-…`, `mocha-v3-…`. The first entry is v0's batch, but the newest is v3's.

The tests in `seed-recipes.test.js` (around lines 540, 668, 829) call `standingFor` on filtered in-memory arrays, so they cannot see the ordering the store returns.

**Fix:** Do not rely on array order. Either give the batches real churn dates, or add a deterministic tie-break in the domain, for example on `recordedAt`, which the tests already pin to `version.createdAt`:
```js
export function sortedBatches(batches) {
  return [...batches].sort((a, b) => {
    const aDate = a.churn.churnDate;
    const bDate = b.churn.churnDate;
    if (aDate !== bDate) {
      if (aDate === null) return 1;
      if (bDate === null) return -1;
      return aDate < bDate ? 1 : -1;
    }
    if (a.recordedAt === b.recordedAt) return 0;
    return a.recordedAt < b.recordedAt ? 1 : -1;
  });
}
```
Add a test that seeds a fake-indexeddb store, reads through `getAllBatches`, and asserts each recipe's standing. Then the reordering in `seed-recipes.js` and its comments can be reverted.

## Warnings

### WR-01: `seedIfEmpty` is non-atomic, and its emptiness guard flips on the first version written, so an interrupted seed is permanent

**File:** `app/src/store/seed.js:13-22`
**Issue:** The guard is `listVersions().length > 0`. The seed used to be 3 writes. It is now dozens of sequential awaited `put`s across three stores, each in its own transaction. If the tab closes, the page reloads, or a write throws part-way, the store holds some versions, the next boot sees a non-empty store, and the seed never resumes. The user is left with a partial library and missing recipes or batches. There is no recovery short of clearing site data. Because the olive-oil group is first, the first version is written almost immediately, so the window is the whole seed.
**Fix:** The repository already exposes `putAllRecipes`, `putAllBatches` and `putAll` (versions), each a single transaction. Flatten the groups, then write recipes and batches first and versions last. The guard store is then written atomically and only after the other stores are complete:
```js
const groups = seedRecipeGroups;
await repository.putAllRecipes(groups.map((g) => g.recipe));
await repository.putAllBatches(groups.flatMap((g) => g.batches));
await repository.putAll(groups.flatMap((g) => g.versions));
```

### WR-02: `FoldRow` builds its accessible name from `labelText`, which is silently optional when `label` is an element

**File:** `app/src/ui/FoldRow.jsx:20-23`
**Issue:** `name = typeof label === 'string' ? label : labelText`. Any caller that passes an element label without `labelText` gets an `aria-label` of `"undefined, Show"`. `aria-label` overrides the button's content, so the visible label is lost to assistive technology with no error and no test failure. Three callers currently comply, but nothing enforces it. `count` is also interpolated blindly, so a non-string count would read `[object Object]`. Today's callers pass strings.
**Fix:** Fail loudly or fall back:
```js
const name = typeof label === 'string' ? label : labelText;
if (name == null && import.meta.env?.DEV) {
  throw new Error('FoldRow needs a string label or labelText');
}
```
Alternatively, drop `labelText` and take a single string `label` prop plus a `captionClassName`.
