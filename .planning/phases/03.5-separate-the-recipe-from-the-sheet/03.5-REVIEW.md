## Warnings

### WR-01: FoldRow concatenates label, control word and count with no text separator — accessible-name risk

**File:** `app/src/ui/FoldRow.jsx:12-19`
**Issue:** Every fold's caption/label and its "Show"/"Hide" control word are adjacent `<span>` children with no whitespace or punctuation between them in the DOM:
```jsx
<span className="fold-row__head">
  {label}
  <span className="fold-row__control">{controlWord}</span>
</span>
{count ? <span className="fold-row__count">{count}</span> : null}
```
`FoldRow.test.jsx`'s own literal snapshot confirms the rendered markup has no space: `...>Version</span><span class="fold-row__control">Show details</span>...`. The visual gap between "Version" and "Show details" comes entirely from `.fold-row__head`'s `gap: var(--app-notebook-recipe-rail-gap)` (flex layout) — a purely visual affordance that inserts no character into the accessible text.

Before this plan, the label and its toggle were always two separate elements (an `<h2>`/`<h3>` heading plus a standalone `HistoryDisclosure` button whose own text was just "Show"/"Hide"/"Batches (n)"), so the button's accessible name was never a concatenation of two unrelated words. This plan's consolidation ("the one full-row fold head... its own label doubles as the caption") is new, and it is now the ONLY source of the button's accessible name across six instances: `fold-version` ("VersionShow details"/"VersionHide details"), `fold-balance` ("BalanceShow"), `fold-check` ("Watch forShow"), `fold-tasting` ("TastingShow" + "tasted 28 Sep" with no separator either), `fold-batches` ("BatchesShow" + "3 batches · latest first"), `fold-history` ("HistoryShow" + "3 versions").

Whether a given browser/AT actually inserts an implicit boundary here is engine-dependent (it hinges on treating flex items as block-context for name computation); Chrome DevTools' Accessibility pane and WebKit/VoiceOver do not reliably agree on this in every configuration, and this project's own working agreement is explicit that device/engine confirmation is required before trusting a layout-only affordance ("Verify in the engine that matters" — Chromium passes miss Mark's iPad/WebKit). No test in this diff — unit or probe — asserts the button's *computed accessible name* (as opposed to its visual/DOM markup) at all, so a garbled VoiceOver announcement like "Watch forShow" would currently go undetected.

**Fix:** Give the button an explicit `aria-label` composed from real words, or insert a literal space/middle-dot between the text nodes so the DOM text itself is well-formed regardless of engine, e.g.:
```jsx
<button
  type="button"
  className="fold-row"
  aria-expanded={open}
  aria-controls={controls}
  aria-label={`${labelText} ${controlWord}${count ? `, ${count}` : ''}`}
  onClick={onToggle}
>
```
(`labelText` would need to be a plain string rather than the JSX `label` prop some callers pass — or, simpler, add a literal `{' '}` between `{label}` and the control span, and another between `fold-row__head` and `fold-row__count`.) Verify the fix by reading the button's computed accessible name in Safari/VoiceOver on the iPad, not just the Chromium probe.

### WR-02: useFold's width-crossing reset — the plan's one genuinely new hook behavior — has no assertion in `npm test`

**File:** `app/src/ui/useBelowDesktop.js:33-40`
**Issue:** `useFold`'s entire raison d'être (decisions_recorded 2: "a fold's own open/closed state... returns to that default whenever the default changes, so an iPad rotation across 1366 resets the fold") is implemented as one `useEffect` keyed on `[openByDefault]`. `useBelowDesktop.test.js` only asserts `typeof useFold === 'function'` (no jsdom in this suite, so no `matchMedia` `change` event can be dispatched to exercise the effect). Grepping every `*.test.jsx`/`*.test.js` under `app/src/ui` for `matchMedia`/`dispatchEvent`/`addEventListener('change'` turns up nothing beyond `BatchRow.test.jsx`'s unrelated "no window.matchMedia" guard test. The only place this reset is exercised at all is `03.5-band-probe.mjs`'s `setViewportSize` round trip — a script under `.planning/`, run manually, not part of `npm --prefix app test`.

Concretely: if a future edit to `VersionRow.jsx`, `RecipePage.jsx`, `DerivedAdvisories.jsx`, `BatchRow.jsx` or `RecipeHistory.jsx` accidentally drops the `foldsOpen`/`belowDesktop` prop from a `useFold(...)` call site (or the effect's dependency array is edited to `[]` by mistake during an unrelated refactor), `npm test` would still report green — the regression would only surface on a live device rotation or a manual probe run, exactly the scenario this behavior exists to guard against.

**Fix:** Add a jsdom-backed test (this file is the one exception the codebase already carves out for `matchMedia`-driven hooks, unlike the domain suite) that mounts a small harness component around `useFold`, flips `window.matchMedia`'s mocked `matches` value, dispatches a synthetic `change` event, and asserts the fold's `open` state follows. This does not need to duplicate the probe's pixel-level checks — it only needs to prove the state machine itself, independent of any specific component's markup.
