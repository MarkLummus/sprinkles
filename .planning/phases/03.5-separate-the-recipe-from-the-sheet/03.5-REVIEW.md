## Warnings

### WR-01: The signed-field wiring that prevents a silent blank save has no test, and the handler runs twice per keystroke

**File:** `app/src/ui/BatchRow.jsx:122-140`
**Issue:** The guard against saving an unreadable entry as blank (T-03.5-82) depends on three pieces of wiring on the `<input>`:
- `onInput={field.signed ? handleEdit : undefined}`
- `onChange={handleEdit}`
- `onWheel` blur

The comment says `onInput` is load-bearing. React's `onChange` never fires for a lone minus typed into an empty field, because the value tracker sees `''` before and after. It also never fires when select-all-delete clears an unreadable entry.

The new tests cover only the helpers (`readSignedInput`, `shownSignedValue`) and the static markup. `renderToStaticMarkup` drops event handlers, so deleting `onInput` or `onWheel` leaves every test green. The first regression would be a maker saving a blank temperature after typing "-".

On a normal valid keystroke, both `onChange` and `onInput` fire from the same native event. `handleChangeRecordField` therefore runs twice per keystroke. It calls `setFieldErrors`, `setBlockedDateMessage`, `setFormStatus`, `setPendingUndo` and `setDraft` each time. This is idempotent today, but it is wasteful, and any future non-idempotent side effect in that handler would double-fire.

**Fix:** Export `MeasuredField`, or render it with the react-dom test utilities under jsdom, and assert two things:
- Dispatching an `input` event on a signed input with `validity.badInput` true calls `onChange(key, MALFORMED_NUMBER_ENTRY)`.
- A wheel event blurs the input.

To remove the double call, drop `onChange` for signed fields and keep only `onInput`. React warns about a controlled input with no `onChange`, so pass a no-op `onChange` instead. For example:
```jsx
onChange={field.signed ? () => {} : handleEdit}
onInput={field.signed ? handleEdit : undefined}
```
If both are kept, document why the double call is accepted.

### WR-02: A restored tasting shows a blank field while the draft still holds the unreadable-number sentinel

**File:** `app/src/ui/BatchRow.jsx:86-92`, with `app/src/ui/RecipePage.jsx:1357-1381`
**Issue:**
1. A maker types text the browser cannot read into Tasting temperature, for example "-" or "5e". The draft holds `MALFORMED_NUMBER_ENTRY`, and the input displays blank only because the DOM still holds the raw text.
2. The maker presses Remove tasting. `tastingHasInk` is true because of the sentinel, so `tastingPayloadFromDraft` captures it into `pendingUndo`.
3. The maker presses Restore tasting. `restoreDraftFromUndo` writes the sentinel back. The input remounts empty, and `shownSignedValue` renders `''` for the sentinel.

The field looks blank, but the draft is invalid. Nothing is flagged until Save. Save then refuses, focuses a visibly empty field and shows "Enter a temperature, such as −6, or leave blank." Nothing is lost, but the visible state and the draft disagree. The "ink" the maker was asked to undo no longer exists on screen. The same mismatch appears whenever the section remounts while the draft holds the sentinel.

**Fix:** Normalize the sentinel to `''` whenever the draft is snapshotted for undo, so a restored field is truly blank. In `tastingPayloadFromDraft`:
```js
tastingTempC: draft.tastingTempC === MALFORMED_NUMBER_ENTRY ? '' : draft.tastingTempC,
```
Also exclude the sentinel from `tastingHasInk`, since unreadable text is not recorded ink. Alternatively, keep the sentinel and render the flagged-but-blank state visibly with `aria-invalid` from the moment of entry.

## Info

### IN-01: The rail's "churned {date}" reads `latestChurnDate`, which ignores the new standing-day rule

**File:** `app/src/domain/historyRail.js:51-52`
**Issue:** Plan 26 made `sortedBatches` rank an undated batch by its recording day. `railEntries` still words a version's churn state through `latestChurnDate`, which skips undated batches entirely. For a version whose newest batch is undated, the rail says "churned date unknown" or names an older dated batch's day. Meanwhile the Batch section and the Batches fold treat the undated batch as newest. Seeded Mexican Chocolate v3 already has a single undated batch, so the rail reads "date unknown" there. That is honest, but it follows a different rule from the one plan 26 introduced.
**Fix:** Either accept the divergence and note it in the `latestChurnDate` doc comment, or derive the rail date from `sortedBatches(versionBatches)[0].churn.churnDate`.

### IN-02: Number-input and parser disagree on exponent strings and the Unicode minus

**File:** `app/src/ui/BatchRow.jsx:129`, `app/src/domain/battery.js:49-54`, `.claude/skills/sketch-findings-sprinkles/references/batch-record-tasting-battery-structure.md:187`
**Issue:** A `type="number"` input reports valid exponent forms such as "1e3" as a normal value. `parseMeasuredDraft` rejects them, so the field passes through the browser's validity check and then fails at Save. The contract says "the browser also filters what can be typed there, so the comma and Unicode-minus rules serve the four text fields". That is not true in WebKit and Gecko, which let arbitrary characters be typed or pasted into a number input. A pasted "−6" (U+2212) becomes `badInput` and is flagged. The error sentence's own example, "such as −6", uses that very character.
**Fix:** Soften the contract sentence. Optionally pass `inputMode`-agnostic text through `parseMeasuredDraft` for exponent forms, or change the sentence's example to an ASCII "-6".
