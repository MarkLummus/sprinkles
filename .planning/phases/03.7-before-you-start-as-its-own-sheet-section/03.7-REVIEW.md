## Summary

Reviewed the diff `384eca0..HEAD` for the 12 files in scope and ran the full suite (`npx vitest run`: 64 files, 1926 tests, all passing).

The areas the caller named all check out against source:

- **One tbody per step group (`IngredientTable.jsx:831-854`).** Keys are unique: numbered groups key on `displayNumber`, removed groups on `removed:${n}`, and the unallocated group on the literal `'unallocated'`. Groups are only created when an entry is pushed, so no group has empty `entries`. `groups.length === 0` keeps one empty `<tbody />`. A flat table (a lone unallocated group) renders one tbody with no step head. The `Fragment` import is removed and nothing else uses it. No `tbody` selector elsewhere in the CSS or JS assumes a single body. The old `tbody tr:last-child` rule became `tbody:last-of-type tr:last-child`, which is the right correction for several bodies.
- **Conditional render, reading versus pen (`RecipePage.jsx:2030-2044`, `2112-2128`).** `beforeRegionShown = developing || notes.length > 0`, and `showsMethodRegion` takes only `{mode, steps}`. The class modifiers are derived from the same two booleans the sections are guarded by, so the grid and the DOM cannot disagree. The pen reads the draft's notes. The `NoteList` guard avoids an empty `<ul>`.
- **Removed Method props.** `Method.jsx` has no remaining reference to `NoteList`, `beforeYouStart`, `onChangeNoteText` or `onRemoveNote`. Its `NoteList` import is gone, and `RecipePage` no longer passes them. `.method__before` is gone from the CSS and the JS. No dead code was left by this change.
- **Grid-area sets.** Row counts are consistent at both widths:
  - Wide: base 5 rows (`auto auto auto 1fr auto`, the 1fr on `method`); no-before 4 rows (1fr on `method`); no-method 4 rows (1fr on `ingredients`); both 3 rows (1fr on `ingredients`).
  - Narrow: the same four combinations are declared, each after the narrow base rule.
  - The double modifier is (0,2,0), so it wins at 984 and up regardless of order. The single modifiers are (0,1,0) and follow their base rules.
- **Tokens-only, tabIndex, markup.** `.before-region` reads `var(--measure-prose)`. There are no literals. No new interactive element was added, and the moved `remove` button keeps `tabIndex={0}`. Notes render as text, and test (e) pins that a markup-like note creates no element. There is no `dangerouslySetInnerHTML`. No domain module or `idb` import was touched.

One defect was found: the new Instructions break rule does not do what its comment says on the live route. The remaining items are minor.

## Warnings

### WR-01: `.method-step { break-inside: avoid }` is documented as "no step is cut at a page foot", but on the live route Chrome still cuts step 1

**File:** `app/src/styles/app.css:2903-2907` (with the matching assertion in `app/src/styles/cross-cutting.test.js`, the print-block test)
**Issue:** The comment above the rule says "The Instructions follow the table's tail on the same page, in whole steps only (Mark's answer 1, K1: no step is cut at a page foot, so the steps break between steps)". The phase's own record contradicts that for the shipped route. `03.7-CONFORMANCE.md`, section Print, case P6, says:
- "Chrome splits Instructions step 1 across pages 2 and 3 ... although `.method-step` computes `break-inside: avoid` in print".
- The cause is stated as "the page's print grid, which holds the Instructions as a grid item beside the side column".
- The same section says it was "found, not fixed".

The rule only holds under the board's conditions (P1-K1, where the side column and batch layer are removed). The cross-cutting test pins only that the declaration exists, so it passes while the guarantee in the comment fails. The caller of `.method-step` rules reading the comment would believe the K1 answer is delivered. A printed bench sheet is the product's core-value artifact, and a step cut mid-sentence at a page foot is exactly what Mark's answer 1 asked to prevent.

The authors acknowledge this and defer it to Phase 4's print route. It is still a defect in what this phase ships, and the in-source comment overclaims.
**Fix:** Either fix it or make the source honest.
- If it is deferred, narrow the comment to say what is true: "a step stays whole where the Instructions are not a grid item beside the side column; on the whole route the page's print grid defeats this (03.7-CONFORMANCE.md, P6). Phase 4's print route owns the fix". Add a deferred-work row so Phase 4 picks it up.
- If it is fixed here, scope a print-only `.recipe-page { display: block }`. The conformance record measured that this keeps step 1 whole. It changes where Balance and Watch for print, which the record says is Phase 4's call, so deferring is reasonable.

### IN-01: The print block's header comment misnumbers itself after this phase inserted a block before it

**File:** `app/src/styles/app.css:2836-2837`
**Issue:** The comment, which this diff rewrote, still says the print layer is "the seventh top-level @media block, sibling to the six above". This phase inserted the screen-only list-form block (line 2599) ahead of it, so print is now the eighth of ten. The tests (`binder.test.js`, `cross-cutting.test.js`) were updated to "ten" blocks, but this comment was not. The comment at line 2742 ("a seventh top-level block") was already off before this phase; it is the same class of drift.
**Fix:** Drop the ordinal ("a top-level block, sibling to the others, never nested"). Ordinals have now gone stale twice.

### IN-02: The `.ingredient-table thead { display: table-header-group }` print rule is a no-op

**File:** `app/src/styles/app.css:2875-2877`
**Issue:** `table-header-group` is the user-agent default for `thead`. The only rules that changed `thead`'s display (`display: none` in the list form, `display: block` in the D3 grid) are both `screen`-scoped now. No non-screen rule overrides it, so in print the declaration restates the default. It is harmless, and the cross-cutting test asserts it. It does read as if something needs undoing that does not. The comment ("The table's header repeats over the rows that run on") also credits this rule for the repetition, which is the UA default, now merely no longer defeated.
**Fix:** Keep it as a guard, but say so in the comment ("restated so a future non-print rule cannot silently hide the repeat"). Otherwise remove it and its test assertion.

### IN-03: Step heads are `<td>` rows inside what are now real row groups

**File:** `app/src/ui/IngredientTable.jsx:838-851`
**Issue:** Each step group is now its own `<tbody>`, but its label ("Step 3 Build the base") is still a plain `<td colSpan>`. A screen reader gets no row-group name. Assistive technology reads "Step 3 ..." as a data cell in the first column and then the ingredient rows with no association to it. This change makes the semantic form available (`<th scope="rowgroup" colSpan>`), and the diff's own comment says "one group, one row group". The `td` was inherited, so this is a missed improvement rather than a regression. The CSS selectors (`.ingredient-table__step-head td`, lines 959, 2642) would need to follow if the element changes.
**Fix:** Optional. Use `<th scope="rowgroup" colSpan={columnCount}>` and update the two `td` selectors. Otherwise leave it and note the gap.

### IN-04: Notes' field label is the raw store key, and two source-text tests pin implementation strings

**File:** `app/src/ui/Authored.jsx:30-34` (label); `app/src/ui/RecipePage.test.jsx` (the "empty Instructions section is left out" describe block)
**Issue:** Two small, mostly pre-existing items touched by this change.
- The textarea's accessible name is `` `${listKey} note ${index + 1}` ``, which reads "beforeYouStart note 1" to a screen reader. The code moved into a visible section this phase, and the new test `RecipePage.beforeYouStart.test.jsx` now pins that string. It conflicts with the project's "plain words, no book vocabulary" rule.
- The `RecipePage.test.jsx` guards assert on the source text of `RecipePage.jsx` (for example `expect(source).toContain("'recipe-page' + (beforeRegionShown ? '' : ' recipe-page--no-before') + ...")`). A harmless reformat or rename fails them while behaviour is unchanged. The jsdom file `RecipePage.beforeYouStart.test.jsx` already covers the behaviour, including the class names, so the string-pinning tests add fragility and little coverage.
**Fix:** Give `NoteList` a human label (for example a `label` prop, "Before you start, note 1") and update the two test assertions. Drop or loosen the source-string assertions in favour of the existing behavioural ones.
