## Summary

I reviewed the diff `7a0035a..HEAD -- app/` and traced every path that writes `churn.timeToDrawTempMinutes`.

The stored value is preserved on every path that exists today:
- **Correct and Record a tasting:** `handleSaveBatch` is the only caller of `completeRecord`. It overrides the field with `batchBeingAmended.churn.timeToDrawTempMinutes` (RecipePage.jsx:1565-1568).
- **Record another and new batches:** `createBatch` stores `null`, as intended.
- **Store and transfer:** export, import and the store seam are untouched, and `seed-roundtrip.test.js` pins that the seeded 20 survives.
- **Dangling pins:** none. `batch-row__plan`, `targetValueFor`, and their CSS and tests were removed together. No remaining reference to `targetValueFor` or `.batch-row__plan` exists in `app/src`. `--sheet-size-small-print` is still used elsewhere, so no orphan token.
- **Tab-index and token rules:** unaffected. The diff adds no new interactive elements and no literals.

The remaining defects are that the preservation is fragile by construction, and that validation still iterates a field the draft no longer carries.

## Warnings

### WR-01: Preserving the stored value is an opt-in at one UI call site; the domain default is to null it

**File:** `app/src/ui/RecipePage.jsx:1561-1568` (root cause `app/src/domain/batch.js:111,185-191`)
**Issue:** `completeRecord` replaces `churn` wholesale through `buildChurn`, and `buildChurn` writes `null` whenever `churnFields.timeToDrawTempMinutes` is absent. Since `buildChurnFieldsFromDraft` no longer emits the key, every `completeRecord(batch, buildChurnFieldsFromDraft(...), ...)` call silently destroys the stored number. The only guard is a spread added inside `handleSaveBatch`'s amend branch.

Any future amend path, such as a second save handler, an undo-save, or a bulk edit, that follows the documented pattern will lose the value. The failure is silent: no error, and the reading shows nothing either way. This is the data-loss path the phase must not open, and the safe behaviour depends on every caller remembering a comment.

The tests do not catch this, because they exercise only the one call site. `RecipePage.test.jsx:811-817` and `:1038-1060` call `completeRecord(augustSecondBatch, churnFields, ...)` without the pass-through and would produce `timeToDrawTempMinutes: null`.

**Fix:** Make the domain preserve the field when the caller does not supply it, and keep the UI spread only if you want it explicit. In `batch.js`:
```js
export function completeRecord(batch, churnFields, tasting, { now }) {
  const carried = 'timeToDrawTempMinutes' in churnFields
    ? churnFields
    : { ...churnFields, timeToDrawTempMinutes: batch.churn.timeToDrawTempMinutes };
  return { ...batch, churn: buildChurn(carried), tasting: buildTasting(tasting), changed: now };
}
```
Alternatively, have `buildChurnFieldsFromDraft` take the batch being amended. Either way, add a `batch.test.js` case for `completeRecord` with churn fields lacking the key that expects the stored value to be kept.

### WR-02: Save validation still walks the hidden field, so a stray key would block silently

**File:** `app/src/ui/RecipePage.jsx:506-514` (comment at `:500-501`), `:1573-1581`
**Issue:** `parseAllMeasuredFields` iterates all of `BATTERY_FIELDS`, which still includes `timeToDrawTempMinutes`. It stays safe only because `draft.timeToDrawTempMinutes` is `undefined` and `parseMeasuredDraft` treats nullish as blank. The phase's own test (`RecipePage.test.jsx:746-751`) pins this accident (`parsed.timeToDrawTempMinutes` equals `{ok: true, value: null}`) as intended behaviour.

If a draft ever carries a malformed value under that key, the save gate fails with `invalidFieldKey: 'timeToDrawTempMinutes'`. Examples are a future draft-persistence feature, a spread of a stored batch, or the `{...draft, timeToDrawTempMinutes: 'x'}` shape the new dirty-check tests use. With no input rendered, `fieldRefs.current[key]?.focus()` is a no-op. The maker gets the generic "Check the highlighted fields" announcement and a Save that never succeeds, with nothing highlighted. This is exactly the failure mode the review brief flags: validation depending on the removed field.

**Fix:** Validate only the fields the pen draws, for example by exporting the pen's field list from the domain or filtering:
```js
const PEN_FIELDS = BATTERY_FIELDS.filter((f) => f.key !== 'timeToDrawTempMinutes');
for (const field of PEN_FIELDS) { ... }
```
Then `parsed.timeToDrawTempMinutes` is simply absent, and the `parseAllMeasuredFields` test can assert `not.toHaveProperty`. This also removes the need to special-case the field in the downstream consumer `buildChurnFieldsFromDraft`.

## Info

### IN-01: Amend test helper reproduces the save flow minus the pass-through

**File:** `app/src/ui/RecipePage.test.jsx:811-817`, `:1051-1062`
**Issue:** These tests assemble the amend flow (`draftFromBatch`, `parseAllMeasuredFields`, `buildChurnFieldsFromDraft`, `completeRecord`) without the `timeToDrawTempMinutes` pass-through. The record they build has `timeToDrawTempMinutes: null`, which is not what the app produces. The changed assertion at `:1059-1062` was moved off the field with a comment pointing at the end-to-end test. The assertions still pass, but the helper models a save that the app no longer performs, and it would mask a regression if `batchSavedStatus` ever read churn.
**Fix:** After WR-01 lands in the domain, these helpers become correct as written. Otherwise add the same spread to the helper, or assert `record.churn.timeToDrawTempMinutes` here so the divergence is explicit.
