<objective>
A step-key allocator hands out step numbers that are never reused, including after a step is removed (MAKE-02; D-05, D-05a). `nextStepKey(method)` scans the whole method, removed steps included, and returns the highest key plus one; no stored counter and no schema change are needed, because removing a step only flags it and a child version copies the whole method.

Purpose: a step's stored key is its identity (diff pairing, row portions, a batch's stepChanges and the uses lists all key on it), so v2's add-step must never hand out a key a step holds or has held. Plan 03 checks that a new recipe's first key is 1. Nothing calls the allocator yet, so no screen changes.
Output: app/src/domain/stepKeys.js, its node-environment suite, and the D-05a pin in penDraft.test.js.

Visible choices (Claude's Discretion in 07-CONTEXT.md, recorded rather than silent):
- Supported range: every step key, and the returned key, is a safe integer. The import check accepts any finite key, but from 2**53 adding one returns the same number, so the allocator would hand out a held key. Outside the range the allocator throws a RangeError rather than returning a reused key (RESEARCH Q5).
- That RangeError is one of the first throws in app/src/domain (Plan 01's TypeError is the other kind). No caller exists; switching to a returned value is a change to this file and its test only (reversible; RESEARCH A1).
- The D-05a pin goes in penDraft.test.js's existing togglePenStepRemoved describe, and removes the highest step (10), not step 3: removing step 3 of 1 to 4 gives 5 whether the step is flagged or dropped, so only removing the highest step tells the two apart (RESEARCH Q7).
</objective>
