<objective>
Settle two shapes creation will store, while the reset window is open: the drafts store's create kind with its own fit check, kept through Phase 8's useKeptDraft (D-18), and the scale definition contract with its kind (decision 3, TASTE-03).

Purpose: Phase 10's creation editor keeps a half-made recipe as a create draft (MAKE-11) and authors scale definitions; nothing it stores may change shape after this phase (criterion 2, LIB-06).

Why the payload holds steps and portions now (addresses review concern: the creation-draft contract was incomplete; reconciles criterion 2 with D-18). Criterion 2 says nothing creation stores changes shape after this phase, and the drafts store is something creation stores. Phase 10 authors everything but the steps, and Phase 11 adds the steps (MAKE-07: lead-in, text, targets, and which rows each step uses in what portions) before the first Save, while MAKE-11 keeps a half-made recipe across a closed tab in both phases. A payload without method and per-row portions would force Phase 11 to add keys to the create kind. So the payload carries them now, in shapes the app already stores: a step as the plan draft's method step (fitsMethodStep in draft.js), a row's portions as the version row's { step, grams } with grams as typed. Phase 11 then fills fields that exist.

What a later change to the payload would cost (addresses review concern, round 2: the shape is settled before Phase 10 and 11 are designed, so the tradeoff must be visible to the executor and to Mark). draftMatchesCreate refuses a payload key outside CREATE_DRAFT_KEYS and a value that fails its field's check, and the hook's restore deletes a draft that does not fit. So if Phase 10 or 11 finds the payload needs a change, which criterion 2 rules out and which therefore goes to Mark as a decision first: a new optional key leaves every kept create draft fitting (an absent optional field reads as its blank value), while a renamed, removed or newly required key, or a narrowed field check, makes every create draft kept before the change fail draftMatchesCreate at its next restore, and the restore deletes it. What is lost is at most the half-made creations kept on that device, never a saved recipe, version or batch: until Phase 11's Save a creation is only its draft. Task 2 pins the key list three ways (the field table, blankCreateDraft and a literal list), so no such change lands without a red test; the draft.js comment and this plan's summary state the same tradeoff.

What the payload gains and loses in round 3 (Mark's decisions of 2026-10-18, made after review round 2, which is why the key list changes inside this phase rather than later): it gains serveTempC, the target serving temperature in degrees C as typed (D-19: picking a style fills it from the style's default serve temperature, Clear empties it, and Phase 11's Save stores it on the version, whose field plans 09-05, 09-08 and 09-10 settle), and it loses machine and process, because the creation editor will not author either (MAKE-09 as reworded on 2026-10-18; decide-p9-pasteurise-fields, editor-only; equipment belongs to churning a batch, todo-rethink-batch-equipment). The consequence, stated plainly: a create draft cannot carry a machine, a pasteurise temperature or a hold time, and a version created in Phase 11 starts without equipment or process, as createRecipe builds it today. Nothing stored loses a field: the version's equipment slot and maxFillG (plan 09-05, D-13), the stored process field with the seeded versions' values, and the machines table (plan 09-09, LIB-09) all stay. If a later phase wants a machine or process in creation, it adds an optional key, and by the rule above every create draft kept before it still fits. No create draft exists on any device yet (this plan introduces the kind), so dropping the two keys now deletes nothing.
