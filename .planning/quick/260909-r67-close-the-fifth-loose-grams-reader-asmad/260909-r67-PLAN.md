<objective>
Close the fifth loose draft-grams reader. `asMadeTotals` in `app/src/domain/batch.js` currently
coerces a present as-made entry with `Number()` and keeps it whenever `Number.isFinite` passes, so
"-5", "1e3" and "1.2345" typed into an as-made cell move the live as-made total even though the save
gate would reject them. Quick item 260909-oow (commit be86eb5) closed the other four readers by
routing them through `parseGramsDraft`; this one was recorded as a follow-up in that SUMMARY.

Purpose: the figure on screen and the rule that governs it must agree in the last reader that still
disagrees — without touching how a stored record reads.

Output: a two-source split inside `asMadeTotals` (typed draft string -> the grams rule; anything
else -> today's check, unchanged), its docstring updated to state that split, and domain tests
pinning both sides.

## Planning-time findings that shape this plan

**1. The brief's suggested import direction is a cycle.** The brief noted `batch.js` importing from
`lineage.js` is "allowed — confirm the direction introduces no cycle before relying on it." It does
not hold: `app/src/domain/lineage.js` line 9 already reads `import { sortedBatches } from
'./batch.js'`. Adding the reverse edge makes the codebase's first import cycle and inverts the
layering (the version-pen module sits above the batch record module, not below it). The rest of the
domain graph is acyclic today (`composition` <- `figures` <- `advisories`/`diff` <- `uses`).

So Task 1 moves the rule down to a leaf: a new `app/src/domain/gramsDraft.js` holding the pattern and
`parseGramsDraft`, importing nothing. All five readers take it from there. Alternatives weighed and
rejected: (a) accept the cycle — works at runtime because both sides are hoisted function
declarations, but it inverts the layering and rests on toolchain tolerance; (b) re-export from
`lineage.js` so the four existing readers keep their import path — smaller diff, but leaves two
import paths for one function and the codebase has no `export { x } from` precedent; (c) put the rule
in `composition.js` — that module declares itself the balance math transcribed from the old slice, not
a home for a draft-string parser; (d) keep the rule in `batch.js` and import it from there — no new
edges at all, but the batch record module is the wrong owner for a version-pen rule.

**2. A stored record cannot carry a string, by enforced contract.** `app/src/store/transfer.js` lines
191-193 reject any `churn.asMade` value that is not a finite number on import (`transfer.test.js:287`
pins the string case). Combined with the post-oow save loop in `RecipePage.jsx` (`handleSaveBatch`
stores `parsed`, a number), the string branch added in Task 2 is reachable only from the live
recording draft. This is why a `typeof value === 'string'` split is safe rather than a guess — and
why the non-string branch keeps today's coercion verbatim instead of switching to a bare
`Number.isFinite(value)`, which would change how a stored `null` reads.

**3. Line numbers in the brief were observed against an older commit.** Every site below was
re-located by reading the current files: `asMadeTotals` at `batch.js:169`, its docstring at 153-168,
its existing tests at `batch.test.js:298-336`, the sole call site at `IngredientTable.jsx:466`, the
rule at `lineage.js:135-151`, readers at `RecipePage.jsx:14/503/684/1003` and
`IngredientTable.jsx:7/590`.
