2026-09-16: pen blue fills every on state; the record-versus-view distinction is
carried by a control's label and location, never by a second fill colour.

plan needs is already written there, verbatim and correct. This plan cites those
blocks **by brief line number** on purpose — so there is exactly one copy of the
CSS in the world and it cannot drift. Do not retype CSS from memory, do not
"improve" the brief's declarations, do not reorder them.

This plan adds only what the brief could not know: the exact app line numbers as
they stand today, and **three existing tests that will fail unless they are

or hover; the print sheet.

**Project rules that bind every edit** (`CLAUDE.md`, `.claude/CLAUDE.md`):
every visual value reads through a custom property in `tokens.css` — `binder.test.js`
gates on no bare px and no hex in `app.css`; agent prose, commit messages and
browser-test input values are English; surgical changes only — every changed line
traces to the brief.

### Task 2 — Show changes becomes the square and the word

**Files:** `app/src/ui/VersionRow.jsx`, `app/src/styles/app.css`,
`app/src/styles/binder.test.js`, `app/src/styles/cross-cutting.test.js`,
`app/src/ui/VersionRow.test.jsx`

**The markup.** `app/src/ui/VersionRow.jsx:223` — the className becomes
`"headnote__show-changes text-control text-toggle"` (brief line 51). Nothing else on
that button changes: `aria-pressed` already carries the state, and that attribute is
what the new CSS keys on.

**The CSS, three edits in `app/src/styles/app.css`:**

1. **Insert the `.text-toggle` block** immediately after `.text-control:disabled`'s
   closing brace — that is line 96 today, which is what the brief means by
   "`.text-control`'s own rules (currently ending line 96)", and it lands before the
   `select.ink-field` comment at line 98. Transcribe **brief lines 59-89 verbatim**:
   five rules — `.text-toggle`, `.text-toggle::before`,
   `.text-toggle[aria-pressed='true']::before`, the paired
   `.text-toggle[aria-pressed='true'], .text-toggle[aria-pressed='true']:hover`
   underline rule with its comment, and `.text-toggle:hover::before`. Note the app
   keys on the `aria-pressed` attribute where sketch 008 uses an `.on` class — the
   brief has already done that translation (brief line 91), matching `.chip-toggle`.

   **Source order is the whole mechanism, not a formatting preference.**
   `.text-control` and `.text-toggle` are both specificity (0,1,0) and both land on
   this one button. `.text-toggle` must come after `.text-control` to win the desktop
   `min-height` (32px over 24px), and must come before the touch union at line 2241 to
   lose it at a coarse pointer (44px). Both halves are asserted below.

2. **Delete** `.headnote__show-changes[aria-pressed='true']` (lines 432-436) entirely
   — the bold-plus-outline pressed state. **Keep**
   `.headnote__show-changes { margin-left: var(--gap-xs); }` (lines 428-430). The
   comment above it (lines 420-427) states "the pressed state is carried by weight and
   outline, never by hue" — that sentence becomes false the moment the rule is deleted,
   so rewrite the comment to state what is true now: the square carries the state, the
   rule keeps only this button's spacing beside its siblings, cite sketch 008 lines 91-95
   and this fix brief.

3. **Forced colours** — in the `@media (forced-colors: active)` block (line 2414), add
   `.text-toggle[aria-pressed='true']::before,` to the first rule's selector list
   (brief line 138). Task 3 adds the checkbox to the same list; whichever task runs
   second must not clobber the other's entry.

**Confirm the touch cascade — do not assume it.** The brief states (line 93) that no
new touch rule is needed because the touch union's
`.text-control { min-height: var(--touch-min) }` already reaches this element and wins
by source order, giving the 44px sketch 008 line 277 asks for. **Confirm it two ways:**

*(a) In source, as an automated assertion* — add a test to
`app/src/styles/cross-cutting.test.js` beside the existing
`'the touch union gives .text-control its own min-height'` test (line 164). `readAllRules`
returns rules in source order (`css-source.js` walks the file linearly, pushing each
pre-`@media` chunk then that block's contents), so assert on `findIndex`:
the top-level `.text-toggle` rule's index is **less than** the index of the
`.text-control` rule whose media is `'(max-width: 759.98px), (pointer: coarse)'`; and
no rule matching `.text-toggle` exists inside any media block, so the 44px can only
come from `.text-control` winning. Name the test for what it protects — that reordering
these two rules silently changes the touch target.

*(b) In a real browser, as the human check* — this suite runs under Vitest's `node`
environment and executes no cascade; it can never prove a computed pixel. Measure it
live, per the checkpoint below.

Also verified at planning time and worth recording in the SUMMARY: at a **wide** touch
viewport (`@media (min-width: 760px) and (pointer: coarse)`, line 2383) the only
`.text-control` narrowing is scoped to `.axis-mark__head .text-control` /
`.segmented-field__head .text-control`. Show changes is not in a caption line, so it
keeps the union's 44px on Mark's iPad too.

**The tests:**
- `app/src/styles/binder.test.js:70-74` — **replace, don't amend.** The rule it asserts
  ceases to exist. The replacement mirrors the defect test at line 331, including its
  `toBeUndefined()` guard. Three assertions:
  - `ruleFor(".headnote__show-changes[aria-pressed='true']")` is `undefined`.
  - `.text-toggle[aria-pressed='true']::before` declares `background: var(--pen-blue)` and
    `border-color: var(--pen-blue)`.
  - The button itself never fills and never bolds. **Do not write
    `expect(ruleFor(".text-toggle[aria-pressed='true']")).toBeUndefined()` here** — it
    would pass for the wrong reason. `css-source.js` stores a grouped selector as one
    normalised string (`.trim().replace(/\s+/g, ' ')`), so the brief's paired underline
    rule is keyed as
    `".text-toggle[aria-pressed='true'], .text-toggle[aria-pressed='true']:hover"` and an
    exact-match lookup on the bare selector returns `undefined` whether or not that rule
    exists. Instead: filter `rules` for every rule whose selector contains
    `.text-toggle[aria-pressed='true']` **without** `::before`, assert exactly one such
    rule exists at that grouped selector string, and assert its declarations contain
    `text-decoration-thickness: var(--rule-ink-field)` and match neither `background`,
    `font-weight` nor `outline`.

  Keep the four content-state tests below it exactly as they are.
- `app/src/ui/VersionRow.test.jsx:422-428` — the exact-string regex
  `class="headnote__show-changes text-control"` no longer matches. Extend it to the full
  three-class string, and extend the looser test above it (line ~413) to assert
  `text-toggle` is present too.

**Verify:**
```
npm --prefix app test
```
green — the whole suite, because `binder.test.js`'s underline census (line 213) and
outline census (line 43) both read every rule in the file.

**Done:** Show changes renders with all three classes; no
`.headnote__show-changes[aria-pressed='true']` rule exists in `app.css`; the pressed

## Checkpoint — the live browser confirmation (blocking)

The three style-contract suites read CSS **as text** under Vitest's `node` environment.
They cannot prove a painted pixel or a resolved cascade, and the sketch-findings skill's
standing rule is to measure the real DOM rather than reason from CSS source. So the brief's
Verification list is a real-browser check. Run the app (`npm --prefix app run dev`) and
confirm, in order:

1. **Desktop width, a version with a parent** — press **Show changes**: a 13px square before
   the word fills pen blue; the word does **not** bold; **no outline** appears; the underline
   stays hairline; **nothing on the line moves**. Hover thickens the square only. Tab to it —
   one 2px ink ring around square and word together.
2. **A batch pen** — check **Skipped** on a step: the square fills **pen blue, not ink**. Same
   for a row in the **Uses** checklist.
3. **Coarse pointer emulated** — this is the VERIFY-not-assume item. Read the computed value,
   do not eyeball it: `getComputedStyle($0).minHeight` on the real Show changes button reads
   `44px` at coarse and `32px` at fine, and both checkbox labels read `44px`. If Show changes
   reads 32px at coarse, the `.text-toggle` block landed after the touch union — move it and
   re-run Task 2's source-order test.
4. **`forced-colors: active` emulated** — all three fills repaint in the system `Highlight`
   and none of them vanishes.

If Mark is away, defer this checkpoint to end-of-phase UAT and record the four items verbatim
in the SUMMARY rather than dropping them; keep the automated verification run and green.
