**Choice: a width signal, not render-both-and-hide-with-CSS.** RecipePage reads one below-724 boolean, `matchMedia('(max-width: 723.98px)')`, and renders exactly one Show changes button. VersionRow renders it from 724 up and IngredientsHead renders it below 724. Why:
1. **Exactly one button exists in the DOM at any width.** Nothing hidden is left for iPad WebKit's Tab order, VoiceOver's rotor or a role query to find. The guarantee is structural. It does not depend on two CSS rules staying complementary on one query. It also does not depend on a third rule for print, where the paper's width can fall under 724 and would otherwise bring the band's copy back.
2. **The band's other below-724 edits already need JS.** 261002-wmy and 261002-wmz change labels and roles by width, which CSS cannot do without duplicates, so the band gets one signal for all of its below-724 edits.
3. **Node tests keep working.** With no window, the hook answers "not below", the same guard as useBelowDesktop and BatchRow's useBelow724. The components take the signal as an explicit boolean prop, as BatchRow's AxesGrid takes `below`, so tests render both placements without stubbing matchMedia.
4. **The head row exists only when its control does.** From 724 up, and for a first version, the heading's markup is the same as today's and needs no neutralising CSS.

The cost: rotating across 724 unmounts one button and mounts the other, so a focused control loses focus. CSS display:none would lose it too.
