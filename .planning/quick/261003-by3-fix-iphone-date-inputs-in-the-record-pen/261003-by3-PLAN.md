<objective>
Fix two iPhone bugs in the record and amend pen's date inputs. Mark approved both fixes together on 2026-10-03. The root causes are in .planning/debug/ios-tasting-date-picker.md (Evidence and Resolution).

**Bug 1. The calendar opens and then disappears on Record a tasting.** The band's Record a tasting opens the pen in one commit. That commit focuses two date inputs within one tap: React's autoFocus on the Churn date (BatchRow.jsx:683), then the addTastingAttempt effect on the Tasted date (BatchRow.jsx:499-502). iOS starts the Churn date's calendar, hands over mid-presentation, and the Tasted date's calendar is torn down.

Fix: `autoFocus={addTastingAttempt == null}` on the Churn date. addTastingAttempt is a number only for the Record a tasting open, and null for Correct and Record another. Record a tasting then makes one date focus, as Add tasting already does.

**Bug 2. iOS's Reset does nothing.** iOS's Reset calls setValue(null). That falls back to the input's value content attribute, which React keeps equal to the controlled value. So Reset re-applies the date already shown, and onChange never fires.

Fix, as approved: a no-deps useLayoutEffect, placed just after line 502, that removes the `value` attribute from both date inputs (churnDateRef, tastedDateRef) after every render.

**Planner finding: the layout effect alone is not enough. The plan adds one complement, and Task 2 proves it is needed before adding it.**

React writes the value attribute at two moments:
- **During a commit.** initInput sets it at mount, and updateInput sets it on update. The layout effect runs after the commit's mutations, so it catches these writes.
- **After the commit, on every change the input itself reports.** In app/node_modules/react-dom/cjs/react-dom-client.development.js (react-dom 19.2.8), batchedUpdates$1 runs flushSyncWork$1 first. That is the commit, so the layout effect has already run. It then runs restoreStateOfTarget (~3178), which calls updateInput (~1644), which calls setDefaultValue (~1737). That last call writes the attribute back with the new value.

This second write is exactly what happens on the iPhone. Opening an empty date fills today's date through an input event, so the attribute comes back as today's date before Mark can tap Reset.

The planner checked this in jsdom with the app's own react and react-dom, using a controlled date input and a picked date followed by a form reset:
- **Layout effect only:** after the pick, the attribute read '2026-10-01'. Reset left '2026-10-01', and onChange saw only the pick.
- **Layout effect plus queueMicrotask(strip) in onChange:** after the pick, the attribute was null. Reset gave '', and onChange saw the pick and then ''.

The debug session's WebKit stand-in was a MutationObserver that strips at any time, which hid the gap.

So the plan keeps the approved layout effect and adds one line to each date input's onChange: queue the same strip as a microtask, which runs after React's restore. Test A4 must fail with the layout effect alone before the complement goes in. If it passes, the complement is dropped and the planner's reading was wrong.

The other approach considered was a MutationObserver on the row. It needs observer setup and teardown for one job, and it replaces the approved mechanism instead of adding to it.

**A behaviour change Mark should expect (the SUMMARY reports it).**
- On the iPhone, opening an empty date's calendar fills today's date (WebKit's controlBeginEditing). After the fix, Record a tasting focuses the empty Tasted date first, so today lands in the Tasted date as soon as the pen opens, as Add tasting already does.
- That makes the pen dirty, so Escape no longer closes it. Cancel does.
- Before the fix, the first focus went to the Churn date, so on Coconut v2 (churnDate null) iOS wrote today into the Churn date instead. After the fix, Record a tasting leaves the Churn date as stored.

Purpose: Mark can record a tasting on the iPhone from the band, and can clear a date to test the empty-date case.
