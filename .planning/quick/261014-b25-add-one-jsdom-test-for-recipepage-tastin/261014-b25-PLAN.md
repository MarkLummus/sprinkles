## Finding: a rendered control cannot reach the tasting-body half (read before executing)

The page can be driven into the "undo pending" state in jsdom by clicking: Record another, Add tasting, type a note, Remove tasting. After that, though, no rendered control can make a tasting-body edit while the undo stays pending. Evidence from the current tree:

- Every tasting-body control (Tasted date, Tempering, tasting temperature, note, melt test, Melt style, From freezer) renders inside `draft.tastingOpen && (...)` at `app/src/ui/BatchRow.jsx` line 910. A removal always sets tastingOpen false.
- Add tasting is not offered while an undo is pending: SaveCeremony gets `onAddTasting` only when `!draft.tastingOpen && !pendingUndo` (BatchRow.jsx line 1155), and PenFoot has the same rule.
- Restore tasting calls `undoRemoveTasting`, which reopens the section and sets pendingUndo null in the same step (`app/src/ui/useRecordDraft.js` lines 124-127).
- `openNew`, `openAmend` and `cancel` all run `resetBlocks`, which clears pendingUndo (useRecordDraft.js lines 70-76). A kept-draft `restore` only runs on mount, when pendingUndo is already null.
- `nextTimeNote`, the one free-text field still rendered while the section is closed, is not a tasting-body field (`TASTING_BODY_FIELD_KEYS`, `app/src/domain/recordDraft.js` lines 71-79).

This matches the 05-01-SUMMARY known limit.

Options:

- **Option A: rendered controls only.** Impossible, for the reasons above. A test that tried would either never reach the state or would have to weaken the assertion.
- **Option B: page-handler seam (CHOSEN, labelled).** Mount RecipePage whole, as `app/src/ui/RecipePage.recordTasting.test.jsx` already does: an in-memory repository stand-in, a MemoryRouter, the real hooks, handlers and BatchRow. Wrap BatchRow in a pass-through `vi.mock` that renders the real BatchRow and records the props RecipePage handed it.
  - The churn half goes through real rendered churn controls.
  - The tasting-body half calls RecipePage's own handler from those props. It is the same function a tasting-body control's onChange would call if one were mounted.
  - What is observed is unchanged and real: the rendered Restore tasting button, plus the pendingUndo prop.
  - Only the trigger for the tasting-body half differs from a click, and only because no clickable trigger exists in that state.
- **Option C: accept the override the verifier drafted (no test).** That needs a decision from Mark. This plan does not take it.

Scope choices (Claude's discretion, stated):

- **Five cases, not one.** The item names five guarded sites. Testing only handleChangeRecordField would leave four of them unexercised and the item still open. The five cases sit in one describe in one file, as one `it.each` table.
- **The four unconditional retirement sites are excluded:** handleChangeRecordMark, handleClearAxisMark, handleChangeDefect and handleToggleDeclaredDefect. They have no guard, so there is no tasting-body-vs-churn composition to test, and the item does not list them.
- **A correction to the task text.** The text says existing RecipePage tests only render static markup. Six sibling files already mount RecipePage in jsdom (recordTasting, drafts, perStep, a11y, folds, beforeYouStart). The new file copies `RecipePage.recordTasting.test.jsx`, which uses the same docblock, createRoot, act and no-testing-library pattern as `useRecordDraft.test.jsx` and `useFold.reset.test.jsx`.
