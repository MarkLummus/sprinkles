<objective>
Close the four warnings in the Phase 7 code review (`.planning/phases/07-creation-primitives/07-REVIEW.md`, WR-01 to WR-04). Each one is a place where a Phase 7 constructor accepts input that `validateStoreFile` later refuses, or where `nextStepKey` refuses a key that the import check accepts.

Purpose: the three constructors (`createRecipe`, `rowFromLibraryRecord`, `nextStepKey`) say in their headers that they throw so a bad record fails at the cause, not at import. After this plan, each one refuses what the import check refuses, and the import check refuses the step keys the allocator cannot read.

Output: changes to `app/src/domain/versionRow.js`, `app/src/domain/newRecipe.js` and `app/src/store/transfer.js`, with tests in their three test files. `app/src/domain/stepKeys.js` and its test are not changed.

Out of scope: IN-01 to IN-03 from the same review; `app/src/domain/draft.js`, which holds a third, older copy of the reserved names; portion `step` validation (`validatePortion` still accepts any finite step, as Phase 7 D-08 lets a portion name a step that does not exist yet).

Decisions recorded in this plan (none contradicts Phase 7 D-01 to D-08):

- **Q-1 (WR-01): `recipeId === versionId` stays accepted.** It is not a hazard for the store. Recipes and versions are separate IndexedDB object stores, each keyed by its own `id` (`app/src/store/db.js`). Every route names the two ids in separate positions (`/notebook/:recipeId/:versionId`). The only single-id route, `/recipe/:id`, resolves `:id` as a version only (`LegacyRecipeRedirect`). The import check accepts equal ids, and the real caller will pass `freshId()` UUIDs. One sentence in `createRecipe`'s JSDoc records this, so a later review does not raise it again.
- **Q-2 (WR-01): `createRecipe`'s second argument defaults to `{}`.** A missing argument then gets the same refusal as a missing `recipeId` and names the field, not the bare destructuring TypeError the review describes. This stays within D-01, where the caller passes the ids and the clock.
- **Q-3 (WR-03): one domain copy of the reserved names.** It lives in `app/src/domain/versionRow.js` as the exported `RESERVED_ROW_IDS`, and `newRecipe.js` imports it from its sibling. `app/src/store/transfer.js` exports its existing `UNSAFE_KEYS`. The pin sits in `app/src/store/transfer.test.js`, because no domain test imports `store/`, while store tests already import domain modules (`creation-roundtrip.test.js`). This follows the way `newRecipe.test.js` pins `VERSION_SCHEMA_VERSION` to `data/olive-oil.js`.
- **Q-4 (WR-02): the entry is checked before the name.** A record with no entry gets 'library record needs an entry', not a misleading name refusal. The name is resolved as before (`ingredientName ?? entry.name`), so an explicit blank `ingredientName` is refused and does not fall back to the entry's name.
- **Q-5 (WR-04, Mark's choice, reversible): `validateStep` requires `Number.isSafeInteger(step.n)`, and `nextStepKey` keeps its RangeError unchanged.**
  - Pre-check done at planning time, so nothing blocks this: no fixture, seed or test under `app/src` uses a fractional or non-integer step `n`. A grep found no decimal or computed `n` literal in JS or JSON strings, and the only non-number `n` is the existing `n: '1'` refusal test. A runtime probe of all 8 seed groups found 21 method steps and every portion step to be safe integers. No app code creates a step yet: `nextStepKey` has only test callers.
  - Known residue, not a disagreement: a key of exactly `Number.MAX_SAFE_INTEGER` passes both checks, and `nextStepKey` then throws 'no safe step key is left after …'. That is the key space running out, which the allocator refuses on purpose. The two modules now agree on what a valid key is.
