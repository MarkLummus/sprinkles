- **R-1 (re-review WR-01): the composition check copies the import check exactly.** Both `validateRow` (`app/src/store/transfer.js` lines 113-121, on `row.ingredient.composition`) and `validateLibraryRecord` (lines 235-243, on `record.entry.composition`) require two things. First, the composition passes `isPlainObject`: `typeof` is 'object', it is not null and it is not an array. Second, every own enumerable value passes `isFiniteNumber`, meaning `typeof` is 'number' and the value is finite. An empty `{}` passes both, so the domain accepts it too: the check is no stricter than the import check and no looser. `Number.isFinite` does not coerce, so `Object.values(composition).every(Number.isFinite)` is the same predicate as `isFiniteNumber` over `Object.entries`. The check sits right after the existing entry check and before the name check, where the review placed it. It checks the record, as the entry check does, before the name, which may come from the argument. Every existing caller passes a library entry from `app/src/data/library.js`, and a planning-time probe found all 26 entries pass the check. The existing name refusals use full olive oil entries, so they still reach the name check.
- **R-2 (re-review IN-01): the review's numbers are right.** A planning-time probe ran `validateStoreFile` on a version with one method step, and `nextStepKey([{ n }])`, for each key. For 2 the import check accepts and the allocator gives 3. For 0 it accepts and gives 1. For -3 it accepts and gives 1. For 2.5, 2**53 and '1' the import check refuses and the allocator throws a RangeError. The expectations below use these values.
