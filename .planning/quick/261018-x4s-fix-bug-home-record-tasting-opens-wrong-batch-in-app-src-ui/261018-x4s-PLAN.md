<objective>
Fix bug-home-record-tasting-opens-wrong-batch. Home's Record a tasting (RowActions, AWAITING_TASTING branch, app/src/ui/RecipeList.jsx line 205) builds its path from the recipe's latest version id and the recipe's newest batch id without checking that the batch belongs to that version. activeWork (app/src/domain/lastEvent.js) gathers a recipe's batches across ALL its versions and decides the standing from the newest one, so when the latest version (v4) has no batch yet and the newest batch (v3-batch-01) was recorded against v3, the link reads /notebook/mexican-chocolate/mexican-chocolate-v4/batch/mexican-chocolate-v3-batch-01. That address names a batch v4's page does not hold, so the page opens with no batch log and no pen.

Purpose: Home's lead and rows must take the maker back to the batch that is actually awaiting a tasting.
Output: a corrected tastingPath in RowActions, and a test that reproduces the v4/v3 case.

**Behaviour decision (stated, per the planning constraint):** when the latest version has no batch and the recipe's newest batch, recorded against an older version, still awaits a tasting, Home KEEPS Record a tasting and points it at that newest batch under the version it was recorded against (its own versionId). It does not drop the action. Reasons, from the sources read:
1. The Home brief (.impeccable/surfaces/route.md line 20, "Active work first", selected by Mark) says Home should help the maker "record a batch, or return to a tasting". The batch awaiting a tasting is the v3 batch. Going back to it is the job.
2. The standing is recipe-wide on purpose. standingFor counts every batch across the recipe's versions, and the row's standing word ("Awaiting tasting", STANDING_WORDS) comes from that same standing. lastEvent.js says a row's word "can never disagree with the standing that also decides RowActions beside it" (T-03.4-G07). If Home offered nothing, the row would read "Awaiting tasting" with no way to record the tasting.
3. Sketch 011 decision 30 and route-recipe-batch.md settle that Record a tasting goes to "the awaiting batch's own address". The band already moves to the batch's own address (useRouteIntents.js lines 23-25). Home will now do the same.
Keep developing still goes to the latest version (v4): that is where development continues.

**Out of scope (not changed here):** Home's Record a tasting still lands with no route state, so it opens the batch log, not the tasting pen. Quick 261012-e8l pins this: RecipeList.nextVersion.test.jsx test 3 expects `landed.state` to be null. The bug's "no pen open" wording is the wrong-address symptom. Whether Home should also send the band's `startTasting` state is a separate behaviour change, and Mark has not decided it. Do not add that state, and do not edit RecipeList.nextVersion.test.jsx.
</objective>
