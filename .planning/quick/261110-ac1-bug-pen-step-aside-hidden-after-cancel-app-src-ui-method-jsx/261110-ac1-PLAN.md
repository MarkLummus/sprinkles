<objective>
Mark approved this bug on Mark's List (row bug-pen-step-aside-hidden-after-cancel): "a purpose or aside that holds text is always shown when the step opens."

The cause was found at planning HEAD 4e678dfa and reproduced in jsdom through the real RecipePage. useOnDemandField (Method.jsx, near "export function useOnDemandField", lines 53-76 at planning) sets its open state once, with useState(initialOpen). StepPenBody seeds it with Boolean(draftStep.purpose) and Boolean(draftStep.aside) (lines 114-117 at planning). StepPenBody is mounted once per step for the whole pen session, and Method only switches its isOpen prop. So: clear the aside and blur it, and the field closes (handleBlur sets it closed and onCollapse writes ''). Cancel on the step then puts the stored aside back into the draft (RecipePage's handleRestorePenStep). But the hook's state stays closed, so Edit this step draws "Add aside" over a draft that holds text.

The planning probe ran the three tests below against the current tree. Every setup assertion passed (the field closed, Cancel worked, Edit this step came back). The final assertion failed for aside and for purpose ("PROBE aside field after reopen: null opener: true"). The same tests against a scratch copy of Method.jsx with this plan's change passed. That run showed the stored aside and purpose, word for word, no opener, and document.activeElement BODY, so no focus was taken.

The fix: the step reads the seed again when it opens. useOnDemandField gains seedOpen(open). It sets the open state and resets openedByUser, so the focus effect does not fire. StepPenBody's Edit this step calls it for purpose and aside from the draft's own text, then calls onOpen. This sits on the one path that opens a step: openStepN is Method-local, and handleOpenStep, reached through onOpen, is its only setter.

Claude's discretion, recorded:
- The seed is read in both directions, the same rule the field already follows when the pen opens (D-23: "the field itself once the maker asks for one or it already carries a baseline value"). So the mirror changes too. Today, on a step with no aside, pressing Add aside, typing, then Cancel and Edit this step draws an empty aside field with no opener (the probe showed this on Step 3). After the fix, the step reopens behind "Add aside". Cancel put the step back with no aside, so the field is closed. This is the same defect seen from the other side, and the third test pins it. If Mark wants only the stated direction, the change is one line in handleOpen: call seedOpen only when the text is there.
- The fix lives in StepPenBody, not in the hook's own seed. The creation editor (CreationSteps.jsx lines 58-59) and the record pen's Done differently line (StepRecordingControls) use the same hook, and they keep exactly what they do now. Neither calls seedOpen, and the hook's existing code does not change.
- A derived "shown when it holds text" flag was considered and rejected. Once the maker cleared a restored field by typing, it would unmount the focused field mid-edit, before any blur.
- The tests go in RecipePage.perStep.test.jsx. They run the real handleRestorePenStep and need no harness of their own, because the file already mounts the whole page over Olive Oil v1 (Step 1 has a purpose, Step 2 an aside, Step 3 neither). No sibling in this batch plans that file: 261110-ac2 uses RecipePage.edit.test.jsx.
- Method.jsx is shared with 261110-abz, which lands first. Its edits sit at the isShowingChanges line and the recording branch (about lines 590 and 779-814 at planning). This plan's sites sit above them (the hook, StepPenBody's hook calls, the Edit this step button at about 425-431). Find every site by content.

Purpose: after a Cancel on a step, its purpose and aside reopen as they were, so the maker never sees "Add aside" over text the step still holds.
Output: a small, additive change to Method.jsx, and three end-to-end tests that fail without it. One commit.
</objective>
