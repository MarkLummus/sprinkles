<objective>
Fix Mark's List row `bug-edit-missing-after-misfit-draft-dropped` (Mark answered "Fix it" on 2026-11-14). When the recipe page deletes a kept pen draft that no longer fits its version, the draft also leaves the page's drafts list, so on a first version with no batch Edit shows at once instead of after a reload.

**Cause, reproduced at planning HEAD 168a5da2 with a temporary test file. The file was then removed and the tree is clean.** Three steps:
1. `useKeptDraft`'s restore effect, in the `if (!fits)` branch of app/src/ui/useKeptDraft.js, calls `repository.deleteDraft(versionId, kindKnown ? record.kind : null)` and returns. Nothing tells the page.
2. RecipePage's `drafts` list from `useRecipeData` was read once by `listDrafts`, and it still holds the deleted record.
3. `editStateFor` in app/src/domain/firstVersion.js returns null while any list entry carries this version's id (`if (kept.length > 0) return null`), so Edit is not drawn.

The probe at HEAD gave these readings:
- A misfit plan draft on seedVanilla: deleteDraft calls were `[["v-vanilla","plan"]]`, the store no longer held the key, no pen was restored (no Cancel), and the acts row read `["Next version","Print sheet"]`, with no Edit.
- A garbage-kind draft (`kind: 'scribble'`): calls `[["v-vanilla",null]]`, the store was cleared, and Edit was missing as well.
- A rejected misfit delete: Edit stayed away. That is correct, and it passes at HEAD.

**The fix, probed at planning on the working tree and then reverted with git checkout:** five added lines, none removed.
- useKeptDraft takes an optional `onMisfitDeleted` (default a no-op). The misfit branch chains `.then((deleted) => { if (deleted) onMisfitDeleted(); })` between its deleteDraft and its existing `.catch`.
- RecipePage passes `onMisfitDeleted` as a callback that calls `setDrafts` with a functional updater keeping only the entries whose `versionId` is not this page's `versionId`.

With that change the probe tests passed (22/22), and the RecipePage*, CreationPage*, useKeptDraft* suites passed (15 files, 416 tests).

**Same mechanism as the Cancel fix (6565fbed), recorded.** That fix's `discardDraft` wrapper in RecipePage.jsx trims the list with `setDrafts((kept) => kept.filter(...))` after the delete resolves. This fix does the same from the one place the page cannot already reach, the misfit branch inside the shared hook. A callback is the least wiring that does it. It matches the hook's existing callbacks (onRestorePlan, onRestoreRecord, onRestoreCreate, onPageStatus), and a default parameter leaves CreationPage untouched. This adds no new abstraction: no new module, no helper, no shared filter.

Claude's discretion, recorded:
- **The trim filters by versionId alone. It does not use the Cancel fix's pen-kinds filter.** The drafts store is keyed by versionId (`createObjectStore('drafts', { keyPath: 'versionId' })`), so a delete that resolves true leaves nothing under this version's key, whatever kind the record carried. Filtering by versionId is therefore exact. It also covers the garbage-kind case the row asks to trim, which the Cancel fix's `['plan', 'record', 'amend']` filter would keep.
- **The trim runs only when deleteDraft resolves true.** `deleteDraft(versionId, kind)` resolves false when it deleted nothing (store.repository.js: the stored record is absent or of another family). The null call always resolves true. "Trim only what the store dropped" keeps T-11-56: Edit is never offered while a record may still be stored.
- **The trim waits for the delete. It does not change `setDraftRestoreDone(true)`'s place or timing**, so the persist effect and the route intents gate exactly as before.
- **Ordering against the drafts read, an assumption the browser walk tests.** The restore does not wait for `draftsLoaded`. In IndexedDB, `listDrafts` is issued at mount, before `getDraft` and the misfit `deleteDraft`. The readwrite delete waits for that earlier readonly transaction on the same store, so the list arrives before the trim runs. If the WebKit or Chrome walk of the fixed build still shows Edit missing while the component tests pass, that ordering does not hold. Stop and report. Do not add a draftsLoaded gate on a guess.
- **The browser walk uses scratch builds served by `.planning/phases/08-split-the-recipe-page-along-its-jobs/08-walk-server.mjs` on ephemeral 127.0.0.1 ports,** as quick 261114-gxe did. It never writes app/dist, never starts a Vite process and never touches the preview on 4173. The row's `npm --prefix app run build` runs as that same script with a scratch `--outDir`. No seeded version qualifies as a first version with no batch (planning ran firstVersionRefusal over seedRecipeGroups: every root has a batch or a child). So the probe makes one inside a fresh browser context: it deletes Olive Oil v1's batches from IndexedDB, then stores the misfit draft. The seed does not re-add them, because seedIfEmpty returns once any version is stored.
- **No device check for Mark.** A misfit draft cannot be produced by hand on the iPad. The WebKit walk is the engine evidence. Per the list rule, a single check goes in chat, and there is none to give.

API coverage, schema push and assumption-delta do not apply: no external API, no schema file, no model generalised.
