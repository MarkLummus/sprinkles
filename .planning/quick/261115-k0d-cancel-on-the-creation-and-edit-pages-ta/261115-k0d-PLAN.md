<objective>
Close bug-creation-cancel-save-race. Mark answered the row on 2026-11-15: "Fix it: Cancel takes the same lock Save does, released if the delete fails". On the New recipe page and the Edit page of a first version, `handleCancel` in app/src/ui/CreationPage.jsx (one handler serves both modes) reads the save lock but never takes it. A Save pressed while Cancel's `writer.discardDraft({ final: true })` delete is out therefore writes the recipe, and Cancel then leaves for the Notebook with its discarded line, or for the version page. After the fix, Cancel takes `savingRef` before the delete. It gives the lock back only when the delete fails. On success it keeps the lock until the page navigates away, exactly as now.

Purpose: a Save during Cancel does nothing, the same as a second Save does today. A failed Cancel still leaves Save and Cancel working.
Output: two added code lines in handleCancel (with its comments brought up to date), five new test cases across CreationFlow.test.jsx and EditFlow.test.jsx, a green full suite and a scratch build.

Decisions taken in this plan (Claude's discretion, within Mark's answer):
- Same ref, no busy state. Cancel sets `savingRef.current` only and never calls `setSaving`. So `saving` stays false, Save keeps reading Save, and Cancel, Save and the fields stay enabled while Cancel's delete is out. This is the screen as it is today, as Mark asked. No visible busy state is added.
- The lock stays held after a successful delete. On the create page Cancel awaits one more read (`repository.listDrafts()`) before it navigates. A Save pressed during that read would write a recipe whose draft has just been discarded. Because the lock is released only in the delete's catch, the fix closes that time too, and C1 pins it. Nothing about what Cancel does after a successful delete changes.
- One consequence to name: `savingRef` is "the lock and the gate in one" (the comment above it). While Cancel holds it, `setCreateDraft` drops edits, exactly as it does during Save. The fields are not disabled, but a keystroke typed during those few milliseconds is not accepted. Today such a keystroke is accepted, held, and written back if the delete fails. This is the "same lock" Mark chose. It cannot be hit by hand, and it is recorded in the SUMMARY. No task works around it.
- A second Cancel pressed while the first delete is out now does nothing. Today it would start a second delete. It is the same guard, and it is harmless.
</objective>
